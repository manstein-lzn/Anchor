# P3 数据中枢读侧：报告

执行：2026-10-21，按 [总体架构](../../../docs/harness-data-hub.md#当前职责与依赖) 第 6、7、9 节和 [任务书](../../../docs/archive/design-records-2026-11-04/harness-data-hub-tasks.md)，由主 Agent 直接实现。

## 做了什么

新 crate `anchor-hub`，一个 crate，内部分层：

| 层 | 模块 | 内容 |
| --- | --- | --- |
| L0 来源 | `source` | trait `HistorySource`：列出资源、读当前状态、从某个位置之后继续读历史。两个实现：`DataRoot` 走内核的 `HistoryReader`，只读、不拿租约、不建文件；`Stored` 把任何内核 `Store`（例如测试用的 `MemoryStore`）当来源读 |
| L1 投影 | `table` | `Projector` 按"数据根 + 资源 + 位置"把每条记录展开成一行，记住每个资源读到哪里，下次只投影新追加的记录。trait `FactTable` 和内存实现 `MemoryTable`。配置清单只有在摘要和名字一致时才收录 |
| L2 轨迹代数 | `query` | 纯函数：任务和它的步骤、按天然标识把 Run 的节点结果和观察记录连起来（两边缺一边的保留并计数）、模型轮次和工具调用的时间线、空档和空档位置、分组、连续重复、分布 |
| L3 分析器 | `analyzers` | trait `Analyzer`（身份、版本、所需字段、运行方式、报告）。两个内置分析器：体检报告 `health`、停滞检测 `stall` |
| L4 对外接口 | `adapters` 和 `anchor-hub` 可执行文件 | 自动发现给定目录下的所有内核数据根；`health`、`stall`（可 `--follow` 持续跟读）、`rows` 三个命令，文本或 `--json` 输出 |

**投影只取 Harness 事实**：谁提交、何时、在哪个配置下、动作、槽位、裁决、任务状态，以及观察记录里的事实。其他提交内容、结局的文字说明、证据都不投影，所以投影表里没有业务内容；测试用带标记的业务内容验证了这一点。

**体检报告**包括：

- 记录：行数、数据根数、盖了时间和配置的比例、按"动作/效果/原因"统计的裁决；
- 任务：状态分布、结算耗时；
- 调用覆盖：两边都记下的、只有一边的；
- 工具效率：次数、成功率、失败类别、耗时分布、参数形状数；
- 模型轮次：轮数、token、延迟、缓存命中；
- 时间去向：模型、工具，以及空档按位置分为启动、工具到下一轮、收尾；
- Run 步骤：Op 节点步骤耗时，以及 Agent 节点在调用之外的开销；
- 按配置分组的统计。

体检报告里的发现类别：`not_accepted`、`task_not_done`、`unobserved_invocation`、`observation_without_result`、`counts_disagree`、`tool_calls_dropped`、`invocation_not_completed`、`call_without_time`、`tool_failures`、`call_corrected`、`configuration_unknown`、`startup_heavy`。

**停滞检测**的发现类别：

- `stalled_task` 和 `parked_task`：任务长时间没有新记录；
- `idle_gap`：调用内长时间没有任何观察到的活动；
- `slow_tool_call`、`slow_model_turn`：比同类中位数慢很多；
- `repeated_failure`：同一工具、同一参数形状连续失败。

阈值是参数，写进报告。数据缺少某个字段时，分析器报告"不适用"，不猜测。

每条发现都引用它依据的记录（数据根、资源、位置）。

## G1：用真实 Run 的数据发现以前不知道的问题

数据：

- P2 的 15 次真实 Flash 运行；
- 本阶段用当前代码编译的 Host 新跑的 15 次（T2 10 次、T1 5 次，全部 completed）。跑的时候停滞检测一直以 `--follow` 跟读，全程没有报错，也没有误报。

报告原文见 [health.json](health.json)、[stall.json](stall.json)。复现命令：

```text
anchor-hub health .local/harness-hub-p2/runs .local/harness-hub-p3/runs
```

原始数据不入库。

### 1. 模型用量报告要等这一轮的工具调用跑完才到，时间按字面理解会重复计算

- **现象**：P2 的 77 个模型轮次，用量报告全部在这一轮请求的工具调用结束之后才被 Host 看到，中位数晚 1 毫秒，最多晚 2 毫秒。也就是说 `observed_at_ms` 不是模型响应结束的时间，而是这一轮处理完的时间。
- **怎么发现的**：中枢第一版按字面把"观察时间往前推 elapsed"当作模型时段，结果模型、工具、空档三者之和是调用时长的 104.8%。交叉核对之后找到了原因。
- **修正**：在 L2 里，一轮的结束时间取"它请求的第一个工具调用开始的时间"和"观察时间"中较早的一个，再往前推 elapsed。修正后三者之和正好是 100%。这一点也写进了 `anchor-facts` 的使用说明。
- **意义**：以后任何人直接按字面用这个字段，都会高估模型时间、错判空档。这是 P2 没有意识到的记录语义陷阱。

### 2. 每次 Agent 调用在第一次模型请求之前固定要等 0.36 到 0.6 秒

两批数据结果一致：

| 配置 | 次数 | 第一次模型请求之前（中位数） | 占调用时长 |
| --- | --- | --- | --- |
| T1 `answer`：单轮、无文件工具 | 10 | 366 毫秒 | **17%**，触发 `startup_heavy` |
| T2 `worker`：多轮、有读写目录 | 20 | 578 毫秒 | 约 6% |

- 有读写目录的配置要多等约 210 毫秒。
- 对于轮次少、调用多的 Graph，这是一个明确的 Harness 优化方向。
- 中枢只能指出"时间花在第一次模型请求之前"，具体是 Goose 进程启动、ACP 会话建立，还是工具和沙箱准备，需要单独测量。

### 3. 编排开销和 Op 节点的耗时，不改 Runtime 就能得到

P2 留下的缺口之一是"Op 节点耗时没有记录"。实际上，同一个 Run 里相邻两条记录的内核时间差，就是串行步骤的耗时（含调度）。再和观察记录对齐，就能分出 Agent 节点在调用之外的开销。

| 指标 | 结果（30 次 Run） |
| --- | --- |
| Op 节点 `prepare`（几条 `printf`） | 中位数 152 到 168 毫秒 |
| Op 节点 `verify`（几条 `grep`） | 中位数 198 毫秒 |
| Agent 节点在调用之外的开销（调度、记录观察、提交结果） | 中位数约 110 毫秒，其中记录观察约 39 毫秒 |
| 调用内部：工具结果到下一次模型请求 | 中位数 32 毫秒 |
| 调用内部：最后一个活动到调用结束 | 中位数约 45 毫秒 |

所以"Op 节点耗时"不必再改 Runtime 来补。并行步骤时，时间差只是上界，文档里已注明。

### 4. 顺带确认了 P2 的修复

P2 数据里 `final_result` 的参数形状有 4 种，新数据只有 2 种，每个任务一种。多出来的两种，正是 P2 修复前参数 key 顺序造成的。

### 结论

G1 通过：

- 第 1 条是记录语义上的缺陷，已在读侧修正；
- 第 2 条是以前不知道的 Harness 开销，给出了量化数据和优化方向；
- 第 3 条说明一个原以为要改 Runtime 的缺口，用已有的时间戳就能补上。

其中第 1 条是靠交叉核对发现的，第 2、3 条是靠跨数据根关联发现的；这两种能力正是中枢要提供的。

## 和架构草案的偏差

- **`reads.rs` 不改用 `HistoryReader`**。它的所有调用方都在 Host 进程内，而 Host 本身就是写入者，读取时拿资源租约正好和提交串行。改成不拿租约的读取，反而会改变并发语义。中枢不经过它，所以保持原样，不在 P3 里改 Host。
- **L5 提议和只读 MCP 接口留到 P5**，和第 11 节的阶段划分一致。
- **体检报告包含了工具效率**。第 7.1 节原本把"工具效率"列为单独的分析器；它和体检报告读的是同一批事实，先合在体检里，等它需要单独演进时再拆出来。"内核规则触发统计"同理，体现为体检报告里的裁决统计和 `not_accepted` 发现。

## 已知边界

- **投影表在内存里**：每次运行 CLI 都从头投影，30 次 Run 用时不到 1 秒。数据量大到需要时，再加列式文件或嵌入式数据库作为 `FactTable` 的另一种实现。
- **任务按 `run/` 命名、节点结果按 `{node}#{invocation}` 槽位**和观察记录关联，这是 Runtime 的命名约定。不按这个约定的记录仍然能投影，只是关联不上。
- **跨数据根的时间**来自同一台机器的系统时钟，不保证单调。多 Host 汇总时需要考虑时钟偏差。
- **8077 服务的数据**是 P1 之前写的，没有时间和观察记录。分析器对这类数据如实报告"不适用"。
