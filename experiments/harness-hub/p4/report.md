# P4 评测任务集：报告

执行：2026-10-21，按 [总体架构](../../../docs/harness-data-hub.md#当前职责与依赖) 第 5.2、5.4、6 节和第 11 节的 P4，由主 Agent 直接实现。代码在 [`experiments/harness-hub/eval/`](../eval/)；原始运行数据在 `.local/harness-hub-p4/`，不入库。

## 做了什么

### 评分成为事实

- **`anchor-facts` 增加评分词汇**：
  - 资源 `grade/{run}`；
  - Validator `validator/grade`：只接受人或宿主代码，模型不能评分；内容必须是名字唯一的检查项，并且属于该 Run；
  - 授权 `GraderOnly`；
  - 内容 `Grade { version, run_id, task, task_version, checks: [{name, passed}] }`，只有检查项名字和是否通过，不带业务值。
- **新 crate `anchor-eval`**：唯一的评分写入方。评分存在评分方自己的数据根 `kernel-grades`，有写入租约，走同一个 `Kernel::submit`。提交者的配置摘要是评分器配置的摘要，即任务定义、期望值和评分代码。重新评分时在同一段历史里追加一条记录。围栏测试保证 workspace 里只有这个 crate 记录评分。
- **中枢读评分**：
  - 投影评分行；
  - `Query::grades` 给出每个 Run 最新的评分；
  - 体检报告新增质量部分：按任务列出平均分、全对比例、各检查项通过率，以及这些 Run 的 token、Agent 耗时和工具调用分布；
  - 新发现类别 `check_failing`；
  - 分布统计增加了标准差，用来估算样本量。

### 任务集

**每个任务是一个 Graph**，由运行器组装：

1. 固定的 `prepare` Op 写入合成输入；
2. 待测的 AgentNode；
3. 固定的 `grade` Op 用 [`graders.py`](../eval/graders.py) 检查输出，打印检查项，总是正常退出。

以后的变体只改第 2 段，评分器不在可改范围内。运行器从 Run 自己的历史里读出检查项，经 `anchor-eval` 记成评分。被运行器看门狗中止的 Run 没有结果，不评分，单独计数。

| 任务 | 档 | 内容 | 检查项 |
| --- | --- | --- | --- |

| logs | 精确 | 12 个日志文件的统计（按服务计数、分位数、部署之后的错误、最忙的一分钟） | 6 |
| contacts | 精确 | 按明确规则规范化联系人（去重、大小写、电话格式、排序） | 5 |
| repair | 精确 | 修一个 Python 模块，可见测试不完整，隐藏测试分组检查 | 5 |
| schedule | 精确 | 会议排期，满足各类约束；任何可行解都接受 | 6 |
| audit | 精确 | 多币种付款和退款审计（周末汇率回退、四舍五入到分、取消订单应退款） | 8 |
| incident | 精确 | 四种日志格式和时区下的请求分析（重试、多行堆栈、分位数） | 8 |

### 评分可信的依据

[`test_eval.py`](../eval/test_eval.py)，21 项：

- 每个任务的参考解都能通过全部检查项；
- 针对性的错误只让它该失败的那些检查项失败，例如：
  - repair 只修可见测试能发现的缺陷，`parse`、`merge`、`value` 仍然失败；
  - fleet 用一车一客户的解只能拿到可行性分；
  - 关键词分类的 triage 会漏判 P1；
- 缺失或损坏的输出让所有检查项失败，评分器不抛异常；
- **五个数据任务的期望值，由另一份只读输入文件的独立实现重新算出，结果一致**（[`solvers.py`](../eval/solvers.py)）；
- routing 的最优值由穷举验证，与动态规划一致；
- 输入、期望值和评分器摘要是确定性的；
- 嵌入 Graph 的评分脚本和评分器本身结果一致；
- 评分器只用标准库。

另外两项检查在真实环境里做：

- **用真实 Host 运行参考解**：11 个任务全部得满分，说明评分器、Graph 连接和沙箱三者一致；
- **重新评分的一致性**：62 个 Run 用本地评分器从 Run 自己提交的文件重新评分，结果和沙箱里 `grade` Op 当时打印的完全一致。

### 结论 1：这个基线下，质量几乎总在上限，可测的是效率

- **原计划的"难题"在这个基线下并不难。** 第一版精确档（前 5 个任务）有 9/10 拿到满分。于是我加了第二批规则更多、陷阱更多的任务，12/12 满分。再加两个分级任务，fleet 和 triage 也都满分。
- **fleet 的情况尤其说明问题。** 我自己的多起点启发式搜到 1,055.62；Agent 搜到 1,047.53。我用破坏重建搜索复核，也收敛到 1,047.53，于是把已知最好解更新为这个值（fleet 升到 v2）。之后 6 次完成的 fleet 全部精确到达 1,047.5336。
- **原因**：会写代码的 Agent 解精确规定的任务，靠的是写程序而不是心算，规则再多也只是程序多几行。真正的差异只出现在两处：
  - contacts 有 2/5 系统性误读电话格式，把 11 位写成了 10 位；
  - 其余差异在花多长时间、多少 token 达到同样的质量。
- **对 P6 的含义**：对这个模型和这套 Harness，质量是约束而不是目标。受控实验应当比较"在质量不下降的前提下，时间和 token 是否下降"。在可承受的样本量下，Agent 时间是更稳定的度量：检测 20% 的差异，多数任务每边 4 到 21 次就够；token 的波动大得多。
- **要得到质量梯度**，需要限制资源的变体，例如时间上限或步数上限，fleet 天然按程度给分；或者换更弱的模型。这本身就是 P6 要比较的 Harness 变量，任务集已经能支持。

### 结论 2：无上限的"尽量好"任务需要停止条件

fleet 的指令是"尽量接近已知最好解"，Agent 会一直优化：

- 6 次用了 258 到 584 秒；
- 第 7 次超过运行器 900 秒的看门狗，被中止。中止前它写了十几个求解脚本（模拟退火、GRASP、LNS 等），这正是方向文档里"Agent 探索出的路线"。

被中止的 Run 有两点值得注意：

- 中枢的停滞检测立即报出 `stalled_task`（"executing with nothing recorded for 16 min"）；
- 它的观察事实全部丢失，因为事实在调用结束时才写入。这就是 P2 记下的边界，第一次在真实数据里出现。

## 新发现的 Harness 缺陷（由中枢的工具统计发现）

体检报告的工具效率部分显示，`anchor_edit` 成功率只有 87.7%，`anchor_read` 91.3%，并且有 `call_corrected`：模型在失败后改了参数形状再成功，也就是靠撞墙学会接口。在本地对照错误原文（不入库），归纳出三个以前不知道的缺陷：

1. **`anchor_read` 和 `anchor_edit` 不接受 `/workspace/...` 绝对路径，而 `anchor_run` 接受**。任务指令和 Agent 的习惯都用 `/workspace/x`，于是：
   - 19 次 `anchor_edit` 失败，占它全部调用的 11%；
   - 9 次 `anchor_read` 被拒，占 8.7%。
2. **`anchor_edit` 和 `anchor_read` 的路径错误信息写的是 `anchor_run not_executed`**，并附上 `anchor_run` 的用法提示 `Pass {"command": [...]}`。工具名和建议都是错的。
3. **`anchor_run` 在 AgentNode 里也公开了 `project` 参数**（`node_tools.rs:619`），但这个参数只在 Pilot Session 可用。13 次调用因此被拒，原因是"development projects are available only in a Pilot Session"。

三者合计约占全部工具调用的 4%，并且每次失败都多一轮模型请求。这正好可以作为 P6 的第一个受控实验：修复这三处作为变体，用这个任务集比较工具失败率、时间和 token，并确认质量不下降。

另外一个环境缺陷：沙箱里的 `/usr/bin/python3` 指向 `/etc/alternatives`，而沙箱没有挂载 `/etc`，所以 `python3` 不可用，只有 `python3.12` 可用。任务里的 Op 改为显式调用 `python3.12`。

## 已知边界

- **任务数量还少**：11 个任务、每个 5 到 7 次。要做受控实验，每个变体还需要按上表的样本量补跑。
- **任务都是单个 AgentNode**。多节点、多 Agent 协作和 Plugin 使用还没有覆盖。
- **评分器版本和评分历史**：fleet 从 v1 升到 v2 后，旧 Run 被重新评分，每个 Run 的评分历史里保留了两条记录。被看门狗中止的那个 Run，在规则改成"不评分"之前已经记下一条全失败的评分；历史只追加，这条保留，分析时按 `guard` 排除。
- **只用了一个模型**（平台默认 Flash）。质量上限的结论只对这个模型和这套 Harness 成立。
