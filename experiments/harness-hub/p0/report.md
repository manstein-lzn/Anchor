- **通过率**：两个任务都是 30/30，处在上限。以 Wilson 下界作为保守估计，n=30 时只能检测出约 23 个百分点的通过率下降。

## 主要发现

1. **多步任务的波动主要来自路径长度，而不是每一步本身。**
   - T2 的轮数从 4 到 17 不等。轮数和总 token 的相关系数是 0.98，和墙钟时间的相关系数是 0.84。
   - 按每轮折算之后，token 的 CV 从 0.45 降到 0.10，时间的 CV 从 0.31 降到 0.15。
   - 也就是说，"Agent 走了哪条路"本身就是最主要的变量。这直接支持方向文档里"轨迹优先"的设计：路径必须作为一等事实记录，分析时要按轨迹分层，或者把轨迹当作协变量来调整。
2. **工具失败全部是 Harness 接口摩擦。** T2 一共 216 次工具调用，失败 5 次，占 2.3%，Agent 每次都自己恢复了：
   - 2 次调用了不在白名单里的 `find`。白名单是本夹具设置的，比 8077 的白名单窄；但它说明 Agent 会默认使用这个命令。
   - 2 次 `anchor_read` 用了不在授权输入范围内的绝对路径。
   - 1 次 `anchor_run` 漏了 `command` 参数。

   这类摩擦会直接增加轮数和成本，正是体检报告应该自动发现的东西。
3. **单步任务的噪声很低。** T1 的输入 token 完全一样，总 token 的 CV 只有 0.03，墙钟时间的 CV 是 0.14。

## G0 结论

暂定目标是"每组 30 次时，token 和墙钟时间能检测出不超过 20% 的相对差异"。

- **T1 达到**：总 token 2%，墙钟时间 10%。
- **T2 按原始总量没有达到**：墙钟时间 22%，总 token 32%。要达到目标，每组需要约 100 次，这时分别是 12% 和 18%。
- **T2 按每轮折算后达到**：每轮 token 7%，每轮时间 11%。

**判断：受控对比在统计上可行，但设计时必须考虑路径长度。** 对 P6 的建议：

- 效率对比同时报告总量和每轮指标；如果比较的是"是否改变了路径"，就把轮数单独作为结局指标；
- 多步任务的每组样本量按 100 次起步；或者按轨迹分层，用协变量调整（例如 CUPED）来降低方差；
- 质量指标需要更难的评测任务。现在两个任务都在上限，没法区分好坏，这是 P4 评测任务集要解决的问题。

## 限制

- 只测了一个时间段、一个模型、两个很小的任务。不同时间段、Provider 负载和更长的任务，噪声可能不同。

- T2 的命令白名单是本夹具设置的，比 8077 窄，所以 `find` 那两次失败部分是夹具造成的。
