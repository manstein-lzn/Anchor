# 减少长会话历史重复解析与查询内存放大

常驻 Run 的每条历史记录带完整 after 快照，状态读取会为了恢复与累计成本重新解析全部历史；列表、时间线及启动 Probe 又重复取得完整快照集合。长历史在普通网页轮询下产生大量重复读取和分配，并在共享内核写锁里放大提交延迟。

本改动让 FileStore 首次逐条校验后保存非持久摘要，自己的同步追加增量更新，外部改写/替换/截断及异常写入使缓存失效；摘要保留原裁决条目和成本、最后 after 的位置，不保存全部状态。Host 恢复和 Probe 消费相同的轻量条目。一次 submit 的目标资源只读一次；编号使用完整历史条目数量。

JSONL、resource.json、恢复和计费语义不变：完整行损坏仍报错，残缺尾部不计入，拒绝/版本过期裁决也计费；恢复不信任快照的 spent，使用同一文件句柄读最后 after。

同机同一份 275 MiB/525 条历史副本，12 次 `/runs`＋`/timeline` 查询读取量 12.9 GiB→24.2 MiB，中位数 4451→32 ms，单进程峰值 RSS 1109→47.6 MiB；一次合成 Write 读取量 552→1.01 MiB。不是完整 Goose 对话或多 worker 长期 soak。

验证：Kernel 60 项、Runtime 159 项、架构围栏 5 项通过。Host 普通回归首轮 1089 项通过、2 项网络 helper/地址空间环境失败、3 项忽略；两项补环境后单独通过，最终相关 40 项再过。Kernel 严格 Clippy 通过；Host 存在上游既有的新工具链告警，仅放行已有两类后通过。独立审查的文件替换恢复及解码一致性问题均已修并覆盖。

未部署、未新增真实 Provider 验收；不处理每条完整快照带来的磁盘增长。完整指标、命令、失败和未覆盖范围见 `experiments/kernel-history-performance/README.md`。
