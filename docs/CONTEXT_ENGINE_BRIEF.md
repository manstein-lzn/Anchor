## 2. 背景：Anchor 是什么

一个 **agent graph 运行时**。要点只有几个，其余与本次讨论无关。

**一个图 = 节点 + 边。** 节点类型包括 `agent`（调用模型的节点）、`tool`、`verifier`（判定）、
`parallel`、`join`、`loop`、`approval`、`artifact` 等。

**一次 run = 把一张【已发布且不可变】的图，在一个具体输入上执行一遍。**

**四个已经建立的机制，它们和本次讨论直接相关：**

```
① 声明式输入（I8）
   一个节点只看到它的【入边声明】给它的东西。
   没有隐式全局共享——节点不能读工作区、不能读别的节点的中间状态。

② 累积在工件里，不在上下文里
   一次节点执行 = 组装一个 prompt + 调用模型 + 结束。
   下一次执行（哪怕是同一个节点的下一次）是【全新的 prompt】。
   累积的产物（证据、代码、结论）作为不可变工件存在外部。

③ 事件日志是唯一真相
   发生过什么 = 事件序列。任何摘要、记忆、投影都是【派生物】，不是真相。
   重试不重放历史。

④ 确定性验证 + 完成门
   节点的完成可以由一个确定性验证器判定（JMESPath 表达式），而不是由模型声明。
```

**换句话说：Anchor 目前的形状是"每个节点每次全新投影"。** 这一点很重要，因为它决定了
累积发生在哪里——**累积发生在工件里，不发生在上下文里。**

## 3. 我想要什么

### 3.1 场景

```
一张拓扑固定的图（节点与边不再改变）
在【单次 run】内连续工作 几十小时
期间累积的信息达到 几千万 token 量级
```

**"拓扑固定"是我明确设定的前提。** 我不关心"如何设计一张能自我改写的图"，
我关心的是：**给定一张固定的图，它能不能无限地跑下去。**

### 3.2 我要的性质

我称之为**认知不漂移**。让我尽量说清它不是什么意思：

```
不是：模型输出完全可复现           —— 那是确定性，我不要这个
不是：不花太多钱                   —— 成本是次要问题
不是：产出质量更高                 —— (见 §4.3，有实测证据说这不由上下文技巧决定)
是：  在任意长的运行中，agent 的决策不会因为"它已经跑了很久"而系统性偏离
```

**反面例子**（实测，见 §4.4）：一个学术调研 run，跑到后面出现了——
评审违反自己声明的标准、同一个缺陷被"修"了 18 次、引用编号漂移。
**这些不是随机波动，是系统性偏离。**

### 3.3 验证方式的要求

**我不想通过跑一个几十小时的任务来验证。**

理由：那样的验证一次只能给一个数据点，非常昂贵，而且我怀疑它根本无法区分
"设计对"与"这次运气好"。

**我想要的是**：把不漂移变成一个**可以推理、并且可以用单元测试验证的命题**——
测的是**单步转移的性质**，而结论覆盖任意步数。

**如果这不可能，那本身就是一个重要答案**，请明确告诉我。

## 4. 我已经确知的事实（全部实测，可复算）

**这些不是推测，是我今天/最近亲手测出来的。你可以质疑测法，但请先认为数字是真的。**

### 4.1 硬墙的确切位置

```
上下文窗口 = 1,048,576 tokens（模型文档写的 1M）

实测：
  1,000,000 字符 →   125,032 tokens → 成功
  6,000,000 字符 →   750,032 tokens → 成功
  8,500,000 字符 → 1,095,300 tokens → HTTP 400

错误原文：
  "This model's maximum context length is 1048576 tokens.
   However, you requested 1095300 tokens
   (1062532 in the messages, 32768 in the completion)."
```

**三个值得注意的细节：**

```
· 超限是 HTTP 400，不是 5xx —— 即"这个请求无效"，不是"稍后重试"
· 补全预留【也计入】：可用输入 = 窗口 − max_tokens（这里 32768）
· 错误消息【精确且可解析】——它告诉你超了多少
```

### 4.2 缓存的经济结构（我们的 provider）

```
缓存命中    $0.003 / M tokens
缓存未命中  $0.15  / M tokens      → 比值 50
输出        $0.6   / M tokens

一次真实 campaign 的账单构成：
  输出        61.7%
  缓存未命中  36.0%
  缓存命中     2.2%
```

**含义**：已经命中缓存的部分几乎是免费的。**改变 prompt 的【前缀】会让整段前缀变成未命中，
按 50 倍计价。**

### 4.3 三项对照实验（关于"上下文该放什么"）

在同一真实 run 的同一真实切点上，让**同一个全新 agent**、用**同一套问题**、看不同材料：

```
实验① 考卷（七问：目标/已确立/冲突/受阻/下一步…），盲评，每条件 3 次
  A 原始材料   141,033 字符  → [15,20,18] 均值 17.7
  S 结构化摘要   5,045 字符  → [ 6, 6, 9] 均值  7.0
  B 认知状态     4,762 字符  → [22,21,18] 均值 20.3
  （S 与 B 由同一模型从同一材料生成，规模几乎相同）

实验② 行为测试：让接任者真的写出论文，按【交付物要求】评判
  → 三个条件【都满足全部 5 项要求】，包括考卷只拿 7/31 的 S

实验③ 取回机制：状态固定，只换取回方式
  材料进 prompt      → 合计  100,305 tokens, 5/5
  分页取回（累积）    → 合计   74,650 tokens, 5/5
  子调用取回（不累积） → 合计  337,324 tokens, 5/5
  → 子调用接口没有"选择"能力，代理只能把整本账本分块问完
```

**我从这三项读出的（可能是错的，请质疑）：**

```
· 在【同样尺寸】下，组织方式（schema）影响很大（7.0 vs 20.3）
· 但【材料的形状不改变产出】——交付物质量完全相同
· 所以"七个问题答得好"这个判据【不预测】能否把活干好
· 取回的接口形状决定对象读多少；没有"先选择"的接口会退化成"读完一切"
```

### 4.4 漂移的实测（这是我想要的性质的反面）

那个学术 campaign 跑到后期出现：

```
· 评审违反自己声明的标准
· 同一个缺陷被修改了 18 次仍未解决
· 引用编号在轮次之间漂移
· 最终报告与最初的证据链脱节
```

**我认为根因不是"上下文太长"，而是**：那个循环里"判断自己是否在正轨上"的东西，
**是模型对自己输出的判断**。而判断本身在环里自我强化。

**这是我的判断，不是测量结果。请质疑它。**

## 5. 现有机制的缺口（只陈述现状）

**我核查过代码，以下是事实：**

| 机制 | 现状 |
|---|---|
| 上下文窗口 | **worker 根本不知道它存在。** 没有任何地方声明窗口大小，也没有任何地方计算请求尺寸 |
| 超窗错误 | 被归类为 `model_rejected`（"模型拒绝了请求"）。**运维看到这个会去查请求格式，而真问题是输入需要拆分** |
| 工具循环的增长 | **按【调用次数】有界，不按【字节】有界。** 上限是 `sum(每个工具的调用上限 × 每次结果上限)`——**这个和没有人计算，也没人和窗口比较** |
| 单次工具结果 | 有 `chars` 截断，但是**逐值**的、静态的 |
| 声明的输入 | 图可以声明任意大的输入（实测有一个 writer 节点的 prompt 是 403,340 字符） |
| 累积的产物 | 在工件里，内容寻址，**不在上下文里**——这一条是好的 |
| "frontier"（账目边界） | 设计文档里有这个概念，但**是纪律，没有任何东西强制它** |

## 6. 问题的准确陈述（这是我最想要你帮我的部分）

我把它分成三个不同的尺度，因为我认为它们被"上下文管理"这个词混在一起了：

```
尺度一：单次模型调用之内
  prompt = 声明输入 + 工具循环已经积累的对话
  两者都可以无界

尺度二：一次节点执行之内 —— 和尺度一相同，因为一次执行就是一个模型循环

尺度三：图的循环（跨节点、跨迭代）
  每一次节点执行是全新的（见 §2 的机制②）
  累积在工件里
  所以这一层"看起来"已经有界了？
```

**我想问的是：**

> **1. 这三个尺度中，哪一个才是"无限时间轴"的真正问题？还是三个都是，但需要不同的处理？**
>
> **2. 尺度三真的已经有界了吗？还是我只是把无界的东西从上下文搬到了"声明的输入"里？**
>    （现在的 writer 节点 prompt 是 403K 字符，而它在一张会循环的图上）
>
> **3. 如果要"用单元测试验证单步转移"，那个"步"应该定义在哪里？**

## 7. 我认为任何方案都必须满足的约束

**以下是从 §4 的事实推出的，不是我的设计。如果你认为其中某条是错的，那比方案本身更有价值。**

```
1. 上下文必须在【调用之前】就有界，而不是在调用失败之后
   （因为超窗是硬错误，不是渐变）

2. 有界必须是【结构性】的，不是【政策性】的
   一个"到了 90% 就压缩"的规则是在两次检查之间会失效的东西

3. 不得【静默丢弃】
   危险不是遗忘，而是"遗忘了却不知道自己遗忘了"——
   一个不知道自己缺什么的 agent 会自信地继续

4. 前缀必须稳定
   改变 prompt 前缀会让整段前缀按 50 倍计价（§4.2）
   所以"每次重新组装上下文"这件事本身有价格

5. 任何派生物都不是真相
   摘要/记忆/投影出错时，必须能从真相重新导出（§2 的机制③）
```

**我明确不知道的：**

- 第 3 条（不静默丢弃）和第 1 条（调用前有界）是不是**可以同时满足**
- "有界"的界应该由**谁**决定——图？引擎？模型？
- 有界化的代价是不是一定表现为**行为退化**（而那就等于漂移，只是换了个名字）
