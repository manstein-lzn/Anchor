## 2. 背景一：Anchor 是什么（当前项目）

一个 **agent graph 运行时**。要点只有几个，其余与本次讨论无关。

**一个图 = 节点 + 边。** 节点类型包括 `agent`（调用模型的节点）、`tool`、`verifier`（判定）、
`parallel`、`join`、`loop`、`approval`、`artifact` 等。

**一次 run = 把一张【已发布且不可变】的图，在一个具体输入上执行一遍。**

**四个已经建立的机制，它们和本次讨论直接相关：**

```
① 声明式输入（I8）
   一个节点只看到它的【入边声明】给它的东西。
   没有隐式全局共享——节点不能读工作区、不能读别的节点的中间状态。

② 累积在工件里，不在上下文里
   一次节点执行 = 组装一个 prompt + 调用模型 + 结束。
   下一次执行（哪怕是同一个节点的下一次）是【全新的 prompt】。
   累积的产物（证据、代码、结论）作为不可变工件存在外部。

③ 事件日志是唯一真相
   发生过什么 = 事件序列。任何摘要、记忆、投影都是【派生物】，不是真相。
   重试不重放历史。

④ 确定性验证 + 完成门
   节点的完成可以由一个确定性验证器判定（JMESPath 表达式），而不是由模型声明。
```

**换句话说：Anchor 目前的形状是"每个节点每次全新投影"。** 这一点很重要，因为它决定了
累积发生在哪里——**累积发生在工件里，不发生在上下文里。**

## 3. 背景二：这个问题的**上一次尝试**（原始 Anchor）

**这一节必须在前一节之后立刻读，否则你会以为这个问题是从零开始的。**

有一个**同名但不同**的早期项目，逐字节归档在本仓库的 `contextengine/`（附 `PROVENANCE.md`）。
它是 `anchor-pi`：一个 Pi 扩展 + 一个纯标准库 Python 状态核心。

**规模**：约 90 KB JavaScript（`src/update.js` 40 KB 是最大的一块）+ 643 行 Python，41 个测试。

### 3.1 它的自我定位（它的原话）

> **Anchor 是 Agent Runtime 与模型 Context 之间的 authoritative cognitive state layer。**
> 明确**不是** Agent Memory，也**不是** Universal Agent Runtime。

职责分工（它的原话）：

```
Runtime  → 发生了什么（工具、transcript、窗口、压缩边界、执行）
认知层   → 当前任务什么是真的、哪些必须保持、哪些可以降注意力
LLM      → 基于当前认知选择下一步
```

### 3.2 它解决这个问题的**同一个问题**

它的连续性评审简报（`contextengine/docs/ANCHOR_CONTINUITY_REVIEW_BRIEF.md`）开篇写的是：

> *"判断 Anchor 当前的架构是否真的能够解决 Long-Horizon Agent 在多轮 context compaction、
> 进程重启和长期任务推进中的『认知漂移 / 降智 / 失忆』问题"*

**这就是本文件 §1 的问题。它是上一次尝试，不是一段引言。**

### 3.3 它**已经实现**的机制（这是它的 ROADMAP 原文，不是我推测的）

```
· serial Update at Pi's compact boundary with stale-version rejection
· SQLite reduced to Task and immutable Checkpoint truth
· anchor.cognition.v3  Situation / Experience / Intent / Knowledge Index
· stable cognition item IDs and provenance
· anchor.transition.v1  coverage and demotion validation
· exact checkpoint:<version>:item:<id> recall through immutable Checkpoints
· bounded Contract-plus-cognition Context projection
· request-local schema-constrained Bootstrap and Update submission
· exactly-one-call, closed-schema, malformed-submission, persistence-boundary tests
```

**把它对照"任何方案都必须满足的约束"（本文件 §8），会发现它逐条回应了：**

| §8 的约束 | 原始 Anchor 的机制 |
| --- | --- |
| 调用前有界 | `bounded Contract-plus-cognition Context projection` |
| 结构性而非政策性 | 不可变 Checkpoint 是真相，投影由它导出 |
| 不静默丢弃 | `anchor.transition.v1` coverage + demotion validation |
| 前缀稳定 | `serial Update at Pi's compact boundary`——不是每次调用重组 |
| 派生物不是真相 | `SQLite reduced to Task and immutable Checkpoint truth` |
| 无界部分可寻址 | `exact checkpoint:<version>:item:<id> recall` |

### 3.4 "不静默丢弃"在它那里是怎么变成可判定的

这是它的机制里最值得你审视的一处，因为它把一条模糊的要求变成了一张**证书**：

```
transition_certificate: {
  schema: "anchor.transition.v1",
  dispositions: [                    ← previous 里的【每一项】都必须出现
    { item_id, disposition: "carry",   reason, sources },
    { item_id, disposition: "revise",  reason, sources, replacement_id },
    { item_id, disposition: "archive", reason, sources },
    { item_id, disposition: "demote",  reason, sources, reference },
  ]
}

强制拒绝（来自 test/cognition-v3.test.js 的断言）：
  · 漏掉 previous 里的任何一项        → /omits|coverage/
  · 处置一个不存在的项                → /unknown previous item/
  · demote 而不给 reference           → /reference/
  · reference 指向 transcript（可变） → /immutable Checkpoint/
  · replacement_id 指向不存在的项
```

**含义：某一项"自己消失了"在结构上不可能发生——必须显式处置它，而降级必须留下可取回的引用。**

### 3.5 它**设计**了三个验证实验，只跑了第一个

| # | 实验 | 状态 |
| --- | --- | --- |
| ① | **Fresh-Agent Takeover** —— 给定 Checkpoint，fresh agent 能否选出**同样且正确**的下一步 | 跑过一个变体，见 §3.6 |
| ② | **Cognitive Drift** —— 构造易漂移任务（见下），观察 fresh agent 是否出现漂移 | **从未跑** |
| ③ | **Repeated Failure Prevention** —— "这条路以前失败过"是否还能约束未来行为 | **从未跑** |

**实验②的设计原文（注意它不需要几十小时）：**

```
人为构造容易漂移的任务：
  Goal:        implement migration
  Constraint:  backward compatibility required
  Decision:    do not modify public API
  Failure:     approach X fails because condition Y
  Correction:  user later changes one constraint
  Long irrelevant context:  many pages of noise
  Compactions: 10–20 次

然后观察 fresh Agent 是否出现：
  Goal drift / Constraint drift / Decision drift / Failure-memory drift / Directive drift
```

它还为这个实验定义了判据（`Continuation Quality`）：Goal / Constraint / Decision /
Failure / Intent / Evidence 六项连续性。

### 3.6 已经跑过的那一个：结果我说得不准

我跑了实验①的一个变体（在同一真实 run 的同一真实切点）：

```
条件（同一个全新 agent，同一套材料尺寸）：
  A 原始材料      141,033 字符
  S 结构化摘要      5,045 字符
  B 认知状态        4,762 字符     （S 与 B 由同一模型从同一材料生成）

判据一：七问考卷（目标/已确立/冲突/受阻/下一步…），盲评，每条件 3 次
  A 17.7   S 7.0   B 20.3
  → 同样尺寸下，认知状态比摘要强约 3 倍

判据二：让它真的写出论文，按交付物要求评判
  → 三个条件【都满足全部 5 项要求】
```

**我之前的说法是"认知状态没有独立行为收益"。那个说法把两件不同的事混在了一起：**

```
· 判据一支持了原始 Anchor：状态比同尺寸的摘要承载任务信息强 3 倍
· 判据二限制的是【判据】，不是【状态】：考卷答得好不预测活干得好
```

**而且实验①问的是"能否答出任务状态"，而原始 Anchor 要的是"能否选出同样的下一步"——
这两者不是同一件事。** 所以即使按字面，实验①也没有被完整执行。

### 3.7 它**没有**解决的

```
  "Update 是一个生命周期节点"是它自己的原则，但把它映射到一张图从未做过。
```

## 4. 我想要什么

### 4.1 场景

```
一张拓扑固定的图（节点与边不再改变）
在【单次 run】内连续工作 几十小时
期间累积的信息达到 几千万 token 量级
```

**"拓扑固定"是我明确设定的前提。** 我不关心"如何设计一张能自我改写的图"，
我关心的是：**给定一张固定的图，它能不能无限地跑下去。**

### 4.2 我要的性质

我称之为**认知不漂移**。让我尽量说清它不是什么意思：

```
不是：模型输出完全可复现           —— 那是确定性，我不要这个
不是：不花太多钱                   —— 成本是次要问题
不是：产出质量更高                 —— (见 §5.3，有实测证据说这不由上下文技巧决定)
是：  在任意长的运行中，agent 的决策不会因为"它已经跑了很久"而系统性偏离
```

**反面例子**（实测，见 §5.4）：一个学术调研 run，跑到后面出现了——
评审违反自己声明的标准、同一个缺陷被"修"了 18 次、引用编号漂移。
**这些不是随机波动，是系统性偏离。**

### 4.3 验证方式的要求

**我不想通过跑一个几十小时的任务来验证。**

理由：那样的验证一次只能给一个数据点，非常昂贵，而且我怀疑它根本无法区分
"设计对"与"这次运气好"。

**我想要的是**：把不漂移变成一个**可以推理、并且可以用单元测试验证的命题**——
测的是**单步转移的性质**，而结论覆盖任意步数。

**如果这不可能，那本身就是一个重要答案**，请明确告诉我。

## 5. 我已经确知的事实（全部实测，可复算）

**这些不是推测，是我亲手测出来的。你可以质疑测法，但请先认为数字是真的。**

### 5.1 硬墙的确切位置

```
上下文窗口 = 1,048,576 tokens（模型文档写的 1M）

实测：
  1,000,000 字符 →   125,032 tokens → 成功
  6,000,000 字符 →   750,032 tokens → 成功
  8,500,000 字符 → 1,095,300 tokens → HTTP 400

错误原文：
  "This model's maximum context length is 1048576 tokens.
   However, you requested 1095300 tokens
   (1062532 in the messages, 32768 in the completion)."
```

**三个值得注意的细节：**

```
· 超限是 HTTP 400，不是 5xx —— 即"这个请求无效"，不是"稍后重试"
· 补全预留【也计入】：可用输入 = 窗口 − max_tokens（这里 32768）
· 错误消息【精确且可解析】——它告诉你超了多少
```

### 5.2 缓存的经济结构（我们的 provider）

```
缓存命中    $0.003 / M tokens
缓存未命中  $0.15  / M tokens      → 比值 50
输出        $0.6   / M tokens

一次真实 campaign 的账单构成：
  输出        61.7%
  缓存未命中  36.0%
  缓存命中     2.2%
```

**含义**：已经命中缓存的部分几乎是免费的。**改变 prompt 的【前缀】会让整段前缀变成未命中，
按 50 倍计价。**

### 5.3 三项对照实验（关于"上下文该放什么"）

**实验①和②见 §3.6**（它们就是原始 Anchor 的第一个实验）。第三项：

```
实验③ 取回机制：状态固定，只换取回方式
  材料进 prompt        → 合计  100,305 tokens, 5/5
  分页取回（累积）      → 合计   74,650 tokens, 5/5
  子调用取回（不累积）   → 合计  337,324 tokens, 5/5
  → 子调用接口没有"选择"能力，代理只能把整本账本分块问完
```

**我从这三项读出的（可能是错的，请质疑）：**

```
· 在【同样尺寸】下，组织方式影响很大（7.0 vs 20.3）—— 这支持原始 Anchor
· 但【材料的形状不改变产出】——交付物质量完全相同
· 所以"七个问题答得好"这个判据【不预测】能否把活干好
· 取回的接口形状决定对象读多少；没有"先选择"的接口会退化成"读完一切"
```

### 5.4 漂移的实测（这是我想要的性质的反面）

那个学术 campaign 跑到后期出现：

```
· 评审违反自己声明的标准
· 同一个缺陷被修改了 18 次仍未解决
· 引用编号在轮次之间漂移
· 最终报告与最初的证据链脱节
```

**我认为根因不是"上下文太长"，而是**：那个循环里"判断自己是否在正轨上"的东西，
**是模型对自己输出的判断**。而判断本身在环里自我强化。

**这是我的判断，不是测量结果。请质疑它。**

## 6. 现有机制的缺口（只陈述代码现状）

| 机制 | 现状 |
| --- | --- |
| 上下文窗口 | **worker 根本不知道它存在。** 没有任何地方声明窗口大小，也没有任何地方计算请求尺寸 |
| 超窗错误 | 被归类为 `model_rejected`（"模型拒绝了请求"）。**运维看到这个会去查请求格式，而真问题是输入需要拆分** |
| 工具循环的增长 | **按【调用次数】有界，不按【字节】有界。** 上限是 `sum(每个工具的调用上限 × 每次结果上限)`——**这个和没有人计算，也没人和窗口比较** |
| 单次工具结果 | 有 `chars` 截断，但是**逐值**的、静态的 |
| 声明的输入 | 图可以声明任意大的输入（实测有一个 writer 节点的 prompt 是 403,340 字符） |
| 累积的产物 | 在工件里，内容寻址，**不在上下文里**——这一条是好的 |
| "frontier"（账目边界） | 设计文档里有这个概念，但**是纪律，没有任何东西强制它** |
| **原始 Anchor 的那套机制** | **已实现、已测试、已归档——但没有集成，也没有跑过验证实验** |

## 7. 问题的准确陈述（这是我最想要你帮我的部分）

我把它分成三个不同的尺度，因为我认为它们被"上下文管理"这个词混在一起了：

```
尺度一：单次模型调用之内
  prompt = 声明输入 + 工具循环已经积累的对话
  两者都可以无界

尺度二：一次节点执行之内 —— 和尺度一相同，因为一次执行就是一个模型循环

尺度三：图的循环（跨节点、跨迭代）
  每一次节点执行是全新的（见 §2 的机制②）
  累积在工件里
  所以这一层"看起来"已经有界了？
```

**我想问的是：**

> **1. 这三个尺度中，哪一个才是"无限时间轴"的真正问题？还是三个都是，但需要不同的处理？**
>
> **2. 尺度三真的已经有界了吗？还是我只是把无界的东西从上下文搬到了"声明的输入"里？**
>    （现在的 writer 节点 prompt 是 403K 字符，而它在一张会循环的图上）
>
> **3. 如果要"用单元测试验证单步转移"，那个"步"应该定义在哪里？**

## 8. 我认为任何方案都必须满足的约束

**以下是从 §5 的事实推出的，不是我的设计。如果你认为其中某条是错的，那比方案本身更有价值。**

```
1. 上下文必须在【调用之前】就有界，而不是在调用失败之后
   （因为超窗是硬错误，不是渐变）

2. 有界必须是【结构性】的，不是【政策性】的
   一个"到了 90% 就压缩"的规则是在两次检查之间会失效的东西

3. 不得【静默丢弃】
   危险不是遗忘，而是"遗忘了却不知道自己遗忘了"——
   一个不知道自己缺什么的 agent 会自信地继续

4. 前缀必须稳定
   改变 prompt 前缀会让整段前缀按 50 倍计价（§5.2）
   所以"每次重新组装上下文"这件事本身有价格

5. 任何派生物都不是真相
   摘要/记忆/投影出错时，必须能从真相重新导出（§2 的机制③）
```

**我明确不知道的：**

- 第 3 条（不静默丢弃）和第 1 条（调用前有界）是不是**可以同时满足**
- "有界"的界应该由**谁**决定——图？引擎？模型？
- 有界化的代价是不是一定表现为**行为退化**（而那就等于漂移，只是换了个名字）

```
② 这个问题的【结构】是什么？
   它是不是某个已知问题的一个实例？如果是，叫什么？

③ 有没有一个【可判定】的性质，它等价于"不漂移"？
   如果没有，为什么没有？

④ "用单元测试验证单步转移"这个想法，有没有可能成立？
   如果成立，"一步"是什么？如果不成立，替代的验证方式是什么？

⑤ 原始 Anchor（§3）的机制是否已经足够？
   如果不够，缺的是什么？如果够，为什么它的实验从未跑完？

⑥ 你认为我漏掉了什么？
   （特别是：我可能把一个真实约束误当成不重要的东西）
```

**最后一条方法论要求**：如果你要提出一个方案，请**同时说明它在什么条件下会失效**。
一个没有失效条件的方案，我没法用它做决策。
