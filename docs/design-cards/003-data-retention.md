# 设计卡 003：数据保留策略

> **状态：已批准（2026-10-23）——D1B / D2C / D3A / D4A，已实现。** 见文末 §8。
> 来源：M5 待决清单中的"history / points.jsonl 保留策略"（[measurement.md](../../experiments/constitution-host-preflight/final/measurement.md#迁移后待决清单)），以及用户 2026-10-23 提出的"担心数据落盘占满硬盘"。

## 1. 现状（2026-10-23 实测）

**真实运行数据很小。** 线上 `.local/rust/state` 只有 224M。实验测得的单个 Run 占用：

| 任务类型 | 每个 Run |
| --- | --- |
| 普通任务 | 1–2 MB |
| 大输入任务（contracts 一类） | 约 8 MB |

其中约一半是节点工作区，其余是产物快照、Goose 会话和内核历史。

**占空间的是编译缓存和测试现场**，约 650G，见 `.local/disk-cleanup-20261023.md`。它们不属于 Anchor 运行时，单独处理。

**现有的回收手段**都是手动或局部的：

- **手动删 Run：** `DELETE /runs/{run}`，删掉该 Run 的产物、工作区、Goose 进程目录、spill（4b36aee 补上）、渠道输入输出和记录。正在运行的、或被别的 Graph 调用引用着的 Run 不能删。
- **删 Graph：** 连带删除它已经结束的 Run 的数据。
- **启动时清理：** 只清半截写入的临时文件、依赖库里没人引用的视图，以及上一个进程遗留的插件暂存目录（4b36aee）。

**没有**任何按时间或按容量的自动回收。

**永不删除：**

- 数据中枢的事实（`kernel-facts`）和评分（`kernel-grades`），每个 Run 几十 KB；
- 删除墓碑（`run-deletions`），每个被删的对话 Run 一个小文件。

## 2. 目标

1. 长期运行时，Anchor 运行数据的总量有上界，而且这个上界可以配置。
2. 回收不得破坏正在进行的事情：运行中的 Run、等待人回答的 Run、被引用的 Run、持久助手当前的会话链。
3. RSI 的原料长期保留，因为"漏记的事实以后补不回来"（数据中枢原则）。
4. 每一次回收都可观测：删了什么、为什么删、腾出多少空间，都有记录。

## 3. 三层数据，三种策略

| 层 | 内容 | 单个 Run 的大小 | 策略 |
| --- | --- | --- | --- |
| **运行现场** | 节点工作区、产物快照、Goose 会话和进程目录、spill | 1–8 MB | 已结束的 Run 到期回收（D1、D2） |
| **运行记录** | 内核 Run 历史、Run 元数据 | 几十到几百 KB | 跟随运行现场一起删，或者单独保留更久（D3） |
| **中枢事实** | `kernel-facts`、`kernel-grades`、删除墓碑 | 几十 KB | 默认长期保留，另设总量告警（D4） |

## 4. 需要你拍的决定

- **D1｜回收的触发方式**
  - A 只在 Host 启动时回收：简单，但长期不重启的服务永远不会回收。
  - **B（建议）启动时回收一次，之后每小时一次，由 serve 进程内的一个周期任务执行**：复用现有删 Run 的代码路径，不引入新的删除逻辑。
  - C 只提供手动的批量清理接口（例如 `POST /runs/prune`），由运维定时调用。

- **D2｜按什么判断"该回收"**
  - A 按时间：已结束超过 N 天（建议默认 30 天）。
  - B 按容量：运行数据总量超过上限（建议默认 20G）时，从最旧的已结束 Run 删起。
  - **C（建议）两个都用**：超过时间或者超过容量，任一满足就回收。默认值都可以通过环境变量配置，也可以关掉。

- **D3｜运行记录是否比运行现场保留更久**
  - **A（建议）不区分，一起删**：沿用现在删 Run 的语义，删除路径只有一条。
  - B 先删现场，记录多留一段时间：能多看一阵 Run 列表，代价是多出一种"只剩记录"的 Run 状态，要求每个读取方都能处理它。

- **D4｜中枢事实**
  - **A（建议）永久保留，`profile` 报告里显示总量，超过阈值（默认 5G）时报警**。按每个 Run 50 KB 估算，5G 约等于 10 万个 Run。
  - B 跟随 Run 一起删：最省空间，但 RSI 会丢掉历史数据。

## 5. 不变量

- **I1：** 运行中、等待人回答、等待恢复、被别的 Run 或 Graph 调用引用的 Run 不回收。只回收 `Settled` 状态的 Run。
- **I2：** 持久助手当前会话链上的 Run 不回收，复用现有删除的会话链检查和墓碑机制。
- **I3：** 回收和手动 `DELETE /runs/{run}` 走同一条删除路径，不另写一套删除逻辑。
- **I4：** 每轮回收写一行汇总：删了几个 Run、腾出多少字节、跳过几个以及原因。
- **I5：** 回收失败不影响服务。失败的 Run 下轮重试，并计入跳过数。

## 6. 验收测试清单

| 编号 | 用例 | 断言 |
| --- | --- | --- |
| T1 | 一个已结束且超期的 Run，一个未超期的 Run | 只删超期的那个 |
| T2 | 总量超过上限 | 从最旧的已结束 Run 删起，直到降到上限以下 |
| T3 | 运行中、等待人回答、被引用的 Run，即使已超期 | 都不删（I1） |
| T4 | 持久助手会话链中间的 Run | 不删，或按现有墓碑规则安全删除（I2） |
| T5 | 回收后 | `kernel-facts` 和 `kernel-grades` 原样保留（D4=A） |
| T6 | 某个 Run 删除失败 | 服务继续运行，下一轮重试，汇总里计入跳过（I5） |
| T7 | 设为关闭 | 不发生任何删除 |

## 7. 明确不做

- 不碰编译缓存和测试现场，它们不是运行时数据，按清单人工处理。
- 不修改内核和 `FileStore` 的格式，也不做归档或压缩。
- 不新增 WebUI 页面。回收结果先写在服务日志里，并通过已有的 Run 列表接口体现。

## 8. 批准与实现（2026-10-23）

用户同意四项建议：D1B、D2C、D3A、D4A。

**实现**

| 部分 | 位置 | 内容 |
| --- | --- | --- |
| 策略与挑选 | `anchor-runner-host/src/retention.rs` | 计算该删哪些 Run |
| 执行回收 | `application/deletion.rs` 的 `RunApplication::reclaim` | 对每个候选 Run 调用现有的 `delete_run`，被拒的计入跳过（I3、I5） |
| 定时任务 | `api/schedules.rs` 的 `start_retention` | serve 启动时执行一次，之后每小时一次 |

**配置**（策略在启动时读取，取值不合法时 Host 拒绝启动）

| 环境变量 | 默认 | 含义 |
| --- | --- | --- |
| `ANCHOR_RETENTION_DAYS` | 30 | 已结束 Run 与未受保护的交付版本超过这么多天回收 |
| `ANCHOR_RETENTION_MAX_GB` | 20 | 唯一 Artifact 对象及 Run 自有现场总量上限，先回收旧交付，再回收已结束 Run |

两个变量设为 `0` 或 `off`，就关闭对应的限制；两个都关闭则完全不回收（T7）。

**口径**

- **结算时间**取 Run 最后一次状态变化的观察时间，Host 在每次状态变化时都会写这个时间。没有观察时间的已结束 Run，只能按容量回收，并且被当作最旧的。
- **候选范围**：Run 只限 `Settled` 且没有 worker；Artifact 独立按版本回收，活跃 Run 的旧交付也可过期。当前节点结果、执行/恢复实际可见输入、发布候选及显式保留版本受保护，历史谱系 metadata 不自动保留全部字节。
- **大小**：Artifact 按实际唯一 inode 计量，包括可重建视图，不能累加每份清单的逻辑字节。Run 仅统计自身默认 Workspace 和 spill；显式共享 Workspace 独立释放，不因来源 Run 删除而清除。保护内容超过额度时报告不可回收，不清理活跃现场。
- **日志**：回收 Run、过期交付、跳过或容量超限时写汇总；中枢事实超过 5G 报警线仍只报告。交付保留和释放经 Kernel 记录；回收先发布过期墓碑，删除最后未受保护引用后才清内容对象。预览、下载和沙箱输入按交付版本持使用租约，回收跳过正在使用的版本。

**与卡片的偏离**

D4A 原文写"在 `profile` 报告里显示总量"，实际实现是写进 Host 回收汇总的那一行日志：超过 5G 时报警，事实本身照旧保留。这样数据中枢不用读 Host 的状态目录，也就不用越过它的依赖边界。如果需要，以后可以在 hub 的 `profile` 里另加一项。

**测试**

- 回收逻辑：`retention::tests`。
- 验收用例 T1–T7：`application::deletion::retention_tests`，用真实的 Run 覆盖每一种状态：
  - T1、T2、T3、T5、T7 各有直接断言。
  - T4、T6 只验证了"删除路径拒绝的 Run 会被跳过、注明原因，回收继续进行"，用的是被父 Run 的 Graph 调用引用的子 Run。会话链上的拒绝没有单独测，它由同一条删除路径和既有的会话删除测试保证。
- 历史 Run 回收基线：workspace 2174 通过、0 失败；选择性交付重构后的验证以当前验收台账为准。

**历史部署观察**：当时按本机线上状态的观察时间和总量核对过。现有 6 个 Run 最早的变化是 10 月 20 日，都在 30 天以内；状态目录总共 224M，远低于 20G。所以第一轮回收不会删除任何 Run。
