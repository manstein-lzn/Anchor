# 第一部分 · 问题

## 1.1 我们要解决什么

一个 agent graph 在长时间工作中会同时坏掉四件事：

| 失效 | 表现 |
|---|---|
| **上下文爆炸** | 每轮 prompt 越来越大 |
| **注意力被稀释** | 关键信息淹没在材料里 |
| **被现象带偏** | agent 被最近的、最显眼的信号俘获，丢掉目标 |
| **认知漂移** | 反复压缩之后，agent 对任务的认知逐步偏离实际 |

目标不是"记住更多"，而是：

> **让 agent 随时间变得老道，而不是进步的失忆者。**

## 1.2 实测证据（本文一切结论的地基）

以下数字来自一次真实运行（academic-research 图，run `f4eb8ac7`）。

### 证据一：修订轮的 prompt 有 60% 是字面重复

```
write 节点首稿 attempt=0    141,033 字符    重复 0
write 节点修订 attempt=1    403,340 字符    重复 243,766 = 60%
```

重复的具体内容：

```
feedback.evidence 与 evidence              逐字节相同（137,094 字符出现两次）
feedback.verified_sources (106,672 字符) 与
  evidence.sources (13,249 字符)         同一批 59 篇来源的两种表示
```

而 `instructions`（真正的行为策略）**只占 prompt 的 1.0%**。

> **"上下文快满了"不是任务复杂度造成的，是我们自己的反馈设计造成的。**
> 修订轮把 prompt 推到 2.9 倍，其中六成是同一批事实换位置再说一遍。

### 证据二：缓存命中 99.9%

```
gross input 173,519 tokens | cached 173,312 | 命中率 99.9%
```

因为我们**每轮原封不动重发**。

> 今天我们已经站在缓存友好的极端上，代价是 60% 冗余加零选择。

### 证据三：模型是不确定的

```
同一个 write 节点，同一份冻结输入，什么都没改，两次运行：
  输出 14,544 字符
  输出 14,573 字符
```

### 证据四：观测是可行的

```
节点测试台重跑一次 write 节点   40 秒   （原 campaign 31 分钟）→ 46 倍
```

### 证据五：契约错误比代码错误更致命

最初那版学术图产出的不是论文，是**一份审计台账**：

```
正文里 57% 的段落带审计语言
116 个证据级标签
35.5% 的篇幅是文献器械
```

**系统精确执行了当时写的契约。契约错了，代码没错。**

### 证据六：评审会违反自己的标准

评审的指令写着 "pass requires no unresolved major issues"，而它在三轮里报出 **0 个 major**，仍给 `revise`（6、6、4 条 minor）。

> 细心的评审总能找到 minor，所以循环永远不结束。

## 1.3 为什么通行答案不成立

社区（含 OpenAI / NVIDIA / Google / 社区扩展）的通行做法是：

```
上下文快满 → 调用模型生成一段历史总结 → 拼接为
系统提示 + 工具提示 + 总结 + 最近几轮
```

**它从根上错在四条：**

1. **时机错** —— 等到满了，你已经为完整上下文每轮付过钱了
2. **信息错** —— 压缩那一刻你不知道后面什么重要；"什么重要"只在**使用时**才知道
3. **不可测** —— 摘要是一段散文，你无法判断"给了它 X 是否改变了结果"
4. **不可审计** —— 压缩由模型完成，是一次没有记录的决策

### 调研到的四种方案（2026-09 一手来源）

| 方案 | 做法 | 关键局限 |
|---|---|---|
| **OpenAI** `OpenAIResponsesCompactionSession` | 把 compaction 搬进服务端 API (`responses.compact`)；整段历史**清除重写** | 不透明、不可检查；官方承认会阻塞流式、恢复失败时历史可能保持未恢复 |
| **NVIDIA** `NVlabs/SoL-Pi` | 四个机制：Action Fusion / **ObservationPack**（重复大结果→稳定句柄+分页召回）/ Evidence-Preserving Reducer（保留引用须匹配归档原文）/ **Online Context Compact**（按计划步骤边界触发，用 `cacheWriteReadRatio`=12.5 做经济决策） | 效率机制，不改变"历史是管理对象"的前提；依赖 Pi 宿主 |
| **社区** `pi-smart-compact` | **EESV 管线**：Extract(0 次 LLM) → Explore → Synthesize → Verify；**验证失败则拒绝**；确定性质量地板；Continuity Ledger；FTS5 上下文图 | 唯一对摘要做验证的方案；但仍是会话级压缩 |
| **Google ADK** | `EventsCompactionConfig`：token 阈值（"absolute safety net"）+ 滑动窗口；`session.state` 作为与 events 分离的可序列化草稿板 | 阈值 + 结构化草稿板，未涉及认知 |

**四者的共同点：都在解决"对话历史累积"。**
**没有一者在解决"这一步需要什么"。**

# 第二部分 · 思想

## 2.1 重新定义：状态是充分统计量

来自原始 Anchor（见附录 A）：

```
minimize size(Project(S))

subject to:
  一个全新 Agent，只看 Project(S) + 近期窗口，
  仍能选对下一步，而无需从完整历史重建任务
```

> **State 是任务特定的充分统计量。**

并给出一条**可证伪的预测**：

> 在任务复杂度稳定时，投影出的上下文应趋近稳定大小，
> 即使 transcript 长度与 Checkpoint 数量持续增长。

这一句回答了"如何保持上下文最优"：**不是逐时刻最优（无法定义），而是维持一个充分统计量并确定性投影。**

## 2.2 遗忘是注意力分配

> **遗忘不是存储失败，也不是物理删除。它是把信息刻意移出当前注意力。**

每个 item 只问一个反事实问题：

> **如果下一个 Agent 看不到它，会不会做错决定、违反约束、
> 重复失败或昂贵的工作、或丢掉必要的下一步？**

答案决定**认知层级**（明确说：不是存储层级）：

| 层级 | 处理 |
|---|---|
| **Active Cognition** | 影响当前决策与行动 → 始终投影 |
| **Dormant Knowledge** | 现在不可行动，但丢失会让未来恢复昂贵/不安全 → **一个简洁精确的恢复引用** |
| **Event Archive** | 不再预期影响正常工作 → 仅供显式恢复/审计/调试 |

而召回是 `explicit / targeted / bounded / recoverable`，且：

> **恢复的材料不会仅因为读过一次就永久进入投影。**

**这就是"知识积累而不膨胀上下文"的答案：休眠知识是引用，不是文本。**

## 2.3 认知是因果模型，不是编年史

按**认知义务**分节（不是按话题）：

```
Situation   当前理解 / 已确认事实 / 活跃假设 / 未解冲突 / blockers
Experience  仍然约束选择的决策 / 失败路径+原因+重试条件 /
            仍然改变未来策略的教训
Intent      当前指令 / 已接受的下一步 / 下一计划 / 开放问题
Knowledge Index  当前相关的休眠引用
```

核心公式：

```
Contract goal − Situation = current gap
current gap + Contract constraints + relevant Experience = Intent
```

而最能说明问题的是那个对比例子：

```
✗  "命令 X 跑了并失败。"                      ← 事件，天然受近因支配
✓  "路径 X 失败，因为条件 Y 不存在；           ← 条件式，对近因免疫
    在有证据 Z 之前不要重试。"
```

**前者是日志，后者是认知。**

> **这解释了状态为什么能治"被现象带偏"：不靠更好地摘要，靠换一种表达形式。**

## 2.4 投影：主要靠排除法定义

```
固定 prefix（system / developer / tool）
+ 不可变的 Task Contract 核心
+ 最新 Active Cognition
+ 紧凑的 Knowledge Index
+ 宿主的 active window（原样不动）
```

**明确排除：**

```
持久化对象 / receipt / Transition Certificate
指令散文史 / 已解决问题的细节
完整 artifact 内容 / 大工具输出
重复的事实              ← 我们 60% 的 bug
旧 Checkpoint 或摘要链   ← 压掉"摘要的摘要"漂移
```

> **投影是确定性本地工作：不调用 LLM、不扫完整 transcript、不重放每个 Checkpoint、不设私有 token 预算。**

## 2.5 frontier —— 抗漂移的形式化

```
Checkpoint = State revision + source frontier
```

> **没有 source frontier 的 Checkpoint，不允许取代 transcript 中的任何内容。**

由此职责干净划分：**frontier 之前由 Checkpoint 承担，之后由 active window 承担。**

## 2.6 分权：代码验证什么，模型判断什么

`Transition Certificate`：每个曾 active 的 item 恰好获得一种处置。

```
carry      保持激活，身份与含义不变
revise     保持激活，但被指名的新证据修正
resolve    因问题已有结果而离开激活集
supersede  因更新的指令或事实而离开
demote     离开详细注意力，但保持精确可恢复
archive    不再具有预期未来行为价值
```

配套的确定性校验能保证：

```
没有旧 item 静默消失 / carried 仍存在 / revised 有后继
新权威事实引用允许的不可变来源 / 用户更正显式 supersede 旧指令
失败没有被转写成成功完成的证据 / demoted 有内容绑定的恢复路径
Task / Contract / parent / frontier / provenance 仍然有效
```

而这里有一句是全篇最关键的取舍：

> **证书让遗忘可问责，而不假装代码能判断所有自然语言的真假。**
> **模型仍决定语义相关性。校验器建立的是覆盖面与证据纪律，不是普遍语义正确性。**

**这解决了"什么算好无法写成谓词"的困境：不去验证质量，去验证"没有任何东西静默消失"和"证据纪律成立"。后者是可判定的。**

## 2.7 PyTorch 类比：把记忆问题换成优化问题

```
PyTorch                     Agent Graph
────────────────────────────────────────────────
计算图（固定拓扑）      →    graph（不可变版本）
输入 tensor             →    run 的输入数据
前向传播                →    一次 run
权重                    →    capability 参数：prompt / 工具矩阵 /
                            上下文策略 / 边契约
loss                   →    输出质量
反向传播 + optimizer    →    观察者 + 归因（见第三部分）
```

它给出的最重要一句话：

> **老道 = 参数变好了。失忆 = 参数没变。**
> **记忆不是老道的载体，记忆是 optimizer state —— "哪次改动带来了哪个结果"的证据。**

**这解释了为什么社区的记忆系统给不出 RSI：它们存的是激活，不是优化器状态。**

### loss 有三层

```
L_deterministic   快、免费、精确      ← 结构/引用可验证/行文规则（已有）
L_judged          中速、有噪声        ← 评审（已有）
L_outcome         慢、稀疏、真实      ← 人用不用、代码在生产过不过
```

**而且有一个神经网络没有的优势：`L_deterministic` 是 per-node 的。**

```
结构/行文规则 → 打到 write
引用可验证性  → 打到 gather
一致性        → 打到 review
```

**所以信用分配不必只在 episode 末尾做。** 图里节点是离散的、命名的、数据流有迹的——这比在 10⁹ 个匿名权重上做信用分配容易得多。

### 类比在哪里断裂（五条）

1. **没有梯度** —— 只能说"离散组合搜索"。但**"梯度"可以由模型提供**：模型能说"这次失败是因为证据不足还是指令不清"，那是一个启发式提议分布。比 autograd 弱，但远不是零。
2. **variance 致命** —— 实测同输入两次输出不同（14,544 vs 14,573）。**如果评估本身有噪声，你会把噪声当信号。**
3. **参数不独立** —— 改 writer 的 prompt，reviewer 看到的东西就变了。这是个耦合系统。
4. **拓扑可能本身是错的，而调权重修不好** —— 我们亲身撞过：最初的学术图让 `research` 一个节点包办搜索+读+分析+写。那需要**拓扑改动**，不是参数调整。
   → 由此得出的纪律：**拓扑改动 = 架构搜索，稀少但有时必须；平时应抵抗拓扑 churn，优先调参数。这是我们之前缺的纪律。**
5. **最根本：PyTorch 的 loss 是给定的，这里"定义 loss"本身就是全部研究工作。**

### 关于噪声的必要澄清

"噪声"只对**边际改进**成立：

```
边际改进：质量分 8.0 → 8.2        → 需要统计，可能不值得
明显缺陷：要论文却交出审计台账      → 一次就能看见，不需要重复
```

所以本文后续讨论的是**明显缺陷**，不是 5% 的微优化。

（另需更正一处早期表述：我说过"确定性 loss 的方差是零"，**不准确**。检查本身是确定函数，但通过与否取决于模型这次写的东西，仍会变化。）

# 第三部分 · 综合到 Agent Graph

## 3.1 为什么它更适合图（用户的判断，我认为成立）

原始 Anchor 有一大块机制在**人为制造确定性**：

```
Plan before authority（"首次 prompt 是意图的证据，不是完整任务状态"）
Grill 式 Planning → sealed proposal → 用户确认
首次 compact 时 bootstrap 一个 provisional Task
read-only 直到提案被接受
```

**这整套东西存在的原因是：聊天场景下"任务是什么"不可先验得知。**

而图场景下，这个谈判**已经在写图时完成了**：

| 原始 Anchor 要谈判出来的 | 图里天然有 |
|---|---|
| goal / acceptance criteria / constraints | 运行输入 + 图契约 |
| execution plan | **就是拓扑本身** |
| verification | 节点/边校验约定 |
| risks | 边上的失败路由 |

> **图省掉的不是"状态"，而是"状态的不确定性来源"。**

## 3.2 但确定性住在哪一层（关键补充）

```
图拓扑        → 确定（会发生哪几类事）
边契约        → 确定（必须交接什么）
───────────── 以上是图给你的，聊天给不了 ─────────────
节点内部      → 不确定（工具循环里模型自己决定）
循环迭代次数  → 不确定
```

**漂移问题恰恰住在下半层。**

> 直线 DAG 几乎不需要状态——它天然无漂移。
> **真正会漂移的是循环**：`coverage → gather → coverage → ... → write → review → write`
>
> **循环是图版的"对话开得太久"。**

所以 `Checkpoint` / `frontier` 这套东西，**该放在循环边界上**。

## 3.3 原始 Anchor 留下的缺口：工作集

这是本次讨论压榨出的**最重要的认知**。

原始 Anchor 的投影公式里，工作集住在 **host 的 active window** 里，由 Pi 的压缩边界负责有界。**它自己不管工作集。**

```
Projection = 固定 prefix + Cognition + 【Pi compaction-aware active window】
                                          ↑ 工作集住这里，由宿主负责
```

**而我们的图没有那个宿主。** 节点的声明输入可以任意大，且没人管。

> **结论：原始 Anchor 的模型不会修好我们的 bug。**
> 我们的 60% 重复是**工作集问题**，不是认知问题。

**必须分清：**

| | 成因 | 随任务时长增长？ | 状态能解决吗 |
|---|---|---|---|
| **历史爆炸** | transcript 累积 | ✅ 线性 | ✅ 能（按构造） |
| **工作集爆炸** | 任务当前的活跃材料本身很大 | ❌ 由任务性质决定 | ❌ **不能** |

**我们之前会犯错，是因为只有一个层，于是把工作集同时当成了认知、当成了历史，还重复了三遍。**

## 3.4 三个时间视野，与两类跨 run 状态

| | 当前 run | 历史 run | 未来 run |
|---|---|---|---|
| 生命周期 | 这个 run | 永久（可寻址） | —— |
| **真值来自** | **本次运行的证据** | **跨运行的证据** | —— |
| 失效方式 | run 内漂移 | **陈旧 / 过度泛化** | 投影错东西 |
| 规模 | 有界（充分统计量） | 无界（归档） | 小（必须小） |

**关键差别在"真值标准"那一行。**

原始 Anchor 的真值标准是本次运行的证据（`sources: ["episode:4:tool-result:2"]`）。而跨 run 面对一个它从未面对的问题：

> **一条在 run A 中学到的经验，凭什么在 run B 中成立？** run B 的课题、代码库、约束都可能不同。

**而跨 run 状态其实是两种相反的东西：**

| | **内容**（substantive） | **经验**（procedural） |
|---|---|---|
| 例子 | 59 篇来源、24 组对立、一篇论文 | "arXiv 限速 3s"、"评审只报 minor 就该批准"、"按产出物切节点而非按阶段" |
| 真值来自 | **provenance** | **outcome** |
| 规模 | 大 | **小** |
| 跨课题泛化 | ❌ 不该泛化 | ✅ 应该泛化 |
| 增长率 | 线性 | 趋于饱和 |
| 失忆代价 | 重复劳动、重复付费 | **永远不进步** |

**"老道"只来自右边那一列。**

## 3.5 统一接口：注意力层级

上面两个维度（时间视野 × 注意层级）**共用同一个判定**：

```
                  小 & 总是相关          大 & 按需
当前 run      →   本次认知              本次材料
跨 run        →   积累的经验            积累的内容
                  （自动投影）           （精确寻址）
```

> **每个 state 项声明它的注意力层级；层级决定它进入上下文的方式。**
> **时间视野不是另一套机制，只是层级判定的另一个输入。**

这条路线的好处：

- **经验小 → 能自动投影 → 默认行为被改变 → 这才是"老道"**
- **内容大 → 必须寻址 → 不爆炸**

### "老道"的真正要求

> **老道 = 默认行为被改变了，而不是记忆可以被检索到。**

如果跨 run 状态只是**能被查到**，那这个 agent 不是老道，只是**多了一个图书馆**。

要真的老道，经验必须：

```
① 自动进入投影（不需要 agent 主动去查）→ 所以必须小
② 可被 outcome 验证（否则就是累积偏见）→ 所以必须带归因
③ 可被推翻（否则错误经验永久污染）    → 所以必须有退役机制
```

## 3.6 归因：缺失的那一环

原始 Anchor 在跨 run 上是**空的**：

1. **没有任何跨 session 机制** —— one session one Task；README 明确 "a fork has a new Pi session identity... never inherits writable State"
2. **明确拒绝向量检索** —— "Anchor does not require vector search. Exact references and bounded textual lookup are sufficient until real recall failures prove otherwise."

**这个立场在 run 内是对的**（你知道要什么，所以能精确寻址）。
**但在跨 run 上是错的**——新 run 开始前，**你不知道自己需要哪条旧经验**。

而 RSI 真正缺的是：

```
State → Decision → Action → Observation → Milestone → Outcome → **Attribution**
                                                                 ↑ 这一环是空的
```

> **没有归因，跨 run 状态就只是"累积起来的观点"，不是"被验证过的经验"。**

## 3.7 run 内 vs run 后：重做 vs 改版

一个必须澄清的区分（本文作者早期曾把两者混为一谈）：

```
改「图」  → 塌方   （一个 run 必须只有一个计划版本；否则"这个 run 跑的是哪版"无解）
改「状态」→ 本该如此（这就是 Update 存在的原因）
```

**run 内到底什么能改：**

| run 内能做的 | 现有机制 | 需要改图吗 |
|---|---|---|
| 更新认知（state） | Update / checkpoint | ❌ |
| 路由回上游（证据不够 → 回 gather） | 循环 + 条件边 | ❌ |
| 重做节点（输出不合格 → 带反馈重做） | `output_retries` + `rejected_refs` | ❌ |
| 节点内换工具/策略 | 模型的工具循环 | ❌ |
| 停下找人 | `needs_input` | ❌ |
| 改节点参数（prompt/策略） | —— | ✅ = 改版 |
| 加/删节点 | —— | ✅ = 改版 |

> **run 内的杠杆是「重做」（带诊断重做）；run 后的杠杆是「改版」（改参数/拓扑，产生新版本）。**

**验证**：本次会话中所有修复（拆 gather/write、引用编号、坏引用路由、收敛判据、评审批准规则）**全部发生在 run 之间**，没有一次在 run 内改图。

**run 内的杠杆在 state 上**——这正好接上"state 才是内核"：

```
图 提供「决策点」   —— 条件、重试、循环（拓扑，固定）
state 提供「流过的内容」 —— 认知（每次都在变）
```

run 内的三种情形：

```
输出不对  → 带诊断重做这个节点
输入不够  → 路由回上游
路子不对  → 只能停下找人（因为"改路子"就是改图）
```

**第三行是关键**：run 内可以**察觉**路子不对，但**修不了**——只能记录并停下。而这条记录正是 run 后优化的输入。

## 3.8 观察者：同一条 Update 协议，三个尺度

```
previous state + Episode → semantic proposal → 校验 → durable commit
```

| 尺度 | Episode | proposal 的内容 | 提交到 |
|---|---|---|---|
| **节点级** | 一个节点的工具循环 | 该节点产出 | run 认知 |
| **run 级** | 一次完整 run | 本次认知 + 归因 | 认知 + **优化器状态** |
| **多 run 级** | N 次 run 的归因记录 | **参数变更提案** | **新 capability 版本** |

**三个时间视野不是三套机制，是同一条 Update 协议作用在三个尺度上。**

### 观察者必须做与绝不能做

| 观察者的活 | 该由谁做 |
|---|---|
| 读 trace，判断失败原因 | **LLM** |
| 提出 prompt/策略改动 | **LLM** |
| 提出"这个节点该拆" | **LLM（作为提议）** |
| 计算结构检查是否通过 | **代码** |
| **判断某改动是否真的更好** | **代码 + 测试台** |
| 决定采用哪个版本 | **人 或 明确阈值** |
| 记录归因 | **代码**（LLM 只提供内容） |

> **观察者提议；测试台裁决。**
> **观察者可以改「怎么做事」，不可以改「怎么算合格」。**
> 前者是参数（prompt、策略、边契约），后者是门槛（检查、验收）。**改门槛的提案必须走人。**

### 自省需要一个对立面

> **问 agent"你干得怎么样"，它会告诉你它干得很好。**

所以自省的内容应该是**差异**，不是概述：

```
✗  "总结一下这次工作"
✓  "确定性检查发现 A 项不通过、评审报了 B 条；
     解释你的产出为什么与它们之间有差异"
```

而且**观察者最好是"没干过这活的人"**——干活的 agent 对自己的假设是盲的。

这正是原始 Anchor 评审简报里的 **Fresh-Agent Takeover**：

> 一个全新 Agent，只看 Contract、投影出的认知、索引和近期窗口，
> 能否继续而不必猜关键决定、也不必从完整历史重建任务？

### 结构性护栏（协议级硬约束）

```
1. 观察者不提交，只提议
2. 图在 run 期间不可变；提议产生新版本
3. 确定性层是地板，不是 LLM —— 零差距的确定性兜底优先于不可验证的模型输出
4. 改动幅度必须超过实测噪声
5. 留出集：不在被调优的输入上验证
6. 每轮改动有界，否则不可归因
7. 拒绝而不降级：宁可拒绝提案，不静默接受
```

# 第四部分 · 架构

## 4.1 分层

```
第 4 层  优化（观察者 · 归因 · 参数改版）      ← 未解问题住这
第 3 层  跨 run 状态（经验 · 内容 · 索引）      ← 未解问题住这
第 2 层  认知（Contract · State · 投影 · frontier） ← 设计已存在
第 1 层  执行 + 观测（已有，实测过）
```

## 4.2 边界：状态框架只做四件事

> **认知 · 注意力 · 归因 · 投影**

**执行、工具、沙箱、工作区、多智能体编排留在下面，不往上长。**

这条边界的依据来自原始 Anchor 自己的 DON'T 清单：

```
vector memory · knowledge graph · scheduler · agent pool
multi-agent governance · reviewer authority · workspace sandbox
automatic per-turn projection LLM · asynchronous Update
parallel state writers · private token budgets
```

以及它写的两句：

> **"Keep the Extension thin."**
> **"现在不要因为 RSI 很有趣而提前扩大核心 runtime。"**

**注意 `workspace sandbox` 在那份清单上，而当前 Anchor 造了其中大部分。**
这不是说那些东西没价值，而是说**它们不是核心**。

## 4.3 已有 / 缺失

### 已有

**执行底座**：图 IR / 不可变版本 / bundle · 租约/attempt/claim/恢复 · 控制·agent·验证·循环·条件·join · 声明式输入(I8) · 血缘(recovery closure) · 人工等待/审批门 · 收敛判据/机械重复守卫

**观测仪器**：模型调用录制 · 精确回放（按位置、分歧定位失败） · 节点测试台（40 秒） · 按节点用量 · 进度/诊断事件 · 日志

**判断层**：交付物确定性检查 · 评审门 + target 路由 · 批准规则（只报 minor → 接受） · 代码质量门 + 棘轮

**思想模型**：原始 Anchor 的完整文档（见附录 A）

### 缺失 —— 必须分成两类

**A 类：没造（照已有设计做即可）**

```
1. Contract 对象 —— 认知的锚；没有它算不出 "gap"
   现在散在 run 输入 + 节点指令里
2. State 作为一等对象 —— Situation/Experience/Intent/Index + 版本 + frontier + 证书
   现在只有 input_snapshot / context_snapshots，没有"认知"
3. 边作为「需求」的载体 —— 现在传的是"上游产出了什么"，
   需要的是"下游声明需要什么"
4. 投影层 —— 按公式确定性读取；现在没有，这就是 60% 重复的成因
```

**B 类：没解（研究问题，不是工程量）**

```
5. 工作集该住哪 —— 原始 Anchor 委派给宿主，图没有宿主。这是 bug 的成因，而它是空的
6. 归因 —— 一次 run 的缺陷 → 具体节点的具体参数。
   图让它可做（节点命名、数据流有迹、per-node 确定性 loss），但没人证明过它成立
7. 跨 run 经验凭什么被相信 —— RSI 的核心问题
   四项外部方案没有答案，原始 Anchor 从设计上就不跨 session
```

## 4.4 原始 Anchor 的表达力上限（诚实清单）

它能表达**任务级认知**，且相当完整。**不能**表达的有：

```
1. 没有关系 —— "No generic relation system or vector representation is part of the core"
   → "fact-17 依赖 decision-3 成立"说不出来
   → supersede 只是证书里的一次性处置，不是可查询的关系
2. 没有工作集 —— 大材料只能被引用，不能在工作集里被操作
   → 对散文任务够用；对"要转换一份 59 项证据表"不够
3. "因果模型"是散文里的说法，不是数据结构
   → 是"该怎么写陈述"的期望，不是可检查的性质
4. 置信度是二值的 —— confirmed fact vs active hypothesis
   → 长期任务里大量东西是部分已知的，二值太粗
5. 没有作用域 —— 一个 session 一份状态，全局
   → 图需要知道"这条事实属于哪个节点/子任务"
```

**它表达的是"任务层面的认知"，不是"多主体共享的工作内存"。**

## 4.5 四个问题：状态到底能解决多少

| 问题 | 状态能否解决 |
|---|---|
| **上下文爆炸** | **半解决** —— 治历史，不治工作集 |
| **注意力被稀释** | **半解决** —— 治量与重复；引入"压缩导致的过度自信"这一新失效模式 |
| **被现象带偏** | **能，最强的一环** —— 靠换表达形式（因果式而非编年式），而非更好的摘要。但该性质**只由 schema/提示词保证，代码不检查** |
| **认知漂移** | **消除"静默丢失"类，不消除"判断偏移"类** —— 漂移从无声变可审计；检测仍需外部实验 |

## 4.6 未解的问题（诚实摆出）

```
① 工作集该住哪        —— 知道故障形状（60% 重复），知道方向（边契约 +
                         休眠引用 + 内容寻址），但没有已验证的设计
② 归因如何成立        —— 推理上可做，但不是证据
③ 跨 run 经验凭什么被相信 —— 我完全不知道答案。
                         "老道 vs 失忆"最终落在这一个问题上
④ loss 如何定义        —— "什么算好"无法完全写成谓词，是本领域的开放问题
```

## 4.7 建议的推进顺序

> **先把第 2 层做出来——因为它两边都靠它，而且它的设计已经存在。**
> **同时为第 3、4 层留出命名清晰的接口，然后把它们明确挂起。**

理由：

**第 2 层做完，立刻能解决已经实测到的问题**（60% 重复、工作集没有归宿、压缩期的漂移）。
**而第 3、4 层是研究问题——它们不该挡住已经知道怎么修的部分。**

在写任何设计之前需要确定的一件事：

> **`Contract` 在图里由什么承载？**
> 运行输入的一部分？图级 metadata？一个显式的新对象？还是由拓扑+节点契约推导？

这个决定往下会影响所有东西。

# 附录 A · 原始 Anchor

本白皮书的思想模型主要来自一个**同名但不同的早期项目**，已归档在仓库的 `contextengine/`（逐字节保真，附 `PROVENANCE.md`）。

它是 `anchor-pi`：一个 Pi 扩展 + 纯标准库 Python 状态核心，主题是"为长时间运行的 Pi 会话提供持久的规划与认知更新"。

**恢复方式**：当前仓库覆盖了同名仓库，旧历史变为不可达。通过 GitHub 公开事件流（记录每次 push 的 `before`/`head` SHA）定位到 `feefcf64940e`（2026-09-04），tarball 取回。

**关键文档**：
- `docs/PRINCIPLES.md` —— 八段，最快的入口
- `docs/PRODUCT_SPEC.md` —— 四个核心对象（Task / Checkpoint / Episode / Projection）
- `docs/ARCHITECTURE.md` —— 充分统计量、注意力层级、证书、投影
- `docs/ANCHOR_UPDATE_PROTOCOL_V2.md` —— 语义操作 + 确定性物化 + 证书 + 事务边界
- `docs/ANCHOR_CONTINUITY_REVIEW_BRIEF.md` —— 风险清单与六个验证实验

**它的八条原则：**

```
1. Plan before authority —— 首次 prompt 是意图的证据，不是完整的任务状态
2. One session, one Anchor
3. State is authority —— 确认的 Task + 不可变认知 Checkpoint 存在一个 SQLite 权威里
4. **Context is a projection** —— Anchor 不在普通模型调用时重新摘要或裁剪窗口
5. **Update is a lifecycle node** —— 压缩触发一个无工具的专用认知任务；
   其输出经校验和版本化提交后才成为状态
6. **Mechanical truth stays mechanical** —— git/哈希/检查决定，不靠 agent 散文
7. **Failure is non-destructive** —— 被拒绝的更新保留先前状态与活动窗口
8. **Keep the Extension thin**
```

**它定义的定位（第四节的判断）：**

> **Anchor 是 Agent Runtime 与模型 Context 之间的 authoritative cognitive state layer.**
> 明确**不是** Agent Memory，也**不是** Universal Agent Runtime。

```
Runtime  → 发生了什么（工具、transcript、窗口、压缩边界、执行）
认知层   → 当前任务什么是真的、哪些必须保持、哪些可以降注意力
LLM      → 基于当前认知选择下一步
```

**它警告的五个风险：**

| 风险 | 判据 |
|---|---|
| State 变成第二份 transcript | 判据不是字段多少，而是"**这个 item 还会改变未来行为吗？**" |
| Belief State 成为第二套权威 | agent 自述只能用于诊断，不能替代 Checkpoint |
| 每个事件都启动 LLM capture | 成本/latency/竞争/churn → 一个边界 → 一个 Episode → 一次串行 Update |
| **任意状态预算**（`maxFacts=100`） | 大小必须由"任务复杂度 + 最小充分认知"决定，不是配额 |
| Recall 把历史污染回来 | 必须 explicit/targeted/bounded，绝不能"agent 想起什么 → dump 5000 token" |

**Risk 4 与本项目最初的原则一致**（"不要用 max_xxx 限制大模型"）——原始 Anchor 独立得出了同一结论。

# 附录 B · 本次会话中修正过的判断

保留这些，因为它们记录了思路的演化：

| 早期判断 | 修正 |
|---|---|
| "上下文爆炸可以由状态解决" | **半解决**。状态治历史，不治工作集。原始 Anchor 把工作集委派给宿主，而图没有宿主——这才是我们 60% bug 的成因 |
| "确定性 loss 的方差是零" | **不准确**。检查本身是确定函数，但通过与否取决于模型这次的输出，仍会变化 |
| "观察者不能改运行中的图" → 被读成"run 内无法自我纠正" | **两者说的是不同对象**。改图会塌；改状态本该如此。run 内的自我纠正是"检测 + 重做"，缺的是语义检测与诊断回灌，不是权限 |
| "回放可以用于 A/B 上下文策略" | **不能**。回放按位置匹配，改变 prompt 必须真实重新调用模型（见 ADR-044） |
| 用噪声/统计讨论优化问题 | **过度工程**。噪声只对边际改进成立；本次撞到的全是明显缺陷，一次就能看见 |

# 附录 C · 一句话摘要

> **状态解决的是"认知"问题：把历史变成充分统计量，把遗忘变成注意力分配，把编年史变成因果模型，
> 把压缩从"丢失风险"变成"可问责的转换"。**
>
> **它不解决"工作集"问题——那需要边契约与休眠引用，而原始 Anchor 从未回答它。**
>
> **它也不解决"优化"问题——那需要归因，而归因目前是空的。**
>
> **而这三件事加起来，才是"一个随时间变得老道而不是失忆的 agent"。**
