# 以提交为细腰：Anchor 的确定性架构方向

> 历史归档（2026-11-04）：保留当时的推导、授权范围、过程与证据，不作为新的实施授权；当前行为见[架构](../../architecture.md)，未关闭事项见[统一台账](../../pilot-development-plan.md)。

编制日期：2026-10-14。状态：**方向讨论稿，未实现，未授权实施**。

本文记录与用户讨论形成的架构方向：Anchor 应以什么作为唯一的公共接口（"细腰"），以及由此推出的内核、Graph、协作、度量与自进化形态。它不是实现清单，也不是进度台账。当前实现以 [architecture.md](../../architecture.md) 为准，产品目标与不变量以 [product-architecture.md](../../product-architecture.md) 为准，实际交付只记 [开发台账](../../pilot-development-plan.md)。

文中区分三类内容：**已确认的方向**（用户在讨论中明确同意）、**推导结论**（由方向推出，尚待实践验证）、**假设**（需要用代码或数据核实）。

## 1. 要解决的问题

### 1.1 Anchor 想成为什么

Anchor 的目标是通用的 Agent 基础设施：大量 Agent 与业务代码、数据协作，像一个整体一样自动、持续、高效地运转，并依据真实运行数据不断改进自身。

这个目标对架构提出三个要求：

1. **规模**：一万个 Agent 与业务相互协作时，系统仍能构建、维护和迭代。
2. **确定性**：大模型是基于概率的自然语言输出，企业落地 Agent 的核心障碍是不确定性。系统必须在不可靠的执行者之上提供确定的行为。
3. **适应性**：未来无法预测，所以架构不能靠预测未来来设计，而要能依据反馈调整自己。改进应首先作用于平台本身，使所有 Graph 共同受益，而不是只优化某一个 Graph。

### 1.2 三个要求指向同一个答案

- **规模**要求标准化的接口。N 个参与者两两约定协议，沟通成本为 N²；共用一个标准，成本为 N。
- **确定性**要求不相信执行者说的话，由确定性代码裁决。final_result 是这个思想在 Anchor 中的第一个实例：普通回答或看似正确的 JSON 不算完成，只有经代码校验的提交才算。
- **适应性**要求冻结的核心尽量小。一个系统的可进化性与其冻结核心的大小成反比：遗传密码几十亿年几乎不变，IP 协议几十年不变，正因如此，上面的一切才能自由演化。核心里的每一个防御性分支，本质上都是对未来的一次预测；既然未来无法预测，这些预测大多会落空，最终成为补丁和兼容负担。

三者共同要求：**一个极小、确定、所有东西都必须经过的公共接口。** 网络架构把这样的接口称为"细腰"（沙漏的腰部）：腰越窄，上下两端越能自由生长。

## 2. 细腰的选择（已确认的方向）

"细腰"是所有东西都必须经过的那一层。选谁当细腰，就是选谁是唯一的事实，其余都是它的派生视图。讨论比较了五个候选：

| 细腰 | 类比 | 擅长 | 主要问题 |
| --- | --- | --- | --- |
| 消息：一切都是对话 | 邮件与群聊、actor 模型；多数 Agent 框架 | 灵活、上手快 | 无结构，N² 理解成本，无法度量，规模化后成为噪声 |
| 日志：一切都是事件 | 会计账簿、事件流、事件溯源 | 审计、重放、数据齐全 | 只记录发生了什么，不约束允许发生什么；事件格式难演进 |
| 资源：一切都是有版本的对象 | Web、Git、Kubernetes | 统一管理、生态繁荣 | 描述名词而非行为，"谁说了算"偏弱，易配置泛滥 |
| 提交：一切改变都是提议加裁决 | 数据库事务、区块链交易、法庭、Pull Request 加 CI | 确定性最强，治理与审计内生 | 需要投资校验器 |
| 契约：一切都是有类型的任务 | 函数与远程调用、采购市场、DSPy 签名 | 组合、替换、优化 | 要求预先知道任务形状 |

成熟系统往往五者都有，但只有一个是根。区块链是最清楚的例子：交易是细腰；账本是已接受交易的有序序列；余额是对账本的计算；智能合约规定哪些交易可被接受。一个事实来源，四种视角。

**方向：以提交为细腰。**

- 已接受的提交按顺序记录，就是**日志**；
- 对日志的计算，就是**资源**的当前状态；
- **契约**规定每类提交如何被裁决；
- 自然语言**消息**只存在于提交的内容之中。

这样各候选的长处都得以保留：提交给出确定性，日志给出数据与可训练性，资源给出统一管理，契约给出组合与优化，消息保留 Agent 的灵活性，而事实来源只有一个。

### 2.1 标准化信封，而非内容

大模型的价值在于处理模糊的自然语言。若把内容也全部结构化，就扼杀了 Agent 的长处。法律体系与合同同样如此：程序、格式与证据规则是严格的，辩论与条款内容是文字。

细腰只规定：**谁提交、提交什么类型、作用于什么、引用哪些证据、裁决结果是什么。** 内容本身可以是自然语言。

## 3. 提交与裁决（推导结论）

### 3.1 提交

```
提交 = {
  目标:     资源，以及提议者看到的版本        ← 提议者填写
  动作:     有限的几种之一                    ← 提议者填写
  内容:     具体内容，可以是自然语言          ← 提议者填写
  证据:     引用的产物、观察记录              ← 提议者填写
  提议者、时间、成本、上下文                 ← 宿主观察填写，提议者不能填写
}
```

身份与成本永远由观察得到，不由提议者报告。

### 3.2 裁决

| 结果 | 含义 | 之后 |
| --- | --- | --- |
| 接受 | 通过校验 | 写入日志，状态改变 |
| 打回 + 原因码 | 可修正的问题 | 返回提议者修正 |
| 拒绝 + 原因码 | 不可修正（越权、违反不变量） | 终止该提交 |
| 待定 | 等待人或校验器 | 挂起 |
| 接受但未验证 | 形式合格，内容无法机械验证 | 写入日志并标记未验证 |

原因码是固定的分类表，由代码给出，不由模型总结。

### 3.3 两条边界

- **只有改变事实需要提交。** 读取、思考、对话、查资料都是自由的。过程自由，只有改变世界的那一刻受约束。这是"Agent 自由"与"行为纪律"同时成立的方式。
- **被打回和被拒绝的提交同样记录。** 它们和原因码是复盘与优化最有价值的数据。

### 3.4 声明分级

提交中的声明按证据强度分级：**已机械验证 / 有证据引用 / 未验证断言**。分级由代码标注，呈现给人时必须可见。"模型说的"与"代码证实的"在任何地方都可区分。

## 4. 内核塌缩为两个函数（推导结论）

```
裁决(提交) → 结果      找到目标资源的校验器并运行
折叠(日志) → 状态      资源的当前状态是对已接受提交的计算
```

校验器、Agent、调度、界面与度量，都是内核之上的东西。

**校验器本身也是资源。** 修改校验器同样是一次提交，由更高一层的校验器裁决。"谁能改什么"不需要另建权限体系，它就是资源的分层本身。递归到最顶层，是只有人能修改的宪法（第 9 节）。

## 5. Graph：从指挥变为约束（推导结论）

以提交为细腰之后，Graph 的含义改变：

> **Graph 规定一次 Run 在每个状态下接受哪些提交。**

Graph 是 Run 这一资源的校验器，是一个状态机：处于"等待审查"时只接受审查结论，审查通过后只接受发布提交。它不推着 Agent 走，而是规定什么样的结果会被接受。

Graph 的严格程度因此成为可调节的旋钮：

| 严格程度 | Graph 的形态 | 适用 |
| --- | --- | --- |
| 最严 | 每一步规定谁提交什么 | 流程化工作、能力较弱的 Agent |
| 中间 | 只规定关键检查点 | 已积累经验的工作 |
| 最松 | 只规定最终交付契约 | 能力很强的 Agent、开放式任务 |

Agent 能力上升后，未必需要用确定性的 DAG 预先约束和划分职能。在这个框架中，Graph 可以退化为只有最终契约，但细腰不变，确定性不变。系统不必为未来修改架构，只需调节旋钮；旋钮的位置本身也可以由数据决定。

同理，Graph 由谁编写不再重要：人编写或 Agent 编写的 Graph，都是对 Graph 资源的一次提交，经 Kernel 编译裁决后才被接纳。

## 6. 规模化协作：通过共享状态，而非相互对话（推导结论）

Agent 之间不直接通信，而是各自向共享资源提交，通过资源状态间接协调。这种协作方式有成熟先例：

- 蚁群通过环境中的信息素协调，不需要开会（生物学称为 stigmergy）；
- 维基百科的大量编辑者很少互相沟通，靠页面历史和规则协调；
- Git 上的大量开发者通过对同一仓库提交来协作。

每个 Agent 只需理解资源的格式，不需理解其他 Agent。新增一个 Agent 不会增加其他 Agent 的负担，沟通成本从 N² 降为 N。

并发冲突采用乐观并发控制：提交声明其看到的版本，若资源已被修改则打回，提议者读取新状态后重新提议。日志按资源分区排序，只有跨资源的提交需要更强的协调；不需要全局协调者。

## 7. 度量、反向传播与自进化（推导结论）

三者都不需要新机制，它们是同一份日志上的查询，以及对更高层资源的提交。

### 7.1 度量

每次提交天然将执行切分成段。两次提交之间的 token、耗时、工具调用、失败与原因，都能精确归属到"为了这一次提交"。所有指标都是日志的视图。

两条原则：

- **效率指标必须由宿主观察，不能由 Agent 报告。**
- **质量是约束，效率是目标。** 核心指标是"每个被接受结果的成本"：被打回和失败的成本计入分子，但不贡献分母。单独优化 token 或耗时，系统会学会少干活。

### 7.2 反向传播

日志就是 autograd 中的 tape。一个产物出现问题时，沿引用找到产生它的提交，再找到该提交依赖的上游提交，在冻结的输入上重放验证：

- 修正上游输入、保持本节点参数不变，重放后通过 → 责任在上游，继续回传；
- 保持输入不变、修改本节点参数，重放后通过 → 得到一个已验证的参数梯度；
- 都不通过 → 记为"未定位"，不硬归因。

模型提议归因，重放裁决归因。通过了自身契约校验的中间提交阻断回传，相当于神经网络中的 stop-gradient；中间契约越多，归因越精确、越便宜。

Anchor 的不可变产物与冻结输入，原本为可追溯和可恢复而建，恰好是可训练的前提。

### 7.3 自进化，以及平台整体受益

平台参数、默认指令、工具披露策略、错误提示、预算与超时默认值都是资源。优化器提交修改，校验器是跨 Graph 的基准测试集：

- 一项平台修改须在多个代表性 Graph 的案例上整体不退化、且有统计显著的改善才被接受；
- 只在部分 Graph 上改善、在其他 Graph 上退化的修改，应被拒绝或转为可配置项；
- 先在部分 Graph 上灰度，再推广；平台参数有版本，回滚就是切换版本。

类比编译器：优化一个程序只让这个程序受益，优化编译器让所有程序受益。平台级进化之所以可行，前提正是统一的细腰：只有所有 Run 都以同一种数据结构记录，才能跨 Graph 比较和汇总。

进化需要三个要素：变异（能提出改变）、遗传（改变能被保留、追溯、回退）、选择（能判断哪个改变更好）。Anchor 已有前两者，**缺的是选择**。度量与基准测试就是选择机制。

## 8. 分层：谁能修改什么（推导结论）

```
        可自由演化：Graph、Plugin、业务、Agent 能力
        ─────────────────────────────────
          平台参数：指令、策略、阈值、默认值      ← 自动演化，基准测试把关
        ─────────────────────────────────
           平台代码：Kernel、Host、Sandbox       ← Agent 可提议，人批准
              ─────────────────────
                       宪法                       ← 只有人能修改，极少修改
```

越往下越小、越稳定；越往上越大、越活跃。每一层的修改都是对该层资源的提交，由更下一层的规则裁决。

## 9. 宪法草稿（推导结论，待确认）

```
一、一切都是有版本的资源。
二、改变资源的唯一方式是提交。提交声明目标、版本、动作、内容和证据；
    提议者身份与成本由宿主观察填写。
三、每类资源都有校验器。提交当且仅当被校验器接受时生效。
    校验器本身也是资源，由更高一层裁决。
四、所有提交与裁决按资源有序记录。资源状态是对已接受提交的计算，可以重放。
五、每个任务必在声明的预算内结束于有限的结果之一：
    完成、带原因的失败、上报、不确定。
六、对外部世界的副作用也是提交：带幂等标识执行，结果被观察；
    观察不到时状态为"不确定"，先核查再继续，绝不自动重放。
七、提议者不能修改裁决它的校验器。最高一层的规则只能由人修改。
```

若后续确有必要增加第八条，应作为重大架构决定单独讨论。

### 9.1 用宪法检验现有设计

对现有每一项设计逐一询问：

- 能从宪法推导出来 → 好的设计；
- 推导不出来，但属于可调整的参数或策略 → 应移到上层，使之可演化；
- 推导不出来，又不是参数 → 很可能是补丁。

如果宪法一页纸写不下，说明核心还不够小。

## 10. 与现状的对照（假设，待核实）

Anchor 当前是多种细腰并存：

| 现有机制 | 偏向的细腰 |
| --- | --- |
| RunStore、Artifact 谱系、工具观察 | 日志 |
| Graph 与 Plugin 共用的资产模型（一份真身、一个编号、一个审批口） | 资源 |
| final_result、原生确认、`plugin_install` 摘要冻结 | 提交 |
| Session、Turn、渠道投递各自的状态与账本 | 各自独立 |

**假设：** 多个细腰并存意味着多个事实来源，它们之间需要同步与兼容，而这些同步与兼容之处，正是防御性分支与补丁集中的地方。例如多个生命周期动词各自的前置条件、多种记录格式的兼容路径。这一假设须通过第 11 节第 1、2 步用实际代码核实，不能直接当作结论。

对照公理，现状大致为：

| 宪法条目 | 现状 |
| --- | --- |
| 一、二、三（提交与裁决） | final_result、原生确认、Kernel 编译已体现，但只覆盖部分状态变化，形状不统一 |
| 四（记录与重放） | 较强；尚未把模型输出作为被记录的输入以支持生产级精确重放 |
| 五（必然结算） | **主要缺口**：预算控制暂未作为交付门槛；部分等待路径默认不设模型耗时上限；没有标准的"上报"提交 |
| 六（外部副作用） | 较强：不自动重放、未知结果先核查、投递账本 |
| 七（分层） | 有若干具体实例（RSI 安全检查不可被模型覆盖、Pilot 不能修改定义自己的 Graph），尚非普遍原则 |

度量与选择机制（第 7 节）基本尚未开始。

## 11. 迁移路径（推导结论）

不重写。采用逐步收编的方式（绞杀者模式）：

1. **建立统一的提交日志，作为投影。** 不改现有逻辑，只把现有的各类状态变化（节点完成、Plugin 安装、挂载、确认、Graph 保存等）投影为统一格式的"提交 + 裁决"记录。零风险，并立即得到跨 Graph 可比的统一数据。
2. **观察哪里对不上。** 投影过程会暴露哪些地方有多个事实来源、哪些状态变化绕过了裁决。这是对第 10 节假设的验证。
3. **新功能只走新路径。** 新的状态变化一律以提交实现。
4. **逐条迁移旧路径。** 从 final_result 开始，它最接近提交的形状。每迁移一条路径，删除对应的同步与兼容代码。

**判断标准：每迁移一条路径，代码应当变少。** 若迁移后代码变多，说明细腰的定义有问题，应回头修正设计，而不是继续推进。

在统一日志之上，度量投影、跨 Graph 基准测试与反向传播可以依次建立，第 7 节的能力随之出现。

## 12. 非目标

- 不让单个 Agent 的输出变得确定；确定的是系统。
- 不把提交内容全部结构化；自然语言保留在内容中。
- 不引入通用事件溯源、CQRS、微服务或新的 Agent loop；日志是提交的记录，不是另一套运行时。
- 不消除人；人是规则的来源和信任的根，目标是把人的参与压缩到最少、最关键的位置。
- 不承诺外部世界可控；系统只保证对外部世界的认知是诚实的。

## 13. 开放问题

- **校验器设计**：这是整个系统的真正瓶颈。自然语言内容大多无法机械校验，"接受但未验证"会很常见，需要诚实呈现，并通过抽样审计度量质量。系统可靠性的上限由校验器的漏检率决定，而不是由 Agent 决定。
- **提交的粒度**：太细则系统被淹没，太粗则归因不精确。"只有改变事实的动作才提交"是原则，"事实"的边界须在实践中确定。
- **动作的种类**：提交动作应是有限的几种，具体是哪几种（交付、移交、申请、执行、提议、上报等）须从现有工具的映射中归纳，不应预先设计。
- **性能**：每次改变都经过裁决与记录，高频操作需要按资源分区与批量处理。
- **跨资源一致性**：涉及多个资源的提交需要怎样的协调，尚未讨论。
- **"确定性"对企业的具体含义**：结果一致、风险有界、过程可审计、错误率已知，各自要求不同。须由真实使用场景回答。
- **进化的边界与目标函数**：哪些层可以自动演化、哪些必须人批准，以及进化的目标由谁定义，尚未冻结。

## 14. 建议的第一步

在不改变任何现有行为的前提下完成第 11 节第 1 步：选取节点完成、Plugin 安装与挂载、Graph 保存三类状态变化，投影为统一的"提交 + 裁决"记录，并输出一份报告：

- 每类变化映射为哪种提交、哪种裁决；
- 哪些变化无法映射，原因是什么；
- 哪些地方出现了多个事实来源；
- 统一记录后，能直接得到哪些此前无法比较的指标。

这份报告将决定第 10 节的假设是否成立，以及细腰的定义是否需要修正。
