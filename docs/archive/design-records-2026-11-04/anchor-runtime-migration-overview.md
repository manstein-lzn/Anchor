## 1. 执行摘要

**做了什么。** 把 Anchor 中负责"运行一个 Graph"的那部分（Run 的运行时）从头重建。旧实现是一个推模型的 `GraphRunner`：它自己选节点、调用执行、等结果、决定下一步，Run 的状态由多处代码直接改写。新实现以一部"宪法"为依据：所有改变都是**提交**，由一个很小的**内核**统一裁决、记录、结算、测量；Graph 的规则写成纯函数的**校验器**；调度器只负责派活和把结果交回去。

**现在在哪里。** 所有新 Run 统一走 Kernel，旧 Runner 已删除；Graph schema 15 不再保存 error/recovery/recovery_submissions/updated，失败和恢复展示来自 Kernel 结算/history。M4 已验收。M5 在固定 master `e60374f` 复核探针可重建，完成逐 crate、规则、C2 和测试函数度量：C2 0/0，Kernel 对 `0859373` 零 diff；本轮 workspace 2,200 / 0 / 126、fmt/围栏通过，Web 359 及构建、完整固定 Goose 123 / 0 / 0 引用 M4。迁移工作已交回，最终数据与后续决定见 [M5 测量](../../../experiments/constitution-host-preflight/final/measurement.md)；真实模型完整业务、渠道实网、部署及长期/规模压力未验。

**内核冻结基点（2026-10-20 更新）。** 数据中枢 P1 给内核加了只记录、不参与裁决的事实：时间、因果引用、Principal 携带的配置摘要、资源创建戳，以及只读的 `HistoryReader`；经过两轮独立审查后曾冻结为 `e172e05`，随后按第一性原理删除了全局序号和内核层的因果引用；简化版审查通过，**新的冻结基点 C1 为 `9a5fa57`**，原基点是 `0859373`。此后 `git diff 9a5fa57 -- rust/anchor-kernel` 必须为空，除非另有经过审查的内核变更。详见 [P1 验证与审查](../../../experiments/harness-hub/p1/verification.md)。

**得到了什么。**

- 生命周期规律（停止、暂停、恢复、放弃、结算不可逆、迟到结果被拒、未知不重放）由唯一的裁决点强制执行，不再依赖各处代码的自觉。
- 每个 Run 都有一份只追加、可重建的完整历史，被拒的提交也记录在内并计费。
- 修正了一批旧行为中的语义错误，例如记录了从未发生的调用、把"未知"伪装成"失败"。
- 为以后的测量与自我改进（RSI）打下统一的事实地基。

**付出了什么。** 代码总量没有减少，粗算生产代码净增约 5,600 行。Host 的复杂度主要在 Session、授权、投递这些层，这次重建本来就不涉及它们。所以这次的收益是**正确性与一致性**，不是**体量**。

## 2. 背景：旧运行时的问题

Anchor 的核心对象是 **Run**：一个 Graph 的一次执行。Graph 由节点和边组成，节点可以是 Agent（由大模型驱动，运行在 Goose 会话里）、确定性操作（Op.run）、子 Graph 调用（Op.call），以及并行的 fanout/join 区域。

旧运行时的问题不在于"有 bug"，而在于结构上很难保证没有 bug：

1. **多个写入者。** Run 的状态字段（`status`、`cursor`、`recovery` 等）被 Runner、恢复、控制、放弃、会话调用等多处代码直接改写后保存。同一条规则（例如"这个 Run 现在能不能恢复"）在 Host 里有十几处各自的判断。
2. **状态词汇过细。** 对外有 10 种状态（Ready、Running、Paused、Stopped、BudgetStopped、WaitingRecovery、WaitingCall、Completed、Failed、Aborted），其中几组之间的区别只是历史原因，规则却要一一照顾。
3. **控制靠轮询。** 停止和暂停通过 `stop_requested`、`pause_requested` 标志实现，执行路径要不断去检查这些标志。
4. **推模型把调度和裁决混在一起。** Runner 既决定"下一步做什么"，又决定"结果算不算数"。并行、子调用、中断恢复都要在同一个循环里特殊处理（`runner.rs` 1,034 行，`parallel.rs` 481 行）。

这些问题的共同根源是：**没有一个地方是"事实"的唯一来源，也没有一个地方是"规则"的唯一执行者。**

## 3. 设计依据：宪法

新架构以 `docs/anchor-constitution.md` 为依据，下面是它的要点。

### 3.1 五条宪法

> 不可靠的提议者在有边界的舞台上自由行动；确定性的代码负责裁决、记录和测量；被选择的改变才会留下。

| 条文 | 它禁止的东西 |
| --- | --- |
| 一、一切改变都是提交，由不是提议者的确定性代码裁决 | 模型的话直接成为事实；组件直接改写别人的状态 |
| 二、历史只追加；没有观察到的就是未知 | 改写历史；把未知当成功；自动重放结果未知的副作用 |
| 三、每件事都在有限的资源内，结束于有限的结果之一 | 永远运行、悄悄放弃、永远"进行中" |
| 四、每次提交都被测量；只有被选择的改变才会留下 | 凭感觉采纳改动；用模型的自我报告做优化目标 |
| 五、目的和最高规则来自人；规则不能被它约束的对象修改 | 系统自定终极目标；被裁决者修改裁决者 |

宪法里没有 Graph、Plugin、Agent、大模型这些词。它们是在宪法之上建起来的第一批东西，可以改变，也可以消失。

### 3.2 六种原语

系统中的一切，要么是下面六种东西之一，要么由它们组成：

- **资源**：有所有者、有版本的状态。一个 Run 就是一个资源。
- **提交**：对某个资源的一次改变请求，带提交者身份、所见版本和成本。
- **裁决**：对一次提交的判定，包括接受或拒绝、原因码，以及效果与核实的组合。
- **效果**：对外部世界的作用，有自己的生命周期。外部世界的结果可能是"未知"。
- **任务**：有预算、有相位（执行中 / 等待 / 已结算）、会恰好结算一次的资源。
- **测量**：从记录派生出的投影，用来统计，不作为事实来源。

### 3.3 内核只做四件事

```text
裁决   提交 → 找到目标资源的校验器 → 判定
记录   裁决、效果、观察 → 所有者只追加的历史
结算   任务 → 恰好一次、有限结果、预算封顶
测量   以上一切 → 测量点
```

内核不知道任何业务：没有 Graph、没有 Goose、没有 HTTP。它只认识资源、提交、校验器和任务生命周期。

### 3.4 "完美"的含义

宪法不追求事先证明正确，而是给出三个可以检验的条件：

1. 每个组件都能从宪法推出，或者属于可以整块替换的边缘；
2. 推到四个极限（模型无限强、规模无限大、时间无限长、对抗无限强）时，核心不需要改变；
3. 核心里没有可以删掉的东西。

## 4. 新架构

### 4.1 整体结构

```text
             ┌──────────────────────────────────────────────┐
  HTTP/Web   │ 业务层：Session、会话、投递、助手、API、Pilot │
  Pilot ───▶ │   只通过 run_access 门面读写 Run              │
  渠道       └───────────────────────┬──────────────────────┘
                                     │ 意图：admit / stop / pause / resume / abandon …
                                     ▼
             ┌──────────────────────────────────────────────┐
             │ run_access 门面（Host）                       │
             │   读：相位 + 进度 + 宿主观察 → 规则谓词       │
             │   写：把意图翻译成对内核的提交                │
             └───────────────────────┬──────────────────────┘
                                     ▼
 ┌──────────────┐  派发空位   ┌──────────────────┐   submit   ┌──────────────────┐
 │ 执行者        │◀───────────│ 调度器（Host）    │──────────▶│ 内核              │
 │ Goose/Op/调用 │──结果─────▶│ 拉取开放空位      │           │ 裁决·记录·结算·测量│
 └──────────────┘            └──────────────────┘           │   └ GraphValidator │
                                                            │   └ FileStore      │
                                                            └──────────────────┘
```

### 4.2 内核（`rust/anchor-kernel`，约 1,500 行）

- **唯一入口** `Kernel::submit(principal, cost, submission)`。所有对 Run 的改变都从这里进入。
- **身份由宿主盖章**：提交者是 Agent、Code 还是 Human，成本是多少，都由宿主填写，不从模型输出里读。
- **乐观并发**：提交时带上"我看到的版本"。版本过期就拒绝（`StaleVersion`），提议者重读后再提交。
- **任务生命周期是内核定律**：
  - 相位只有三种：Executing、Waiting（等人 / 等子任务 / 等效果）、Settled（结局有限）；
  - 已结算的任务拒绝一切后续提交（`TaskSettled`），但这些被拒的提交仍然记入历史；
  - 处于等待状态的任务拒绝 Agent 提交。
- **存储**（`FileStore`）：先追加 `history.jsonl` 并 fsync，再原子替换 `resource.json`。崩溃后可以从历史恢复。删除操作先把目录改名，再移除，中途崩溃也能幂等地完成。
- 整个迁移过程中，内核只改过两次，两次都经过登记和审查：K0.1（成本记账、中断事实等 D1–D5）和 K0.2（删除与按资源的排他租约）。

### 4.3 Graph 校验器（`GraphValidator`）

Graph 的全部规则写成一个纯函数的校验器：不做 I/O，不调用任何端口。

- `open` / `frontier`：根据当前进度，回答"现在接受哪些节点调用"，每个调用对应一个空位，形如 `节点#序号`。
- `judge`：对一次提交，记录结果、选择路由，并判断 Run 是否结算。
- **并行不是特殊路径**：fanout 一次开放多个空位，所有分支完成后 join 才开放。调度器是按波次执行还是空位一开就执行，由调度器自己决定，与 Graph 无关。
- **Op.call 不是特殊路径**：宿主代码绑定子 Run 之后，父 Run 进入"等待子任务"；子 Run 结算后，宿主代码提交结果，父 Run 继续。
- **控制节点只能由 Code 提交**：fanout、join、call 由宿主代码提交，Agent 不能伪造。

### 4.4 调度器与执行者（拉模型）

```text
loop:
  读取 Run → 相位不是 Executing 就退出
  frontier = GraphValidator::frontier(Run)
  对每个尚未运行的空位：派给执行者（并发，不需要波次屏障）
  任一执行者完成：冻结产物 → 提交 → 内核裁决 → 回到 loop
```

- 调度器内部只保存"正在运行的 future"，所有进度和决定都由校验器重新计算。所以进程重启后不需要游标文件，直接从内核读回即可。
- 停止就是一次 Human 的 `stop` 提交。执行者的取消在这次提交被接受之后才触发，执行路径上没有任何轮询标志。
- 暂停是一个边界意图：在下一个节点边界，把已持久化的暂停意图消费掉，提交一次 `stop`，原因是 `paused`。

### 4.5 run_access 门面

这是 master 和分支协作的关键（见 §5.4）。业务代码只通过门面访问 Run：

- **读**：`RunView` 包含相位、Graph 进度和宿主观察（是否有 worker 在跑、更新时间），每条规则对应一个谓词，例如 `can_resume`、`is_quiescent`、`needs_attention`；
- **写**：按意图命名的操作，例如 `admit`、`stop`、`pause`、`resume`、`abandon`、`record_recovery_decision`；
- **对外 JSON** 由门面统一生成：`phase`、`waiting_for`、`outcome`、`reason`、`active`、`actions`；
- **围栏测试**：扫描业务代码，只要出现 Run 的内部类型就让测试失败。业务侧的引用数从 224 降到 0。

### 4.6 几个关键机制

| 场景 | 新的处理方式 |
| --- | --- |
| 节点执行失败 | 宿主代码提交 Settle，Run 结算为失败；并行区域中第一个被接受的终结事实决定结局（S17/S18） |
| 结果未知的外部效果 | 不提交节点结果，Run 进入等待。人点 resume 后，Agent 在同一个原生会话里核查现场再继续，不会把效果重放一遍。人也可以直接裁定"已完成"或"放弃" |
| 预算耗尽 | Code 提交 stop，Run 进入"等待人，原因是 budget"，人可以追加预算后恢复。要不要改为直接结算为失败，是待决的 W4 |
| 常驻助手被新消息打断 | 打断是宿主代码的提交，会产生一个中断事实；被打断的旧回复不会记为成功 |
| 删除 | 门面在执行锁内复查相位、worker 和会话引用，然后调用 `FileStore::remove`，连同历史一起物理删除 |
| 迟到的结果 | 被拒绝（`TaskSettled`），但完整保留在历史中，不重试 |

## 5. 推进过程

### 5.1 时间线

| 日期 | 阶段 | 内容 |
| --- | --- | --- |
| 10-16 | K0–K3 | 在分支上建内核与校验器，覆盖串行、并行、Op.call，用 20,000 个随机 Graph 与旧 Runner 做差分对照 |
| 10-16～17 | K0.1、H1、H2.1、P | 内核修订；删除旧格式兼容；节点失败结算；串行内核路径接入 Host |
| 10-17～19 | R、R2 | 两次读取侧探针，结论为负（见 §5.2） |
| 10-19 | 决策 | 用户决定全量迁移；采用双轨策略（§5.4） |
| 10-19 | F0–F2、G0 | master：门面与围栏；修复 Goose 测试基线 |
| 10-19 | M1、M1.5、M2 | 分支：统一状态词汇；合并 master；内核路径功能补齐 |
| 10-20 | M3 | 默认切到内核，同时删除旧实现，独立复验通过 |

从开分支到删除旧 Runner 共 4 天，分支上约 48 个提交。

### 5.2 一个重要的负结论：Host 不会因此变小

最初的假设是：把运行时换成内核以后，Host 中按状态分支的判断会大幅减少。为此做了两次探针，用同一套脚本统计同一组消费者的"独立判断点"：

| 时点 | 判断点 |
| --- | --- |
| 基线 | 82 |
| R：引入只读视图，对外 JSON 不变 | 90 |
| R2：同时收敛对外状态词汇 | 92 |

原因是：这些判断大多不是运行时规则，而是 Session 层的规则，比如这个会话是不是当前会话、能不能交接、有没有未结算的投递。只 `conversations.rs` 一个文件就占了基线 82 个中的 59 个。宪法从来没有打算简化这一层，所以"减少 50%"这个目标从构造上就达不到。

这个结论改变了迁移的理由：从"让 Host 变小"改为"让规律统一、语义正确、旧 Runner 可以删除"。用户在这个前提下决定全量迁移。

### 5.3 pause 的教训

R2 曾把 pause 当成 stop 的别名，导致十多个 API 测试失败，原因是 pause 的语义是"在下一个节点边界停下"，这是一个调度意图，不是一种状态。M1 把它改成边界控制，结果是"等待人，原因 paused"。这件事说明：收敛状态词汇时，**动作**和**状态**要分开考虑。

### 5.4 双轨策略：先降耦合，再换实现

全量迁移面临一个现实问题：master 上的业务开发很活跃，Host 有 37 个文件、约 370 处直接引用 Run 的内部类型。分支每换一处实现，合并时都可能出现语义冲突。

解决办法是分两条线：

- **master（F0–F2）**：建门面和围栏，把业务代码改成只调用门面，行为完全不变，对外 JSON 逐字节不变。结果：业务侧引用从 224 降到 0；13 条规则的独立实现从 36 处收成 13 处。
- **分支（M1–M5）**：在同一套门面接口背后，用内核实现。

这样两边合并时，冲突只集中在门面内部。之后三次合并 master 都很顺利。顺带得出一个结论：**规则去重本身不需要内核，靠门面就能做到。** 内核额外提供的是强制执行：门面只靠约定和围栏，内核让绕过在结构上做不到。

### 5.5 测试基线修复（G0）

推进中发现，Goose 回归测试几乎全部失败，而且这种状态已经持续了一段时间，所以 M1 报告的"全绿"其实没有覆盖这部分测试。根因是测试 fixture 没有配置网络 relay：任务网络被 slirp 隔离后，访问不到宿主本机上的 MCP 控制面。产品路径本来就配了 relay，不受影响。修复之后，Goose 门槛立刻在分支上抓出 5 个真实 bug。

### 5.6 停止条件与裁定

任务书给 agent 规定了两级停止条件：

- **必须停下交回**：要改内核、要改校验器的裁决规则、要放宽业务断言、两组现有测试的要求互相冲突；
- **自行判断后继续**：只需登记、事后批量审查的事项。

实际触发过的停止，以及当时的处理：

| 停止原因 | 裁定 |
| --- | --- |
| 并行分支里的模块作用域需要扩展校验器 | 批准，属于 Graph 语义 |
| 删除需要 `FileStore::remove` | 批准；实现时额外加了租约，追认并登记为 K0.2 |
| 并行分支里的 Op.call | 不扩展校验器。master 在准入时就拒绝这种组合，内核路径复用同一条拒绝 |
| 普通 resume 的恢复契约 | 回到 master 的行为：Agent 核查后继续，人工裁定作为另一条路径保留 |

## 6. 语义变化（S 条目）

每一处行为变化都编号登记，经审查批准。下面是对理解系统最重要的几条，完整列表见工作记录。

| 编号 | 场景 | 新行为 |
| --- | --- | --- |
| S1 | 节点提交了非法路由 | 打回给提议者修正，不让整个 Run 失败 |
| S2 | 所有节点都因轮数上限停下 | 结算为 Escalated，附上原因 |
| S5 | 并行区域中某个分支触发上限 | 不把从未派发的调用记为"已开始" |
| S6 / S18 | 并行区域已经无法汇合 | 立即结算；之后到达的兄弟结果被拒绝，但完整记入历史 |
| S7 | 子 Run 有没有被接纳不确定 | 结算为"未知"，不伪装成失败 |
| S8 | 调用节点有多条出边 | 创建 Run 时就拒绝 |
| S10 | 成本 | 所有提交都计费，包括被拒绝的；因版本过期重新提交同一份工作时，成本记为 0 |
| S19–S24 | 状态词汇收敛 | 10 种状态收成 3 种相位，可用动作由相位推出 |
| S27（结清 S4） | 助手退役之后 | 退役只移动 Session 的"当前"指针；未结算的 Run 仍可由人放弃 |

## 7. 质量保证

| 手段 | 作用 |
| --- | --- |
| 差分测试 | 同一个随机 Graph 分别用旧 Runner 和新内核执行，比较派发序列和最终事实。M2 的规模：串行 10,000，并行有失败和无失败各 5,000，模块 5,000，调用 5,000 |
| 冻结快照 | 删除旧 Runner 之前，先把 30,000 例旧侧事实冻结成快照，之后用快照代替旧 Runner 做对照 |
| 围栏测试 | 业务代码一旦引用 Run 的内部类型，测试就失败；允许名单不能放宽，计数只能下降 |
| C1 检查 | 内核相对基线的 diff 必须为空，除非是批准过的改动 |
| C2 棘轮 | 直接写 Run 的地方只减不增，最终为 0 |
| Goose 门槛 | 用固定版本的 Goose 二进制跑真实 Agent 会话回归，失败名单必须为空 |
| 独立复验 | 审查方在机器空闲时自己重跑。M3：workspace 2153/0/125，Goose 122/0/0 |
| 断言纪律 | 状态词汇类断言可以改，但要逐条登记；旧 Runner 内部的断言要有映射才能删；业务断言一律不得放宽 |

## 8. 评估

### 8.1 已经证明的

- 内核加校验器能完整表达旧运行时的语义，有差分和快照对照作为证据。
- 内核很稳定：功能补齐的过程中只做了两次登记过的修订。
- 生命周期规律成立：直接写 Run 的地方为 0，停止和暂停的轮询为 0。
- "先降耦合、再换实现"有效，合并成本可控。

### 8.2 没达到预期的

- **代码量**：固定区间 fc558e2→e60374f，Rust 生产删除 6,459、新增 12,930，净增 6,471 行；测试删除 7,043、新增 29,468，净增 22,425 行。内联测试已分开；区间包含独立 master 工作，不能全部归因于迁移。行数未达到 Host 变小的预期，也不代替规则收敛验收。口径与逐 crate 表见 [M5 最终测量](../../../experiments/constitution-host-preflight/final/measurement.md#按-crate-的-rust-行数)。
- **Host 复杂度**：Session、授权、投递层的复杂度没有变化，这是 §5.2 的结论。
- **测量**：探针已经在产出数据，但还缺时间、任务类别、模型这几个坐标。

### 8.3 过程中的教训

- **任务书的规格错误是最大的拖累**，前后约 9 处，每一处都让 agent 白跑一轮。例如：达不到的 50% 目标、把 pause 当成 stop、快照时机安排错误、恢复契约的措辞含糊。现在的对策是：发出任务书之前，先列出所有编码了"将被改变的行为"的现有测试，再计算度量的基线构成。
- **测试基线要先验证**："全绿"必须确认覆盖了应有的测试，不然就是假信号。
- **并发负载会制造假失败**：多个 agent 共用一台机器时，构建目录要分开，失败要单独复跑确认。
- **采信 agent 的数字有风险**：关键节点必须由审查方独立复验。

## 10. 与 RSI 的关系

宪法第 6 节描述的"系统如何变好"是一个有门禁的调优闭环：

```text
信号（从测量统计）→ 旋钮（有版本、可回滚的少数自由度）→ 策略
  → 选择门禁（保留集上质量不退化、成本显著下降才采纳）→ 旋钮集合本身也接受数据检验
```

这次重建并没有实现这个闭环，它交付的是闭环的**地基**：

- 所有工作都经过一个裁决点，每次裁决都留下带身份、成本、序号和旋钮版本的事实；
- 测量是从这些事实计算出来的投影，统计、分析、旋钮、梯度都可以以后在历史上重新计算。

需要注意的是：**分析可以以后补，当时没记下的事实补不回来。** 目前 Run 级的事实是齐的；以下三类还没有确认，或者确认没有记录：每次提交的时间（已确认没有）、使用的模型（未核实）、会话内部的工具调用与沙箱拒绝（未核实）。要不要补、什么时候补，用户以后再决定。

## 11. 术语表

| 术语 | 含义 |
| --- | --- |
| Run | 一个 Graph 的一次执行，在新架构中是一个内核任务资源 |
| 提交（Submission） | 对资源的一次改变请求 |
| 裁决（Verdict） | 内核对提交的判定，包括接受或拒绝、原因码 |
| 相位（Phase） | Executing、Waiting、Settled 三者之一 |
| 等待者（Waiter） | Waiting 的对象：Human、Child 或 Effect |
| 结局（Outcome） | Settled 的结果：Done、Failed、Escalated、Unknown、Aborted |
| 校验器（Validator） | 资源的纯函数规则；GraphValidator 就是 Graph 的规则 |
| 空位（Slot / Dispatch） | 一个当前可接受的节点调用，形如 `node#3` |
| 门面（run_access） | 业务代码访问 Run 的唯一入口 |
| 围栏（fence） | 阻止业务代码引用 Run 内部类型的测试 |
| 差分测试 | 新旧实现在同一输入上的行为对照 |
| C1–C6 | 迁移的硬约束：内核零业务、唯一改变入口、校验器不调用任何人、不新增轮询、不读模型自述、分支不保留旧格式兼容 |
| S 条目 | 编号登记、经过审查批准的行为变化 |
| K0.x | 经过批准的内核修订 |
| Goose | 运行 Agent 会话的引擎，Anchor 使用固定版本的二进制 |
