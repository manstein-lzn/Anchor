# Anchor 收敛与能力补齐：开发方案

> 历史归档（2026-11-04）：保留当时的推导、授权范围、过程与证据，不作为新的实施授权；当前行为见[架构](../../architecture.md)，未关闭事项见[统一台账](../../pilot-development-plan.md)。

编制日期：2026-10-14。实施授权仅覆盖 **W1**；W2–W5 仍待审核、未授权。验收结论见 [当前验收与待办](../../pilot-development-plan.md)。

本文是实施交接入口，不是进度台账。当前实现以 [architecture.md](../../architecture.md) 为准，产品目标与不变量以 [product-architecture.md](../../product-architecture.md) 为准，实际交付、失败与证据只记 [开发台账](../../pilot-development-plan.md)。方向讨论见 [以提交为细腰](submission-narrow-waist.md)；本方案吸收了对该讨论稿的评审意见，不以它为实施依据。

## 1. 结论与依据

### 1.1 结论

**不做整体重构。** 做三项局部收敛（W1–W3）和两项增量能力（W4–W5）。

### 1.2 依据（编制时对代码的抽样核查）

支持"不重构"的事实：

| 事实 | 位置 |
| --- | --- |
| Kernel 执行契约不依赖 Goose、HTTP 或业务；`NodeExecutionOutcome` 已是有限的结算类型 | `anchor-runtime/src/graph/ports.rs` |
| `Op.host` 校验只要求 `operation` 为非空字符串，Kernel 不枚举具体操作，新能力无需改 Kernel | `anchor-runtime/src/graph/admission.rs` `validate_host_operation` |
| Run、Session、Library 各自拥有不同事实，属于合理分工，未发现同一事实存在两个独立可写来源 | 抽样：`run_deletions.rs`、`application/queries.rs`、`application/assistants.rs` |
| Host 约 7.4 万行（含测试），最大源文件 2,375 行，无失控的巨型文件 | `anchor-runner-host/src` |
| Host 已采集每次 invocation 的 token、缓存、成本、耗时、首 token 时间、上下文用量与压缩 | `anchor-runner-host/src/goose_acp/usage.rs` |

编制时识别的局部问题（当前验收状态以台账为准）：

| 问题 | 规模 | 对应工作包 |
| --- | --- | --- |
| "终态""已静止"两个领域概念没有名字，`RunStatus` 上没有任何方法，各处手写 `matches!` | 非测试代码中 15 处 | W1 |
| "Run 是否仍在执行"由持久状态与进程内 `active` 集合共同决定，组合判断散落 | 17 个非测试文件 | W1 |
| Run 查询依赖全量扫描 `runs/` 并逐个反序列化 | `records()`、`has_unfinished_plugin_run`、`child_metadata` 等 | W2 |
| 兼容分支只增不减，无退役机制 | 含 `legacy`/旧格式字样的非测试命中约 135 处（未逐条分类） | W3 |
| 任务没有必然结束的保证；缺少标准的上报结果 | 产品架构明确"预算控制暂不作为交付门槛" | W4 |
| 用量已采集，但没有跨 Run、跨 Graph 统一关联的视图，失败原因没有分类码 | — | W5 |

### 1.3 核查的局限

本次为抽样核查，不是全面审计。提交历史的变更频率分析未执行；兼容分支数量是关键字命中数，未逐条分类。各工作包的第一步都包含对自身范围的完整核对。

## 2. 本方案的原则

1. **W1–W3 不改变任何用户可见行为、持久格式、权限或恢复语义。** 它们是纯收敛，现有测试是行为基线。
2. **W4、W5 是新增能力。** W4 改变产品语义，必须先取得用户决定；W5 只读，不新增运行时写路径。
3. **区分"重复的同一规则"与"看起来相似的不同规则"。** 不做机械替换，每个调用点逐一分类。
4. **度量改善用"同一规则的独立判断点数量"，不用代码行数。**
5. 遵守 [AGENTS.md](../../../AGENTS.md)：同一路径单一编辑者；先定向测试，切片完成后一次全量；不 reset/checkout/clean；只提交实际修改的路径。

## 4. W1：Run 状态与执行者观察

本工作包只收拢已有判断，不改变状态、持久格式、权限、错误文本或恢复行为。当前接口与归属见 [当前架构](../../architecture.md#执行链与所有权)，验收结论与证据见 [当前验收与待办](../../pilot-development-plan.md)。

实施与验收边界：

- Kernel 的 `RunStatus::is_terminal()` 统一 `Completed`、`Failed`、`Aborted`，原有非终态判断使用其反向查询。
- Host 的 `RunLiveness::is_quiescent()` 表达“执行者未登记，且为终态或 `Stopped`”。登记涵盖启动、清理与等待输入，不等于模型正在工作。
- 调用方保留原有 active 锁、Run lease、读取与轮询顺序。查询接收现有记录和登记观察，不另加锁、不缓存事实；持 active 锁不代表冻结 Runner 的状态写入。
- 不引入“陈旧运行”查询或自动恢复决定。未登记的 `Ready` 可能等待调度，`Running` 的恢复仍由原用例处理。
- abandon 中 `Aborted` 的幂等成功、仅接受 `Completed` 的产物路径，以及仅看持久状态的停止条件分别保留，不强行套用静止判断。
- 验收覆盖全部 Run 状态、执行者登记组合与前驱 wait child 退出边界，并执行相关控制、退役、删除和恢复回归。使用行为测试，不新增扫描源码写法的守护测试。

## 5. W2：Run 查询的性能基准与索引

### 5.1 目标

确认 Run 数量增长后，全量扫描是否成为瓶颈；只有数据证明需要时才建立索引。

### 5.2 步骤一：基准（必做）

在 `anchor-devtools` 或 Host bench 中，用合成数据生成 1,000 / 10,000 / 50,000 个 Run 记录及 metadata，测量：

- `records()`
- `has_unfinished_plugin_run`（Graph 保存前置条件）
- `child_metadata`
- `GET /runs` 列表
- Host 启动时的恢复扫描

记录耗时与内存，结果写入台账。

### 5.3 步骤二：索引（视基准结果）

判定标准：任一操作在 10,000 个 Run 时超过 200 ms，或在请求路径上以 O(N) 反序列化方式出现。

若需要，设计约束：

- 索引是**可重建的投影**，不是事实来源。字段限于 Run ID、Graph 身份、状态、是否有 Plugin 绑定、父 Run。
- Host 启动时从 `runs/` 重建；不持久化，避免"记录已保存、索引未更新"的窗口。
- 运行期更新只能发生在 Host 唯一的 Run 保存路径上。实施前须核对所有 `store().save` 调用点，确认它们经过同一入口；若不是，先收拢保存入口，再建索引。
- 查询结果有疑问时（索引缺失某个 ID），回退到读取该 Run 的记录文件，而不是信任索引。

### 5.4 验收

- 基准数据入台账。
- 若建索引：删除索引后重启，查询结果与全量扫描逐条一致；并发保存与查询的定向测试通过；10,000 个 Run 时达到判定标准。

## 6. W3：兼容分支登记与退役政策

### 6.1 目标

让兼容代码有明确的期限，而不是只增不减。

### 6.2 步骤

1. **盘点。** 对约 135 处命中逐条分类：
   - 持久格式兼容（如 Run format 12/13、mount snapshot format 1/2、无链接字段的旧墓碑、`can_upgrade_legacy_authorization`）
   - 旧执行器隔离（如 `legacy_invocation_exists` 拒绝恢复旧 Agent 状态）
   - 旧产品路径（如一次性助手与常驻助手并存）
   - 误报（注释、名称中含 legacy 但非兼容逻辑）
2. **登记表。** 建立 `docs/compatibility-registry.md`，每项记录：位置、兼容对象、引入日期、依赖它的真实数据是否存在、退役条件、退役后的行为（具名拒绝的错误信息）。
3. **离线工具。** 在 `anchor-devtools` 增加只读盘点命令：扫描给定数据根，报告每类旧格式的实际存量。只读，不迁移。
4. **退役政策（需用户决定，见第 10 节）。** 建议形式：新增兼容分支必须登记并给出退役条件；到期后，若存量为零则直接删除并改为具名拒绝，若存量非零则先提供显式迁移命令。
5. **首个退役候选。** 盘点后选一项存量为零或可安全迁移的分支完成退役，验证流程。

### 6.3 约束

- 不对现有生产数据执行任何迁移；台账记载的现有生产工作区不在本工作包的处理范围。
- 退役删除代码属于行为变化（旧数据从"兼容"变为"具名拒绝"），每一项都须单独确认。

### 6.4 验收

- 登记表覆盖全部真实兼容分支，误报单列。
- 盘点工具在隔离数据根上的输出入台账。
- 首个退役项：删除后旧数据得到具名拒绝；新数据行为不变；相关测试更新并通过。

## 7. W4：必然结算

### 7.1 目标

每个任务在声明的上限内结束于有限的结果之一：完成、带原因的失败、上报、不确定。

### 7.2 与现行产品决定的冲突

[product-architecture.md](../../product-architecture.md) 写明"预算控制暂不作为交付门槛，优先完成任务"；[企微助手文档](../../wecom-assistant.md) 写明 Host 等待路径不设默认模型耗时上限。**W4 会改变这两项决定，未经用户明确批准不得实施。**

### 7.3 已有基础

- `NodeExecutionRequest` 已有 `max_provider_requests` 与 `wall_time_limit_seconds`；节点整体墙钟控制已生效。
- `NodeExecutionOutcome::BudgetExhausted` 与 `RunStatus::BudgetStopped` 已存在。
- `NodeExecutionCapabilities::exact_provider_request_budget` 区分精确与近似计数。

因此 W4 主要是**默认值与结果语义**，不是新机制。

### 7.4 待决定的设计选项

| 问题 | 选项 |
| --- | --- |
| 默认上限放在哪一层 | 平台默认值 + Graph/节点覆盖（推荐） / 只在 Graph 显式声明 |
| 默认值是否对现有 Graph 生效 | 只对新 Graph 生效（推荐，避免改变已部署行为） / 全部生效 |
| 上报如何表达 | `final_result` 增加上报类结果，经已有 route 交给指定节点 / 新增 Run 终止原因 |
| 常驻助手 | 单轮设上限、实例不设上限（推荐） / 不纳入 |

### 7.5 实施切片（决定之后）

1. 平台默认上限配置（沿用 `RuntimeConfiguration` 的唯一解析入口，不新增配置来源）。
2. 上报结果：Agent 可以诚实地提交"做不到，原因如下"，由 Graph 路由处理，而不是被迫硬提交或等待超时。
3. 前端与 API 展示结束原因。
4. 确定性回归：超上限、上报、上报后路由、旧 Graph 行为不变；真实 Provider 验证一次上报路径。

### 7.6 验收

由用户决定后的契约确定。至少包括：在默认配置下构造一个不会收敛的任务，它在上限内以明确原因结束；旧 Graph 行为不变。

## 8. W5：度量关联投影

### 8.1 目标

把已经采集的用量与已经保存的结算事实，关联成一个跨 Run、跨 Graph 可比较的**只读视图**，供复盘与 RSI 使用。

### 8.2 设计约束（回应评审意见）

- **不新增运行时写路径。** 投影从现有持久事实离线计算：RunStore、节点结果与证据（含 `usage.rs` 的聚合指标）、run metadata、Session/Turn。主路径的任何失败都不会因投影而产生，也不存在"状态已保存、投影未保存"的窗口。
- **可重建。** 删除投影后重新计算，结果逐条一致。
- **不是质量背书。** 投影记录发生了什么、花了多少，不表示结果正确。

### 8.3 每行内容

粒度为一次 invocation。

| 类别 | 字段 | 来源 |
| --- | --- | --- |
| 归因 | Run、Graph 身份与摘要、节点、invocation、模型、指令摘要、Plugin 摘要与依赖视图 | RunStore、`plugin_bindings`、`plugin_digests`、`plugin_views` |
| 结果 | 结算类型、原因码（8.4）、是否经反馈边返工 | 节点结果、`NodeExecutionOutcome` |
| 成本 | 请求数、输入/输出/缓存 token、成本、耗时、首 token 时间、压缩次数 | `usage.rs` 聚合指标 |
| 来源 | 手动、计划、Webhook、渠道、调用 | Run metadata |

**须先核实：** `usage.rs` 的聚合值是否完整写入了每个节点的持久证据，以及 `model_requests_scope` 在确定性 fixture 与真实 Provider 下的含义差异（`goose_acp.rs` 中有区分）。

### 8.4 原因码

建立固定分类，由代码从已有类型化错误映射，不由模型总结：

| 码 | 含义 |
| --- | --- |
| `completed` | 正常完成 |
| `yielded` | 让位（中断、新输入打断） |
| `budget_exhausted` | 预算耗尽 |
| `cancelled` / `interrupted` | 取消、中断 |
| `waiting_recovery` / `aborted` | 未知外部效果待核查、操作员放弃 |
| `failed.sandbox_denied` | 沙箱拒绝 |
| `failed.tool_error` | 工具业务错误 |
| `failed.tool_timeout` | 工具超时 |
| `failed.completion_invalid` | final_result 校验失败（如有持久记录） |
| `failed.other` | 未能分类，保留原始文本 |

口径写入 `docs/metrics-definitions.md`，冻结后修改须记录版本，避免历史数据不可比。

**须先核实：** 被打回的 final_result 尝试是否有持久记录，还是只存在于 Goose 原生历史。若只在原生历史中，第一版不包含这一项，不从原生历史解析。

### 8.5 共享成本的归属规则

统一记录不能自动解决共享成本，需要明确口径：

- 成本归属于实际产生它的 invocation。
- fanout 分支各自计算；join 只计算自身。
- 依赖准备、MCP 启动、Plugin 候选准备等不属于任何 invocation 的成本，单列为"共享准备成本"，不分摊到节点。
- 等待人工（确认、提问）与排队的时间不计入节点执行耗时；若现有数据无法区分，标注为"未区分"，不推测。

### 8.6 交付形态

- `anchor-devtools` 中的只读命令：输入数据根，输出 JSONL 或 CSV。
- 第一版不提供 HTTP API。是否提供由 RSI 接入时的实际需要决定。
- RSI 的 `collect` 节点改为读取该投影的工作，作为后续单独切片，不在本方案内。

### 8.7 验收

- 在隔离数据根上，对至少三个不同 Graph 的真实 Run 生成投影。
- 删除后重建，结果一致。
- 抽查若干行，与原始节点证据逐字段核对。
- 原因码覆盖率：`failed.other` 的比例记录入台账，作为口径完善的依据。

## 9. 验证纪律

- 每个工作包先跑直接相关的定向测试；工作包完成后一次 Host all-targets、Clippy `-D warnings`、workspace fmt。
- W1–W3 无 Web 改动，不跑 Web 检查。
- W4 涉及运行时语义：确定性 Goose fixture 回归 + 一次隔离真实 Provider 验证。
- W5 只读：在隔离数据根上验证，不读取生产数据，除非用户另行授权。
- 验证报告只写实际执行的命令和结果，失败、跳过、未覆盖的边界分别列出。

## 10. 需要用户决定的事项

| 编号 | 事项 | 影响的工作包 | 建议 |
| --- | --- | --- | --- |
| D1 | 是否改变"预算控制暂不作为交付门槛"的产品决定 | W4 | 改变，但默认值只对新 Graph 生效 |
| D2 | 上报结果的表达方式 | W4 | 经已有 route 交给指定节点，不新增 Run 终止状态 |
| D3 | 兼容分支的退役期限与存量非零时的处理 | W3 | 新增分支必须登记退役条件；存量非零先提供显式迁移命令 |
| D4 | 度量口径文档的审核人 | W5 | 冻结前由用户审核一次 |

W1、W2、W5 的实现部分不依赖这些决定，可以先行。

## 11. 不在本方案范围内

- 提交与裁决协议的全面统一。新增的状态变化可以按该形状设计，已有路径只在本来就要修改时顺手收敛。
- 案例库、节点重放、评估门禁、RSI 闭环。它们依赖 W5 的投影，另立方案。
- Kernel 契约、Goose 集成、沙箱策略、权限模型的任何改动。
- 生产部署、生产数据迁移。
