## §P0 噪声测量

**状态（2026-10-20）：已完成。** 用户改为由主 Agent 直接推进，结论见 [P0 报告](../experiments/harness-hub/p0/report.md)：

- 受控对比在统计上可行，但多步任务的波动主要来自路径长度，需要按轨迹分层或折算到每轮；
- 两个任务的质量都在上限，需要 P4 的评测任务集；
- 工具失败全部是 Harness 接口摩擦。

### 目的

在配置完全固定的条件下，测量同一任务重复运行时四个判据的波动有多大，并据此算出"两个变体之间要相差多少、每边要跑多少次才能看出区别"。这决定后面的受控实验（P6）能不能做、要做多大。

**本阶段不改任何产品源码。** 脚本、夹具和结论放在 `experiments/harness-hub/p0/`；原始日志、模型输出和证据只放在 `.local/harness-hub-p0/`，不入库。

### 环境

- **使用平台已保存的渠道和默认 Flash 模型**。用户已授权，不必节省 token。
- **隔离运行**：参照 `.local/weekly-gateway-wording-20261020/verify.py` 的做法：
  - 使用和运行中 8077 服务相同的 Host 可执行文件，并记录它的 SHA-256；
  - 使用固定的 Goose；
  - 使用已保存模型配置的私有快照，以及独立的数据根目录；
  - 运行结束后删除快照。
- **不碰 8077 服务**：不修改它的数据、配置、Graph、授权和定时任务。如果隔离运行做不到，停下来报告，不要改用 8077 的数据目录。
- **不设预算**（用户决定 W4）。每个 Run 只设一个 900 秒的看门狗，防止测试脚本卡死。触发看门狗单独记为 `guard`，不算模型失败。

### 任务

夹具 Graph 和输入都用合成的公开数据，不接外部业务 Plugin。

| 任务 | 结构 | 测什么 |
| --- | --- | --- |
| T1 无工具 | 单个 AgentNode。提示词里直接给出固定输入（例如 30 个整数），要求通过 `final_result` 返回可以精确校验的结果（例如总和和最大的 5 个数） | 模型本身的波动 |
| T2 工具型 | AgentNode 后接一个确定性的校验 Op 节点。AgentNode 用授权的文件工具读取一个固定的输入目录（例如 10 个小文本文件），按规则统计，写出结果文件、读回，再提交 `final_result`；校验 Op 精确检查结果 | 工具调用和多节点调度的波动 |

- 每个任务的判定都必须是确定性的：通过或不通过。这作为任务质量的替代信号，也是 P4 评测任务集的第一批样本。
- 每个任务**串行**运行 **30 次**，同一时间只跑一个 Run，避免并发干扰耗时数据。记录每次的开始时间。

### 每个 Run 采集的指标

数据来源：Run 状态、节点 evidence 里的 `usage`（`goose_acp.rs` 里的 `evidence["usage"]`）、`notifications`，以及内核历史。

- **结局**：phase、outcome、reason；校验是否通过；
- **时间**：
  - Run 从创建到结算的墙钟时间；
  - 每个节点的 `elapsed_ms`；
  - 首 token 时间；
- **模型**：
  - 请求次数；
  - 输入、输出、缓存读写和总 token；
  - `cost_micros`（如果有上报）；
  - 压缩次数；
- **工具**：
  - 按工具统计调用次数和失败次数（从工具调用更新通知的状态判断）；
  - 如果能拿到，记录每次调用的耗时；
- **内核**：
  - 历史记录条数；
  - 按原因码统计的被拒提交、版本冲突。

**拿不到的指标同样重要。** 比如工具调用没有时间戳、拿不到某种 token，都要明确列出来，作为 P2 记录适配器的输入。

### 统计

对每个任务的每个指标，计算：

- n、均值、标准差、变异系数；
- 中位数、p10、p90、最小值、最大值；
- 漂移：指标和运行序号之间的 Spearman 相关，看是否随时间系统性变化。

对通过率，计算 Wilson 95% 区间。

计算**最小可检测差异**：两组对比，α = 0.05，检验力 0.8，每组 n = 10、30、100 时，能检测出的最小相对差异。

- 连续指标：用正态近似 `MDE ≈ 2.8 · sd · √(2/n)`，再除以均值；
- 通过率：用两比例检验。

### 产物

`experiments/harness-hub/p0/` 下：

- 运行脚本、分析脚本；
- `fixtures/`：Graph、输入、校验器；
- `runs.jsonl`：每个 Run 一行指标，**不含模型生成的文本**；
- `summary.json`；
- `report.md`，内容包括：
  - 环境身份：Host 和 Goose 的 SHA-256、模型标识；
  - 统计表；
  - 最小可检测差异表；
  - G0 结论；
  - 拿不到的指标清单；
  - 对 P6 样本量的建议。

### G0 判断

暂定目标：**每组 30 次时，token 和墙钟时间能检测出不超过 20% 的相对差异**。报告如实给出数字和结论；达不到也照实写，由审查方和用户决定后续怎么调整。

### 停止条件

- 超过 20% 的 Run 出现 Provider 或传输错误：停下来，报告错误分布；
- 出现任何对 8077 服务数据的写入：立即停止并报告。

## §P1 内核变更：时间、因果、配置、只读读取

**状态（2026-10-20）：已实现，两轮独立审查通过后（`e172e05`），又按第一性原理做了简化：删除全局序号和内核层的因果引用。简化版审查通过，新的冻结基点 C1 为 `9a5fa57`。** 下面是原任务书，第 2、3 项已被简化取代，见 [P1 验证与审查](../experiments/harness-hub/p1/verification.md)。

### 目的

让内核记录后续分析需要、但现在没有记录的事实。**内核只记录，不新增任何裁决规则，也不根据这些字段做判断。**

这是 `0859373` 之后第一次改 `anchor-kernel`。审查通过后，以 P1 的提交作为新的冻结基点（C1）。

### 不变量

- 现有的所有裁决结果不变：已有的内核测试和 workspace 测试全部通过，业务断言不放宽。
- 不新增 `Reason`、`Phase`、`Waiter`、`Action` 或新的 Store 种类；不新增第二个写入口，`Kernel::submit` 仍是唯一的改变入口。
- 内核代码里没有任何基于时间、配置摘要或因果引用的分支判断。
- Anchor 还没上生产：新字段一律可选，旧记录读出来是"未记录"，**不做迁移，也不拒绝旧记录**。分析侧把"未记录"当作"不适用"。

### 改动

1. **Clock 端口**
   - 新增 `Clock` trait，返回 Unix 纪元以来的 UTC 毫秒数；
   - 构造方式和 `with_probe` 一样提供 `with_clock`，默认使用系统时钟，所以现有的构造调用不用改；
   - `submit` 在持有写锁时取一次时间，写进 Stamp 的新字段（例如 `at`）；
   - 内核不保证时间单调：顺序以 `seq` 为准，时间只是记录。
2. **因果引用**
   - `Submission` 增加可选字段，引用引发这次提交的那条记录，形式为"资源 id + seq"；
   - 内核不校验它，原样写入历史。
3. **每次提交的配置摘要**
   - 删除全局的 `knobs`（`kernel.rs:52`、`:64`、`:79` 的 `set_knobs`；生产代码里没有调用，只有 `tests/constitution.rs:534` 在用）；
   - 改为每次提交由宿主提供一个可选的配置摘要，写进 Stamp，和 principal、cost 一样是宿主盖章的内容；
   - 具体是改 `submit` 的参数，还是把三项合成一个宿主盖章结构，由你根据调用点决定。约束是：仍然只有一个入口。
   - 在 P2 之前，Host 一律传"未提供"。
4. **资源创建也要可查**
   - 现在 `Kernel::create` 只写 `resource.json`，不写历史，所以 Run 是什么时候、用什么配置创建的查不到；
   - 要求：创建时间和配置摘要必须能从持久事实里得到；之后的每次提交都不能把它们弄丢，包括 Validator 生成新状态的时候；任何规则都不读取它们；
   - 可以写一条创建记录进历史，也可以作为资源上由内核维护的字段，由你选择，交回时说明理由，以及对探针重建、历史读取的影响。
5. **测量点**
   - Point 加上时间和配置摘要，用来替代 `knobs`；
   - 同步修改 Host 的探针重建，见 `kernel_probe.rs:95`。
6. **只读历史读取**
   - `FileStore` 增加只读访问：列出资源，按资源读取历史；
   - 不加锁，不创建任何文件或目录，不写入；
   - 跳过正在删除的资源和锁目录；
   - 只返回以换行结尾的完整记录，正在追加的半行不返回也不报错。
   - 中枢以后只通过它读取数据，不自己解析目录结构。

### 测试

- **新增内核测试**：
  - 固定时钟下，时间和 `seq` 正确写入；
  - 因果引用和配置摘要原样进入历史和测量点；
  - 创建事实可以查到，并且在多次提交、包括 Validator 改写状态之后仍然存在；
  - 旧格式的记录，也就是没有新字段的，能正常读出为"未记录"；
  - 只读读取在另一个写入者追加半行时只返回完整记录，并且不在目录里产生任何新文件；
  - 同一组提交序列在改动前后得到完全相同的裁决序列。
- **允许改动的断言**：`tests/constitution.rs:534` 从全局 knobs 改为每次提交的配置摘要。其他断言改动必须逐条列出理由。

### 门槛

- `anchor-kernel` 测试、workspace 测试；
- 严格 Clippy、fmt、围栏；
- Web 测试和构建：只有 API 投影变化时才需要；
- **完整固定 Goose 回归**，因为改动影响所有 Run 路径。

### 文档

- 更新 [总体架构](harness-data-hub-architecture.md) 第 5.1 节，写入实际的字段名、选择和提交号；
- 在 [迁移最终说明](anchor-runtime-migration-overview.md) 里记录新的冻结基点。

### 实验 1：修复三处工具接口缺陷（2026-10-21，已完成，采纳）

方案和结果见 [实验 1](../experiments/harness-hub/p6/experiment-1.md)。方案在运行前写定，判定规则没有在看到结果后修改。

- **准备**：
  - 配置清单增加 `host_sha256` 和 `tools_sha256`（提交 `1af26b1`），让只在 Harness 上不同的两组能被中枢分开；

  - 评测运行器增加 `experiment.py`：两组交替运行，先跑哪组按"轮次加任务序号"的奇偶交替。

  - `anchor_read`、`anchor_edit` 接受 `/workspace/<path>`；
  - 两个工具的错误信息报自己的名字和用法；
  - `project` 只在可用时公开。
- **结果**：10 个任务，每组 100 次。
  - 工具失败率从 6.1% 降到 0.8%（p < 0.0001），三处缺陷造成的失败全部消失；
  - 质量没有下降，全对的 Run：A 93/100，B 97/100；
  - Agent 用时 0.98、token 0.93，没有变差，但也不显著。

下一步候选（按价值排序）：

1. **把"提出变体"交给策略插件**（第 7.2 节 `Policy`）。从体检报告的发现自动生成候选变体，由人批准后，用 `experiment.py` 运行、用 `contrast` 判定。
2. **P5**：只读 MCP 接口和流程挖掘。MCP 接口已在 §P7 实现，流程挖掘的第一步（路线）也在 `signals` 里。
3. **调用中途中断会丢事实**：fleet 超时时真实发生过。可以考虑在调用过程中分段写入，或者在恢复时补记。

## §P7 在数据中枢上的 RSI

### 目的

旧的 RSI Graph（[RSI](rsi.md)）让 Agent 按领域分工，逐个读原始证据。这样读取量随 Run、Graph、Plugin 的数量线性增长，异构数据会分散注意力，结论也局限在已有的 Graph 和代码里。

P7 改成两部分分工：

- 中枢做确定性的、量级为 O(N) 的工作，把它压成一张有界的信号表；
- Agent 只在信号上花 O(k) 的注意力，沿信号引用的证据经 MCP 下钻，再提出不受既有结构限制的改进。

内核不改，C1（`9a5fa57`）不变。

### 已实现（2026-10-21）

- **`signals` 分析器**（`rust/anchor-hub/src/analyzers/signals.rs`），纯 L3，经 L2 读数据：
  - 合并体检和停滞的发现：按类型、位置和 detail 形态合并；同一工具的不同失败类别分开，一个节点的一百个同类空档合成一条；
  - 每条信号带这些字段：
    - 稳定 id：类型、位置和 detail 形态的摘要。下一轮可以据此判断它是否消失；
    - 权重；
    - Harness 空间坐标：配置、Graph、节点、模型、工具摘要、Host 摘要；
    - 有界的证据，最多 5 条，另给总数；
  - **前沿**：每个评分任务上，按"这个 Run 里被观察的配置集合"把 Run 分成 Harness，至少 3 个 Run 才参与。一个 Harness 被另一个支配的条件：
    - 平均分不低，token 和 Agent 用时的均值都不高；
    - 并且分数高出 0.05 以上，或者 token、用时之一显著更低（Mann-Whitney 检验，p < 0.05）。

    没被支配的 Harness 组成前沿；被支配的成为 `dominated_harness`，排在最前；
  - **范例**（正向离群）：同一个评分任务里通过的 Run，或者没评分时同一个 Graph 里，同一节点至少 5 个完成的调用。两种范例：
    - `frugal_route`：token 不到中位数一半的调用；
    - `rare_route`：只有一个调用走过的工具路线，前提是其余调用多数走同一条，并且它的成本不高于中位数；
  - 排序：先质量，再浪费，再慢，最后是记录完整性。信号和范例各保留 `limit` 条，默认 20；放不下的按类型计入 `omitted`。
- **`Invocation::route`**（L2）：按记录顺序列出工具，连续调用同一个工具时合并计数。
- **只读 MCP 接口** `anchor-hub mcp PATH...`（`rust/anchor-hub/src/mcp.rs`）：
  - 在 stdio 上按行收发 JSON-RPC 2.0，没有新增依赖，依赖围栏不变；
  - 支持的方法：`initialize`、`ping`、`tools/list`、`tools/call`；
  - 工具：

    | 工具 | 作用 |
    | --- | --- |
    | `signals` | 信号表 |
    | `report` | 单个分析器的报告：health、stall 或 contrast，发现可以按代码、主题筛选并分页 |
    | `invocations` | 调用列表：按 Run、节点、配置前缀、结局、用过的工具、任务筛选，每个调用一行摘要和路线 |
    | `invocation` | 一个调用的全部生命周期、轮次、工具调用、空档和证据 |
    | `configurations` | 配置清单 |
    | `records` | 按证据键读事实行 |

  - 所有工具都标为只读，列表分页并给出 `total`，单个调用的明细也有上限；
  - 每次调用前增量刷新，Run 跑的过程中也能读；
  - 出错时以 `isError` 回答，不退出。

  Plugin 用 `{"command": ".../anchor-hub", "args": ["mcp", "<数据目录>"]}` 接入（见 `anchor-graph-host/src/mcp.rs` 的 stdio 支持）。
- **CLI**：`anchor-hub signals [--json] [--limit N] PATH...`。
- **测试**：`tests/hub.rs` 新增 2 个，覆盖前沿和支配、范例、id 稳定、截断计数、MCP 的握手、分页、筛选、下钻、增量刷新、错误回答，并确认不泄漏业务内容。hub 共 17 个测试加 3 个围栏测试，全部通过，clippy 无告警。
- **真实数据**（实验 1，`.local/harness-hub-p6/exp1`，390 MB，约 1000 个数据根）：
  - `signals` 0.5 秒（debug 构建），14 条信号；
  - MCP 默认的 `signals` 回答约 20 KB，`limit: 3` 时约 12 KB。作为对比，同一批数据的事实行有 2 MB，原始数据 390 MB；
  - 结果和实验 1 的结论一致：
    - 每个任务的前沿上 A、B 两组都在，单个任务每组 10 次时用时和 token 差异不显著；
    - 信号里有：`anchor_run`、`anchor_edit` 的 `invalid_arguments`，`anchor_read` 的 `not_authorized`，失败后换参数形状再成功的 `call_corrected`，以及一次 `interrupted`；
    - 范例有两条：repair 任务里一个只用 35832 token 的调用（中位数 86979），和 schedule 任务里一条独有的路线。

### 已知边界

- 前沿只看平均分、token 和 Agent 用时这三个维度，不看方差和尾部；`MIN_RUNS = 3` 时，判断支配主要依靠分数差异。
- 合并粒度包含 detail 形态，不同失败类别分开。`call_corrected` 现在计入同形状换值后成功的调用，并分开报告换形状和同形状两种；A 组上 `anchor_edit` 30 次恢复里 29 次、`anchor_read` 12 次全部是同形状，即"参数结构对、值错"。
- 工具调用新记 `path_class`（`relative`、`workspace`、`absolute`、`parent`），只记路径属于哪一族，不记路径本身；体检按工具和路径类别统计调用和失败。失败类别保持原口径不变（宿主测试固定），以便跨实验比较；"值写错了地方"由路径类别区分。实验 1 的旧记录没有这个字段，读出来是未记录，所以 read/workspace 在 A 组数据上仍然只能靠工具代码解释。
- 证据键里带完整的数据根路径，是信号表体积的主要来源，以后可以改成数据根的短 id。
