# 深度调研任务书：多 Agent 编排 + 工作区架构

> **用途**：把这份文档原样交给执行深度调研的 agent（或人）。
> **目标**：产出一份可支撑架构决策的证据报告，而不是技术选型广告。
> **交付物**：见 §7。**判断基准**：见 §3（不可动摇的不变量）。

## 0. 给执行调研者的指令

1. 先读 §1–§3，理解被调研系统（Anchor）的现状与不变量。**不要跳过 §3**——所有结论都要用它评判。
2. 按 §4 的 RQ1–RQ10 逐条调研。每条都要给出**证据**（见 §9），而不是观点。

4. 明确区分三类结论：**Adopt（直接采用）/ Adapt（借鉴改造）/ Avoid（明确不用）**。
5. 遇到"行业共识"时，必须给出**至少两个独立来源**。
6. 如果发现证据推翻了本任务书的假设，写进 §10，不要迎合。

## 1. 背景：被调研系统 Anchor

### 1.1 它是什么

Anchor 是一个"长周期多 Agent 协作图"的运行时内核 + Web 控制台。核心抽象：

```
Graph（不可变版本） → Run（pin 到某个版本） → NodeRun → 事件/产物/决策/验证/操作账本
```

- **图**：声明式、类型化、校验后不可变的执行计划（12 种节点类型：agent / tool / router / parallel / join / verifier / approval / wait_for_event / human_task / artifact / loop / subgraph）。
- **执行**：worker 领取 ready 节点 → 解析**声明式输入快照**（仅由入边 `input_mapping` 决定）→ 调用能力（模型/工具/验证器）→ 原子提交结果。
- **节点间通信**：不可变值，通过边映射传递。**没有共享可变状态。**
- **副作用**：操作账本 + 审批门 + 未知结果人工对账。
- **恢复**：事件日志 + lease + 快照重放。

### 1.2 现状能力与缺口

| 有 | 没有 |
|---|---|
| 事件溯源、幂等、操作账本 | 持久共享工作区 |
| lease 恢复、supervisor、watchdog | 可写文件系统 / 代码执行 |
| 确定性验证门、审批/等待 | 共享可变缓存区 |
| 不可变产物（内容寻址 blob） | 工作区版本（git） |
| 图版本固定、输入快照可哈希 | 并发编辑控制 |
| 每次工具调用的**临时**沙箱（bubblewrap，无网络、只读根） | 容器/microVM 级隔离、受控联网 |
| 存储预算 + 滚动清理（含产物 GC） | 跨平面（控制面+内容面）的统一审计 |

### 1.3 目标状态（待验证）

> 让 Anchor 同时支持**知识工作**（研究/写作/数据）和**代码开发**（改仓库/跑测试），
> 且**两者都保持可复现、可审计、可恢复**。

拟议方向（**需要被调研验证或推翻**）：

```
双平面架构
  控制面（已有）：事件溯源、确定性、可重放
  内容面（新增）：版本化可变树（工作区/仓库）
  边界（新增）：content_ref = artifact://<digest> | workspace://<revision>[/<path>]
```

## 2. 问题陈述

**核心问题**：

> 如何在引入"持久、可变、可执行的工作区（内容面）"的同时，**不破坏** Anchor 现有的
> 可复现性、可审计性和可恢复性？业界是否已有可复用的参考架构？

拆解为三个子问题：

1. **控制面**：持久化 agent 编排的成熟模式是什么？Anchor 自研的语义是否等价或更优？该借鉴什么？
2. **内容面**：生产级编码 agent 如何管理工作区、并发、依赖、网络与密钥？有哪些成熟件可用？
3. **边界**：有没有系统把两者统一到**端到端可审计/可复现**？如果没有，最接近的参考设计是什么？

---

## 3. 不可动摇的不变量（评判基准）

调研结论必须逐条对照这张表。**任何方案如果破坏其中一条，必须显式标注代价。**

| # | 不变量 | 含义 |
|---|---|---|
| I1 | **图不可变** | 发布后的图定义不可修改；run pin 到具体版本 |
| I2 | **Canonical State 是恢复源** | 事件日志是"发生过什么"的唯一真相；上下文/记忆是带溯源与保留规则的投影 |
| I3 | **副作用有账本** | 每个副作用有 operation id、幂等语义、授权、审计记录 |
| I4 | **完成需验证** | 完成由确定性或领域验证器判定，不是模型的自然语言声明 |
| I5 | **长等待不占 worker** | 等待从持久状态恢复；UI 断连不终止工作 |
| I6 | **不因猜测的数值预算中断健康 agent** | 安全来自自适应看门狗（检测停滞、断连、重复副作用、无进展循环） |
| I7 | **供应商中立** | 不依赖特定模型厂商、工作流引擎、向量库或可观测后端 |
| I8 | **声明式输入** | 节点只看被声明的输入；不做"全量可见"的隐式共享 |
| I9 | **每个 run 可复现** | 给定图版本 + 输入 + 运行期版本，能重放出同样的决策路径 |

> 特别关注：**I2 与内容面的关系**。若工作区成为第二真相来源，I2 需要重新表述吗？
> 如果答案是"需要"，请给出精确的修订措辞（这是本调研最有价值的产出之一）。

## 4. 研究问题

### RQ1 — 持久化 Agent 编排的模式
- 主流持久执行引擎（Temporal / Restate / DBOS / Inngest / Prefect / Cadence 等）的**恢复模型**分别是什么（事件历史？状态快照？数据库事务？）
- 它们如何表达**agent 特有的语义**：模型调用、工具调用、人工审批、长等待、非确定性
- 哪些是"agent 框架 + 持久引擎"的组合（如 LangGraph + checkpointer）
- **对 Anchor**：现有语义与它们的差异；哪些可以直接借鉴，哪些自研更优

### RQ2 — 内容面：编码 Agent 的工作区
- OpenHands / SWE-agent / Devin / OpenAI Codex（cloud）/ Claude Code / Cursor / Aider / Goose 等**如何组织工作区**（容器？VM？git worktree？每任务一份？）
- **并发**：多个 agent/会话同时改同一仓库怎么处理（分支、锁、合并、冲突升级）
- **版本化**：什么被 commit、何时 commit、如何回滚
- **依赖与缓存**：如何加速重复安装；缓存共享的安全边界

### RQ3 — 隔离与执行沙箱
- 隔离层级对比：进程 / 容器 / gVisor / Firecracker microVM / Kata / 完整 VM
- 沙箱即服务：E2B / Daytona / Modal / Fly Machines / 自建 K8s 的取舍（成本、冷启动、持久化、网络）
- **执行策略**：超时、CPU/内存上限、磁盘上限、进程数、网络白名单、DNS、出站审计
- **密钥**：如何在不把密钥交给 agent 的前提下让其调用外部服务

### RQ4 — 控制面与内容面的边界
- 是否存在**同时**做到"持久编排 + 版本化工作区 + 端到端审计"的系统或参考设计
- 内容如何被引用：内容寻址 / git SHA / 快照 ID / 事务日志；各自的**可复现性**差异
- 崩溃恢复：控制面说"完成"，但内容面缺失时如何检测与修复
- **这是本调研最关键的问题**。如果业界确实没有，请给出最接近的 3 个设计并分析差距

### RQ5 — 共享可变状态与并发
- 多 agent 共享状态的主流做法：消息传递 / 黑板 / CRDT / 事务文件系统 / 单写者 / git 分支
- 各自的**冲突处理**与**确定性**影响
- 是否有"共享缓存区"的生产实践（语义缓存、依赖缓存、检索缓存）及其一致性要求

### RQ6 — 互操作：MCP 与 A2A
- MCP 与 A2A 的**范围**：各自解决什么、不解决什么（重点：A2A 是否涉及共享状态）
- 治理与采用现状（谁在维护、哪些产品支持）
- 如何把 Anchor 的能力暴露为 MCP server；有哪些成熟实现可参考
- 是否存在其他值得关注的协议（如 AGENTS.md、OpenAI Agents 互操作、W3C 相关）

### RQ7 — 长期上下文与记忆
- 长周期 agent 的上下文管理：压缩、摘要、检索、结构化记忆
- 记忆的**冲突解决**与**保留策略**
- 向量检索在"证据可追溯"要求下的定位（是否只能做检索辅助，不能做真相来源）
- 代表实现：Letta/MemGPT、mem0、Zep、LangGraph store、OpenAI sessions 等

### RQ8 — 可观测性与审计
- 如何让 agent 的工作**可审计**：轨迹日志、决策记录、证据链
- OpenTelemetry GenAI 语义约定的现状与覆盖范围
- 事件溯源 vs 轨迹日志 vs 分布式追踪：各自的适用边界
- 是否有"agent 行为审计"的合规/监管要求（金融、医疗、政府）

### RQ9 — 可靠性与成本
- 长任务失败模式：模型超时、工具失败、沙箱崩溃、并发冲突、成本失控
- 重试语义分层（业务循环 / 节点执行 / 请求重试）的行业实践
- 人类介入的时机与形式（审批、纠偏、接管）
- 成本控制手段：token 预算、模型路由、缓存、任务分解

### RQ10 — 图式编排的对比
- LangGraph / AutoGen(AG2) / CrewAI / Microsoft Agent Framework / Google ADK / OpenAI Agents SDK / LlamaIndex Workflows / Mastra / PydanticAI / Temporal AI
- 各自：编排模型、持久性、审计能力、人机协同、生态、许可
- **哪些是"框架"、哪些是"运行时"、哪些只是"库"**——分层要清楚

## 8. 范围与边界

**包含**：开源 + 商业产品；运行时/框架/沙箱/协议/可观测；2024 年之后的主要进展。

**不包含**：
- 模型训练、微调、GPU 基础设施
- 非 agent 的纯 ETL/批处理工作流（除非其恢复模型有借鉴价值）
- 具体云厂商的锁定型方案（可作为参照，不作为主结论）

**地域/语言**：英文来源为主，中文生态（如国内 agent 平台）可作补充，但需标注成熟度。

## 9. 证据质量标准

| 等级 | 标准 |
|---|---|
| **高** | 官方文档/源码/论文 + 至少一个独立第三方验证（生产案例、事故报告、基准测试） |
| **中** | 官方文档/源码，无独立验证 |
| **低** | 博客、演讲、二手报道 |

- 每个"最佳实践"结论必须有**≥2 个独立来源**。
- 引用必须可点击、可核查。注明访问日期。
- 区分**厂商宣称**与**可验证事实**。
- 对"我们不建议 X"的结论，要说明**在什么条件下 X 反而是对的**。

## 10. 什么证据会改变我们的结论

请特别留意并明确回答：

1. 如果存在一个系统**已经**同时做到持久编排 + 版本化工作区 + 端到端审计 → 应评估直接采用而非自研，给出差距分析。
2. 如果业界主流**放弃**了"共享可变工作区"，改用消息传递 + 不可变产物 → 说明 Anchor 现有方向可能是对的，内容面需求可用别的机制满足。
3. 如果 microVM/容器沙箱的成本或延迟使其**不适合长周期任务** → 需要替代隔离方案。
4. 如果 MCP/A2A 的治理或范围**不足以承载** Anchor 的语义 → 说明需要自建协议层的程度。
5. 如果"事件溯源 + 可变内容面"在业界被证明**难以共存** → 给出 Anchor 应如何取舍的具体建议。
6. 如果法规（如欧盟 AI Act、金融审计要求）对 agent 行为审计有**强制要求** → 这会成为 I2/I3 的硬约束。

## 12. 一页速览（给执行者的最后提醒）

- 我们要的不是"哪个框架最好"，而是：**引入工作区后，如何保住可复现/可审计/可恢复。**
- 判断一切的标准是 §3 的 I1–I9。
- 最重要的未知是 RQ4：**控制面与内容面的边界**。
- 如果业界没有答案，也要如实说，并给出最接近的参考设计与差距。
- 不要为了给出"标准答案"而编造共识。
