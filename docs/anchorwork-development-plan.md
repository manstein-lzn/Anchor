# AnchorWork 系统设计与实施计划

日期：2026-11-13。状态：设计与分片计划；本文件不代表实现、授权变更或上线。

## 1. 目标与边界

**让群主只负责表达意图、讨论方案和关键决定；由常驻 Manager 主动形成需求、规范管理文档并持续协调交付，不需要群主反复催办。**

用户体验及长期职责以[组织约定](feishu-agent-organization.md)为准；本文只定义实现落点、先后关系和验收。当前实现仍以[架构](architecture.md)、[Graph 作者契约](rust-graph-authoring-contract.md)、[Plugin 契约](plugins.md)为准。计划实现后将真实契约并入对应文档，验收结论归[统一台账](pilot-development-plan.md)，本计划完成后退出活跃入口。

必须保留的边界：

- 项目管理是可安装、可替换的 Graph + 普通 Plugin 业务方案，不在 Kernel 增加项目、需求、审批、里程碑或组织角色。
- 关键变化驱动推进；Schedule 只补充期限、约定汇报、失联检查和遗漏核对。没有推送来源的外部资源可以轮询，但必须如实标明。
- 群主需要决定时可以暂停整个组织的新业务派发；取得有效决定后在原授权内继续。没有待决不代表所有故障都能自动恢复，未知效果或权限问题必须明确处理。
- 飞书云文档体系是正式业务工作台，Manager 负责维护与验证；业务计划、执行事实和渠道送达各有自己的权威来源。
- 先用总 Manager 和 Anchor 项目 Manager 验收完整链路，再复制到 SeeMine、Codex Manager；后两者的真实账号、目录与授权不猜测。

## 2. 现状与缺口

下表是本次仓库契约核对，不是本次生产探测；部署时仍须回读实际配置。

| 已有基础 | 不能推定的能力 | 本次处理 |
| --- | --- | --- |
| 常驻助手使用 `session.wait_input → Agent → session.reply`，同一 Session 串行 | 不能随意插入复杂常驻 Graph 节点；Graph ID 不等于唯一 Session | 保留获准循环，按明确组织/群绑定目标 Session；角色业务放 Plugin |
| `graph-tasks` 支持普通异步任务、结果回原 Session、计划与共享结果 | 受委派 Graph 禁用 Host Op 和递归委派，不能直接运行已有常驻项目 Manager | 增补获准常驻助手之间的工作交接，保留普通委派限制 |
| Codex Bridge 可观察原生通知及 `native_events` 游标 | 事件可读不等于自动持久送达 Manager；环形缓冲与 epoch 不能当永久事件历史 | 接入有作用域的关键变化观察，明确断线、缺口和停止语义 |
| 飞书群对话、通用 CLI 和受限 peer 协作 | 一个人类根的有向 peer 对限流不是长期任务交接；私聊通知授权不覆盖群 | 任务关系走可信内部交接；群中展示真实摘要，不重复派工 |
| 飞书 Wiki/Base 可由获准 Bot 工具操作 | 应用 scope 不等于资源 ACL；自由文档文本不证明具体人已决定 | 建立业务资料结构、写入核对和可信决定来源 |
| Anchor 项目 Manager 的 `project_*` 与 Codex 目录租约 | 总 Manager 没有因此获得项目目录，Codex 独立配置不归 Anchor | 继续复用；长任务异步委派，保持群对话可响应 |

依据：[常驻循环](rust-graph-authoring-contract.md#host-op-与常驻助手)、[任务授权](rust-graph-authoring-contract.md#按需-graph-任务授权)、[任务结果](architecture.md#按需-graph-任务与结果输入)、[飞书渠道](feishu-assistant.md)、[Codex 接入](codex-project-manager.md)。

## 3. 交付组成与责任

```text
群主 <--> 飞书群 / Wiki / 多维表格
                    |
          总 Manager 常驻 Graph
                    | 获准工作交接 / 结果回流
          项目 Manager 常驻 Graph × 项目
                    |
          直接项目工具 / 普通任务 Graph / Codex
                    | 结果、阻塞、待答及必要进展
                    +----------> 原责任 Manager

project-management：业务 Skill、模板、完整性检查
feishu / graph-tasks / codex：复用已有能力及必要通用扩展
Host：可信接纳、Session 排队、授权、观察生命周期和投递
Kernel / Runner / Goose：沿用原有执行与事实语义
```

### 3.1 Graph 与管理 Plugin

复用并改造现有 `examples/graphs/feishu-organization-manager.json`、`feishu-codex-project-manager.json`，不为每个项目复制一套专有程序。保留已有 Bot、Session、笔记和项目现场，不拿模板直接覆盖运行实例。常驻循环负责接收和处理输入；独立任务按真实执行边界使用普通 Graph，不先增加固定十步业务流程。

拟新增普通 `plugins/project-management/`：

```text
plugin.json
skills/organization-manager/SKILL.md
skills/project-manager/SKILL.md
templates/                       # 项目首页、方案、三张业务表、验收说明
```

它取代并删除两个 Manager 模板中重复的业务长指令和临时表格约定。角色 Skill 定义需求提炼、方案讨论、工作分解、决策升级、文档维护与交付收尾；模板定义最小资料结构。飞书身份和渠道规则仍引用 `feishu` Skill，项目执行仍引用 `codex` 等能力，不在管理包再复制一份。

若现有工具不能完成必要的完整性检查，再增加小型 Rust 业务检查工具，只校验记录结构、关联证据和未处理事项，不包装第二套飞书 CRUD、Codex API 或任务运行时。普通 MCP 不能隐式调用另一个 Plugin 的宿主能力；需要可信现场时由既有授权入口提供引用或观察，不能信任模型自报的“已接纳”。Skill 和自检不是权限围栏，也不宣称仅凭提示词能杜绝模型遗漏。

### 3.2 绑定与配置

复用 Graph/渠道、Plugin 配置、项目目录授权和飞书资源授权的现有事实；项目表只引用这些身份，不成为第二套授权注册表。部署准备时绑定：

- 组织群、获准人类决定者，以及总 Manager 的确切实例与 Session 作用域。
- 每个项目 Manager 的实例、业务项目 ID、Wiki 入口与表格资源；实际目录沿用 Host 的项目授权。
- 可交接的对象和操作范围、观察源、结果回流与群通知目标；按节点授权，不因组织层级继承权限。
- 管理业务参数：工作并发、提醒窗口、讨论/汇报节奏及获准工作范围；不凭本规划新增默认累计 token/金额限制。

配置承载优先复用当前模型；只有现有模型确实表达不了的新授权或观察绑定才增加字段，并明确版本和迁移。普通 Plugin 的 owner 默认连接配置不能被误用成每个项目一份独立身份；凭据不进入项目表、Graph 包或 Skill。

## 4. 最小业务资料与事实归属

只用既定的三张表和少量文档，不新增项目管理数据库：

| 记录 | 最小内容 | 权威与维护 |
| --- | --- | --- |
| 项目表 | 稳定 ID、长期职责、当前目标、责任 Manager、里程碑、健康度、Wiki 入口 | 业务目标与负责人；总 Manager 维护组织总览，项目 Manager 维护本项目 |
| 任务表 | 稳定 ID、项目/父任务、类型、范围与验收标准、优先级、责任人、依赖、业务状态、下一步、计划版本、执行与证据引用 | 业务承诺；Run/thread 状态是观察，不由手改表格覆盖 |
| 问题表 | 稳定 ID、阻塞/风险/待决类型、影响范围、选项和建议、决定者、真实期限、决定来源/版本、结论及应用结果 | 决定结论只保留一份；Wiki 存背景、方案和来源链接 |
| 项目 Wiki | 项目入口、需求/方案、当前确认版本、验收与交付说明 | 详细业务说明；技术契约需随代码版本维护时引用仓库，不复制冲突正文 |

业务任务初始状态建议为待澄清、待办、进行中、受阻、待验收、完成、取消；具体模板可调整，不加入 Kernel 枚举。暂停范围、待决项和依赖单独引用，不把所有“受阻”当成人类决定。已执行成功但文档未交付的任务保留相应未收尾事项，不能回滚真实执行结果。

共享资料的写入者按现有 ACL 确定；总 Manager 管公共入口，项目 Manager 管自己的资料。共享表需序列化写入；若无法取得可靠应用级项目隔离，就按项目分 Base 再汇总，不以筛选视图作权限边界。最终资源方案在真实租户验证后绑定，不先授予全部 Bot 全局写权限。

## 5. 连续推进与人类决定

### 5.1 生命周期

```text
想法/反馈 → 主动澄清与调研 → 讨论方案 → 获准计划
                                              |
                       派工 → 结果 → 核查 → 下一步
                                  |
                         真正需人决定的事项
                                  |
                    明确等待范围 → 有效决定 → 继续
                                              |
                     验收与文档交付 → 收尾与下一阶段建议
```

讨论和建议不等于实施授权；已经批准的范围不在每个步骤反复请示。阶段目标完成后结束相关执行和无用观察，Manager 的长期职责保留：推进既有承诺，或带着证据准备下一阶段讨论。没有有价值的工作时安静等待，不生成虚假任务保持活跃。

### 5.2 每轮必须有真实去向

对本轮影响的未完成工作，Manager 核对以下一种真实安排：

1. 已在当前获准工作中推进，或下一项已被执行端接纳。
2. 已可靠交接，由明确责任人处理，并能收到结果或异常。
3. 等待具体依赖、有效决定、外部结果或必要时间条件，并有可验证的恢复入口。
4. 有依据地完成、取消、暂停或上报无法自动处理的故障。

单纯留下“稍后继续”的文字不满足约定。判断所引用任务、接纳事实和等待对象是否存在可以确定性核查；目标理解与方案质量仍需 Agent 判断及真实业务验收，不能把结构校验当作智能正确性保证。缺失后续安排应成为明确未处理工作，不能在普通完成报告中隐藏。

计划分两个层面实现保障：Host 保证已经接受的交接/输入不会因 Agent 回复结束而失去记录，业务包核对待办是否真正有人推进。为主动检查而发起的同事实自唤醒不得无限循环；重复输入回读原记录，无变化不重复派工，不新增另一套 Agent loop。若现有 Graph/工具不能可靠承载业务检查，先交回具体缺口，不在 Kernel 添加 PM 专用完成门禁。

### 5.3 决定与暂停

群里或约定文档区域都可以作决定；需关联决定 ID、当前方案版本、可信人类身份和原始来源。Bot 转述、文档最后编辑人及模型提取结果本身不能证明授权。不能可靠归因的文档结论只请求一次定向确认，不默认忽略，也不自动实施。跨 Bot 的用户标识按原渠道/应用身份核对，不能直接比较不同应用内的裸 ID。

决定记录区分待决、已决、已应用和取消；已决不意味着外部操作已成功。范围冲突或过期决定停止受影响操作，核对当前现场后再处理。组织级待决停止所有相关新业务派发，保留结果收集、必要记录和解释；不擅自杀掉运行中的命令。人主动暂停还停止催办；人决定后若另有主动暂停，不能由一条结果自动解除。

## 6. 通用宿主能力补充

本节为拟议契约，不是现有工具名、manifest 字段或 API。先做小型垂直验证，再确定最少字段；不引入通用事件总线、独立任务数据库或无限插件钩子。

### 6.1 常驻助手的可靠工作交接

在既有 `graph-tasks` / 应用服务 / Session 输入链上扩展，不绕过普通 Graph 委派的安全限制：

- 发送端只能选择操作员批准的目标引用；Host 解析具体实例和组织/会话作用域，不让模型随意指定 owner、Session 或跨群收件人。同图多个渠道会话不混为一个经理。
- 请求有稳定身份、原始来源、业务引用和受限上下文；持久接纳后才返回成功，重试相同请求读回原结果。传输请求不是第二份业务任务状态。
- 接收者用自身已经批准的能力处理受托范围；发送者不能通过高权限经理取得自己未被允许发起的操作，需同时满足交接范围与接收端授权。
- 完成、受阻、待答分别回原责任会话，普通结果不被当作新的人类命令；后台输入排队而非打断当前人类讨论。保持现有用户输入优先与同 Session 串行规则。
- 重用 Session 的待处理、领取和处理事实及现有任务关联；发送端崩溃或回应丢失后可按相同身份核对。尚未持久接纳的不报“已派工”，停止的 Manager 不因新工作自动复活。

替代路径：长期工作不再靠无限 peer @ 或要求用户转述，也不重新 run 已活动的 Manager；保留 peer 渠道的原防循环规则，群摘要只展示同一交接的事实。

### 6.2 外部执行观察接入

先接 Codex 的完成、失败、待答/待批准和连接异常；不把 token、日志和每个工具片段都变成新模型回合。已有 Graph Task 完成直接走既有结果输入，不再旁路监听一次。

推荐采用“获准观察绑定 + Host 管理生命周期 + Plugin/Bridge 提供源协议”的最小契约：绑定指向已接纳工作与原责任 Session，包含来源引用和明确作用域；宿主只处理输入接纳与授权，Codex 适配解释其协议。不能开放任意外部调用者向任意 Session 注入事件。具体使用有界长轮询还是事件流，先核对当前 Bridge/SDK 支持，再在同一契约下确定，不对现有 MCP 通知作未验证承诺。

普通 stdio Plugin 在调用结束后不被假定仍有监听进程；观察生命周期由宿主已管理任务承担并支持撤销、重启核对、退避和结束清理。只持久化必要绑定/游标与已接纳身份，沿现有事实路径归属，不建立第二套 Codex 日志。Bridge epoch 变化、缓冲 gap 或断线触发现场核对；不把未知写操作当失败后自动重放，也不把观察成功当任务成功。

该通用能力取代 Codex 周期唤醒模型只为读取 `inspect` 的主路径；已有巡检保留为有期限的失联/遗漏兜底。第三方来源缺少可靠事件时，只允许有界查询并标明覆盖限制。观察工具和权限如需新增 manifest/Graph 字段，必须同步清单白名单、授权摘要、披露与验收，不伪造目前可安装的配置。

### 6.3 群通知与业务效果

扩展原结果发送的会话绑定，使获准后台结果能发到原组织群；机器人、群和逻辑投递身份由 Host 确定。复用网关账本，confirmed 不重发，unknown 先核查；`session.reply`、显式发送和 CLI 不各发一份相同结果。

飞书 CLI 仍是业务能力，不因新增管理 Plugin 自动获得强制流程约束。项目规范检查不能阻止一个拥有全部原始工具权限的 Agent 绕过模板；权限边界靠工具授权，业务合规靠明确交付检查与验收。若要硬性限制某类操作，应在其原有授权入口收窄，而不是另加一个可被绕过的 PM 工具宣称安全。

## 7. 文档写入与外部效果

采用“读取当前记录 → 按稳定 ID 定位 → 修改负责部分 → 回读核对”的工作约定；保留来源、适用版本和已被替代关系。群主不用重复填写记录。资料内容不当作新工具指令，外部文本不能改变宿主授权。

飞书写入与 Anchor 派工不是一个原子事务。不承诺跨系统 exactly-once：派工前先有业务引用；派工成功但回填失败时，按原接纳身份补齐引用，不再派一次；文档写入超时先查现场，不能盲目新建同名对象。冲突无法安全合并时保留待处理项，提示明确受影响工作，真实已完成执行不被抹掉。

第一条试运行优先使用群内可信决定；文档指定区域的决定输入仍必须交付，在无法直接取得可信来源时提供群内一次确认路径。事件订阅或轮询只是发现变化，不等于确认决定人。群主只看项目首页就能找到当前计划、进度、问题和证据，链接与实际访问范围另行验收。

## 8. 实施顺序与退出条件

以下均为待实施；每片先跑相关确定性用例，再做必要真实验收，不要求重复全量或用更多测试代替业务交付。

主要修改落点优先复用以下现有模块；此表是导航，不是预先要求拆出新 crate 或同时修改所有文件：

| 责任 | 既有落点 |
| --- | --- |
| 业务角色与资料模板 | `examples/graphs/feishu-organization-manager.json`、`examples/graphs/feishu-codex-project-manager.json`；拟新增普通 `plugins/project-management/` |
| 获准交接与任务来源 | `rust/anchor-runner-host/src/application/graph_tasks.rs` 及其目录、`task_delegation.rs`、`graph_task_tools.rs`；必要策略沿现有 `GraphTaskPolicy` 保存链路 |
| 可靠输入与结果关联 | `rust/anchor-platform-session/src/channel/assistant/task_inputs.rs`、Host 的 `application/task_results.rs`、`application/run_access`；依赖方向不反转 |
| Codex 关键变化 | `rust/anchor-codex-bridge/src/client.rs` 及既有状态投影、Host 当前 Plugin/任务装配边界；源协议不进入 Kernel |
| 原群通知与工具上下文 | `rust/anchor-runner-host/src/channel_tools/task_delivery.rs`、`anchor-feishu-gateway` 现有发送账本；身份与回执保持单一所有者 |

## 9. 必须通过的验收

1. **从想法到计划**：Manager 带建议主动澄清，不要求人先填完整需求；确认范围和标准进入正确资料。
2. **关闭周期巡检仍推进**：已接入事件的执行链可完成下一步；未接事件的外部资料查询明确列例外，不能假装全事件化。
3. **没有无主进行中事项**：每项都有实际执行/接纳引用或具体等待对象；伪造引用、只写承诺及正文“已完成”不能代替证据。
4. **决定与暂停有效**：局部/组织级范围清晰；没有答复不批准，重复/冲突/旧版本输入不乱序应用，主动暂停后不自动派工或催办。
5. **恢复不重复副作用**：重复事件、接纳确认丢失、结果处理期间用户输入及重启，都核对原事实；未知外部写不自动重放。
6. **资料是可用工作台**：只从 Wiki 入口可找到方案、任务、待决和验收；人工改动冲突、权限不足及回填失败不会被报告为完成。
7. **正常回应只有一份**：普通回复、结果通知及群协作不会重复发送或无限互相 @；无变化不刷屏。
8. **阶段完成后仍有人负责**：停掉无用观察，推进已批准后续或提出下一阶段建议；不自动扩大授权、不为了活跃造工作。
9. **可迁移、可替换**：增加一个项目不修改 Kernel/Runner；管理规则变化改普通 Plugin/配置，项目数据和已接纳工作不会因模板更新被删除或重放。

确定性验证使用小型 fixture Graph、模拟源和真实 Host/Runner/Goose ACP/工具链；真实 Provider 和真实飞书分别验。重点边界覆盖即收口，不增加第二套管理评分引擎。

## 10. 发布、未定事项与明确不做

发布顺序：保存现状证据 → 隔离 fixture → 明确资源授权的真实试运行 → 原 Manager 的受控更新 → 扩展项目。保留原 Session、资料、历史与未结算工作；当前 Turn 不热扩权。回退停止新增观察与派发，沿原生命周期处理运行任务，不以删除事件或文档回滚副作用。

实施前只需核对现场，不要求群主重新作已确认的产品决定：

- 真实 Wiki/Base 的访问范围、应用写隔离、共享表串行写方式；若需要额外权限才提交具体授权请求。
- 当前 Bridge 支持的事件获取方式及受管观察绑定的最小形状；已有公共入口优先，不新增泛化框架。
- 决定输入是否有足够的操作人和内容版本证据；不足时采用群内一次确认，不悄悄降低标准。
- SeeMine/Codex Manager 的应用、项目目录和凭据绑定，以及获准提醒时间、并发容量；缺少资料时不猜。

不做：新的 Agent loop、项目数据库、审批引擎、通用事件总线或消息平台；不照搬 Paperclip/Linear 运行时；不重写 Codex 本地配置；不向所有 Bot 开放全部仓库和飞书资源；不把方案研究、测试通过或平台回执写成已经生产验收。
