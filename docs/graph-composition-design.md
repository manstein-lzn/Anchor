状态：已接入主线并完成隔离真实模型、真实后端浏览器及自动回归验收，已部署；后续周报实测已收到企业微信平台 ACK，验证记录以开发台账 A27 为准。

用户已确认保留两种组合能力：同一次 Run 内展开子图，以及通过节点启动独立 Graph Run。设计以 Graph、Node、Edge 组织工作；周报通知只是首个验证场景，不为它建立独立的业务联动配置系统。本文延续 `product-architecture.md` 的对象边界；当前实现见 `architecture.md`，推进与验收见 `pilot-development-plan.md`。

## 用户应当看懂什么

无需阅读脚本，用户应能从画布直接判断：

1. 这里引用了哪个流程，它在当前 Run 内执行还是另起 Run？
2. 下一步会立即继续，还是等待被调用流程完成？
3. 给目标传了什么，完成后能拿到什么？
4. 这次运行实际启动了谁，失败发生在哪里，停止操作会影响谁？

定义关系和运行关系是两层事实：同一个调用节点可能每周执行一次，也可能在图内循环多次。Graph A 引用 Graph B 不能代替 A 的某一次 Run、某个节点轮次与 B 的具体 Run 的关联。

## 实施前起点（历史基线）

- 内联模块来自同一文件的 `graphs` 声明，展开为带前缀的节点，属于同一 Run；它并非已支持引用任意已安装独立 Graph 文件。不能把两种来源冒充同一种实现。
- 前端 `WorkflowCanvas` 已区分智能体、命令、子图。子图在编辑画布显示一个节点，执行视图读取展开后的定义。
- 添加节点面板目前主要支持 Agent，Op 定义只能只读查看或通过 JSON 修改；新增调用操作必须提供可编辑的表单。
- Op 目前是沙箱命令，以退出码判定完成。新增内置 Graph 调用将扩展这条契约，不能靠识别任意 Shell 文本伪装成结构化调用。
- `Scheduler.trigger` 可启动普通 Run，但以 Graph 为单位拒绝重复执行，没有调用幂等契约；运行 ID、运行中索引、恢复读取定义的方式都需要核查。
- AgentNode 的 Harness 负责模型步骤记录；Graph 调用属于 Graph 调度层，不应放入 PydanticAI 模型循环。
- 用户通道已允许不同会话同图并发，同会话新输入会打断旧 Run。后台调用到会话不能直接套用用户输入的取消规则。

## 画布上的两种组合

**内联子图**：继续使用折叠的子图卡片，标注“本次运行内执行”。进入子图查看内部节点时保持当前 Run 的身份与返回路径。

**独立调用**：在添加节点中提供“调用工作流”，选择已安装 Graph，卡片上直接显示目标名称和完成条件。例如：

```text
┌─────────────────────────┐       ┌─────────────────────────┐
│ 子图                    │       │ 调用工作流              │
│ 审核与修改              │       │ 企业微信助手 ↗          │
│ 本次运行内执行          │       │ 独立运行 · 启动后继续   │
└─────────────────────────┘       └─────────────────────────┘
```

建议将独立调用建模为 Op 的一种标准操作，不新增 Agent 类型，也不增加可随意执行宿主命令的权限。技术上是扩展 Op 的结构化操作定义；字段名称待实现前冻结。旧命令 Op 保持原语义。前端的“调用工作流”是操作类别，不要求用户知道 Op 的内部分类。

保留同一 Graph 内 Edge 的已有含义：前一节点按自身完成契约完成后，才沿已选边推进。独立调用的完成契约由模式决定；不把普通 Edge 改成跨 Run 的线，也不把多出边偷偷改为广播并发。

## 调用模式及生命周期建议

| 问题 | 等待完成 | 启动后继续 |
| --- | --- | --- |
| 调用节点何时成功 | 对应 B Run 成功，所需结果已可读取 | B Run 已持久接纳，拿到可追溯引用 |
| A 的后续节点 | 等待上述成功 | 接纳后继续，不等 B 工作完成 |
| 节点返回什么 | B Run 引用、终态、显式选择的结果与产物引用 | B Run 引用与接纳事实，不返回未完成的业务结果 |
| B 后续失败 | 调用节点失败，沿现有失败规则停止 A | B 保持失败事实；已完成的 A 不被改写 |
| 停止 A | 建议停止本次调用创建且仍在执行的 B，再核对状态 | 建议已经接纳的 B 继续；UI 可单独停止 B |
| 暂停 A | 当前调用按节点完成边界处理；暂停不等于取消 B | A 在节点边界暂停，B 独立继续 |
| 服务重启 | 找回同一个 B Run，再根据其状态等待或返回结果 | 找回原接纳事实，不启动第二个 B |

界面必须显示停止范围，不能只用模糊的“停止全部”。停止只能作用于本调用实际创建的 Run，不能按 Graph 名称停止别人触发的同图 Run。已发生的外部操作不回滚。

“启动后继续”要求先完成持久接纳，不是仅创建了一个内存线程便报告成功。若目标忙碌、校验失败或无法创建 Run，就不能把调用节点标记成功。目标有排队能力时，明确显示“已接纳，排队中”；不能把当前 HTTP 409 包装成排队。

用户已确认：多来源调用相同目标，各自创建独立 Run，默认允许并发。目标有业务串行需求时应明确限制。同一助手会话仍需串行，后台输入不能抢占用户对话。这个变更将涉及现有按 Graph 索引的 running 状态、编辑保护与恢复，不只是增加一个字段。Graph 页头应能显示多个活动 Run，修改/删除保护检查全部活动运行；单个停止操作仍以 Run 为目标。此次确认针对独立调用，既有手动/定时触发的繁忙策略是否统一调整应显式说明，不借此静默改变原有行为。

## 输入、结果和可信上下文

调用属性面板提供：目标 Graph、执行模式、输入映射、需返回的输出节点/产物，以及停止范围说明。

首期输入映射应采用有限的结构化来源：常量、本 Graph 的 input、明确上游节点的已提交文件；不新增可执行表达式语言。用户看到“来源 → 目标参数”的表单，并能预览解析后的输入。凭证不作为输入传给下一 Graph。

跨 Run 文件沿用既有 commit 快照与只读输入语义：只传被选中的产物及其稳定来源，不能把宿主路径或源 Graph 全工作区自动交给 B。等待完成后，A 的调用节点提供对 B 选定输出的只读引用，后续节点仍经普通 Edge 读取。首期无需统一所有业务报告的结构，但必须明确结果来自哪个输出节点/文件，不能猜“最后一个节点的任意字符串”就是结果。

独立 Run 不等于新建用户 Session。周报调用助手时，还需要绑定已授权的用户会话/投递目标；它属于可信执行上下文，不能因 input 中写了他人的 session ID 就获得其聊天历史。系统来源与用户输入要区分。同一助手会话繁忙时，后台请求的接纳规则需要在现有 Turn 路径上明确，不能打断当前用户 Run。

## 运行身份、恢复及限制

- 以源 Run、调用节点、节点的逻辑执行轮次建立稳定调用标识。恢复/运输重试沿用同一标识；图内循环的下一轮是另一调用。已有全局节点轮次可复用，不能使用恢复次数或会重置的局部子图计数。
- 第一次调用固定目标定义和解析后的输入，B Run 保留实际执行快照。A 恢复时找回原 B，不重新读取最新版 B 创建替代任务。现有恢复会重新读取工作区 graph.json，不能未经修正就声称已保证定义快照恢复。
- 调用关联是业务调度事实，放在已有 Run/节点控制记录的边界内；继续使用原生 Agent/Op 持久化，不另造模型恢复引擎。只有持久调用关联与可重复接纳都成立，才具备防止重复创建 B 的保证。
- 原 B 失败后的“查看”“恢复原运行”“明确重新执行一次”需要区分。普通恢复不得偷偷创建新 B；显式重做会产生新的运行身份，并保留前次失败。
- 初期目标采用可静态解析的 Graph 引用；动态由模型选择目标另行讨论。检查实际调用祖先链，拒绝尚未定义语义的递归调用，避免等待死锁及无限触发；普通 Graph 内已有反馈边不受此限制影响。
- 多个任务共用企业微信发送能力时，需解开“挂载 Plugin”与“占有入站助手绑定”的耦合；这仍由现有通道监管处理，不由每次调用另建连接。

## Web 表达：定义、执行、全局关系

### 编辑一个 Graph

调用节点仍是一张普通卡片，目标 Graph 不展开到当前画布。单击编辑参数；“打开目标工作流”进入其独立定义，并保留返回位置。目标无效在卡片及保存校验中明确指出，不等到执行时才发现。

设置模式后显示自然语言提示：

- 等待完成：“此步骤会等待「数据分析」完成，再执行后续节点。”
- 启动后继续：“「企业微信助手」被接纳后，本流程继续；助手会独立完成工作。”

不能只写 sync/async，也不能把“已接纳”写成“任务已完成”。

### 查看一次 Run

调用节点同时呈现两个互不混淆的状态：本节点的完成状态、目标 Run 的实际状态。例如：

```text
调用企业微信助手
启动后继续 · 已接纳
目标运行：正在执行    [查看运行 ↗]
```

因此，父 Run 已完成而目标仍在执行是正常状态。详情展示本次传参、源节点轮次、目标 Run 与结果引用。目标 Run 页头显示“由 周报 / Run … / 通知节点 发起”，可返回来源。等待模式则显示“等待目标完成”，而不是让用户误认为节点卡死。

运行看板保持每个 Run 独立的时间条、Graph 颜色和状态；详情标注来源调用，可按同一调用链筛选。不要在默认时间轴铺满跨行连线。

### 理解很多 Graph 的关系

提供从同一份 Graph 定义派生的关系视图：每个已安装 Graph 一个节点，调用关系显示有向连线，并标注“等待完成”或“启动后继续”。从连线可定位到来源 Graph 的调用节点；相同 A→B 的多个调用可聚合并展开查看。

默认只展开选中 Graph 的直接调用者与被调用者，按需扩展层级；保留列表形式查找。计划标记附在它直接触发的 Graph 上，被其他 Graph 调用不等于拥有独立定时计划。

关系视图是导航与事实投影，首期不另存关系、不开第二套关系编辑器。每周生成的多个 Run 不混入定义关系图；具体执行关系只在 Run 详情/调用链筛选中展示。

## 首批验收场景

| 场景 | 用户可观察的结果 |
| --- | --- |
| A 内联 B | 编辑可辨为子图；一次 Run、同一停止边界 |
| A 调用 B 并等待 | A 后续节点在 B 成功前不执行；可跳转实际 B Run 并返回 |
| A 启动 B 后继续 | A 可先完成；UI 仍显示 B 运行中，B 失败不改写 A 成功 |
| B 接纳后 A 崩溃 | 恢复后指向原 B，仅一个目标 Run；输入/定义不静默更新 |
| 调用节点在循环中执行两次 | 两个有区分的 B Run，各自可追溯；恢复不误当新轮次 |
| 两个 A 同时调用同一个 B | 按已选并发策略明确接纳/排队/拒绝，运行身份和产物不串 |

| 定义关系与运行关系 | 从关系图找到调用节点，从执行节点找到准确 Run；编辑只有一个事实来源 |

## 2026-09-30 实施契约

用户已授权按本设计开发。独立调用以 `ops.<name>.call` 表达，与旧 `run` 命令互斥；`nodes` 继续引用 `op`。call 包含 `graph`、`mode: wait|detach`，可选 `input` 常量、`input_map`（目标顶层键→来源 input 的 JSON Pointer）、`files`（上游 node/path/as）、`result`（目标 node/files，只用于 wait）、`session`（操作员指定的现有通道 Session）。文件只从调用节点可见的已提交输入选择，子运行只读挂载 `/in/call`；返回文件保存在调用节点 `result/`，调用引用保存为 `call.json`。调用身份由源 Run、节点和不随恢复改变的执行轮次确定。

源调用为 wait 时停止父 Run 会请求停止其目标；detach 已接纳的目标独立继续。不同调用默认并发；后台调用同一助手 Session 串行、不打断用户输入。动态目标、跨 Graph 递归调用、本轮对普通 Edge 增加广播语义均不在范围内。使用现有服务/Run/节点持久化，不建立第二个 Graph 调度器或模型恢复引擎。

分工：Runner/Schema 25%、服务调用与持久接纳 35%、Web 25%、主线通道集成与验收 15%。三个独立 worktree，边界和 API 先冻结，再分包测试→主线交叉测试→真实 provider/服务重启/浏览器验收。原有企业微信四项能力代码作为基线提交；未提交的部署和文档改动保留，不纳入无关提交。


## 实施补充与边界

- 新调用的控制目录使用完整节点 ID 和全局调用轮次的摘要，避免 `a` 第 2 轮与 `a-2` 第 1 轮碰撞；手动/定时 Run ID 带唯一标识，避免同秒运行复用历史。
- 会话后台执行复用独立调用的 admission 和普通 Run，不新建虚构用户消息。用户新消息先请求后台让出，再等待退出；后台恢复同一个 Run。原生命令无法确认完成时仍可返回 Uncertain，不保证每个已开始的副作用都能无人工介入恢复。
- Graph 模型完成与平台投递完成分别记录。会话仍在等待或投递时，调用详情显示 queued/running；投递失败不能作为 wait 成功。已领取发送但 ACK 不确定时由既有网关账本阻止自动重发。
- 当前 UI 的关系视图是由定义派生的一跳/全部关系列表，可点击关系定位来源节点；不建立独立的关系编辑器。运行视图保留每次调用及父子导航。
- 历史调用的双向引用参与删除保护；本轮没有提供级联删除整条历史调用链的功能。
- 独立调用开发阶段使用隔离 Session 验收；后续已按用户明确授权在本机 weekly-work-report 的 Docmost 发布后追加通知调用，绑定既有用户私聊会话，完整真实周报和平台 ACK 已通过。详见开发台账 A21/A27。

## 同一 Run 内的配对 fanout / join（2026-10-01）

用户确认：在一个 Graph、一次 Run 内，通过 `fanoutOp → 多个并行 AgentNode → joinOp` 构建局部并行；fanout 与 join 必须一一配对。分支节点属于原 Run，使用原有节点身份、独立工作区、trace 和 commit，不为实现此能力创建独立子 Run，也不要求作者拆分和安装多个 Graph。

```text
                 ┌→ AgentNode A ─┐
准备 → fanoutOp ──┼→ AgentNode B ─┼→ joinOp → 综合
                 └→ AgentNode C ─┘
```

fanout 显式激活分支；配对 join 负责等待和收束，再继续后续流程。普通节点保留既有路由语义。LLM 完成自己的局部任务，不承担启动其他分支、统计完成数量或释放 join 的职责；join 的机械收束与综合 Agent 的内容判断分别执行。

单 Run 内可以存在多个活动节点；调度器有序处理启动与完成事件、提交和状态更新。运行时将单活动游标扩展为区域内的活动节点集合，fanout/join 是结构化控制 Op。继续复用现有 Node/Harness 执行与恢复接口。

配对关系属于 Graph 定义；同一对节点被循环再次进入时，本次展开的分支状态与前次隔离。配对信息有一个权威来源，避免作者双向重复填写。以下设计检查项已按文末首期契约落地：

- 保存/解析时拒绝缺失、重复或不匹配的配对；明确分支越界、嵌套和跨区域循环的合法性。
- join 的成功条件、失败和取消传播、部分结果策略，以及哪些产物成为下游输入。
- 展开身份的持久化、活动节点恢复、重复完成通知处理及停止后迟到结果处理。
- 画布呈现配对边界与各分支状态；作者无需管理线程、锁、计数器或运行身份。

验收需要覆盖乱序完成、循环轮次隔离、启动/完成中途崩溃、恢复、停止和失败，确认 join 不提前放行、结果不串轮。状态统一记录在开发台账 A31。

### 首期实施契约（用户已授权开始开发）

- Op 恰有一种操作：`run`、`call`、`fanout: {"join": "收束节点 ID"}` 或 `join: {}`。配对引用只写在 fanout；边列出分支，不重复维护成员列表。
- 同一 Run 内每个 fanout 至少有两条分支，分支为互不重叠的串行节点链，在唯一配对 join 收束。禁止外部边进入分支、分支越界、内部选择/循环和嵌套并行，保存时明确报错。整个区域前后的选择和反馈循环继续可用。此首期范围后续可以扩展。
- join 要求本次所有分支成功并有已提交结果，才提交收束产物并向后推进一次。分支失败时请求停止活动同伴，保留已完成结果与未完成执行记录，不放行 join。用户停止取消活动节点；暂停等待活动节点结算，在节点边界暂停。
- 沿用节点输入快照及祖先输入可见性。join 生成 `join.json`，绑定本次 fanout 执行轮次及各分支结果 commit；综合节点可经现有只读输入读取分支证据。
- `RunState.active` 为节点 ID 到原 cursor 形状的映射；非并行旧路径保留 `cursor`。`RunState.parallel` 保存当前区域的 fanout、join、invocation 和本轮进度，所有写入由原调度线程完成。字段缺省兼容旧 Run。
- 活动节点沿用原生 completion fact / Harness 历史恢复。并行 Graph 的控制记录按完整节点 ID 和执行轮次摘要隔离，trace 按节点摘要和执行轮次隔离；旧串行 Run 路径保留。跨会话步骤引用读取各 Run 自己的定义快照，新增/移除并行结构后仍能找到旧记录。未完成会话分支保留文件快照，不把它标记为成功。
- Schema/区域校验（约 20%）与 Web 作者/观察入口（约 20%）独立实现，主线负责调度/恢复（约 40%）和集成/真实验收（约 20%）。依赖顺序为契约 → Schema + Web → 调度集成 → 故障及真实运行验收；运行时共享状态由主线单独维护。
