# 长运行语言模型代理图的工作集：先例核查

核查日期：2026-09-11。范围：仅一手论文及厂商官方工程文章；提交了 5 个搜索查询，但网页工具未返回可见结果，随后直接抓取下列已知一手 URL 核对正文及日期，未追加搜索、未派生子代理。因此这是定向先例核查，不是搜索结果覆盖性调查。未获得白皮书全文及其参考文献清单，以下针对任务给出的三项主张，而不认定其实际审阅范围或实现缺陷。本文区分“逐步选择已有可行机制”与“选择质量、最小性或最优性已获保证”。

## 结论

1. **“没有已审阅方法回答这一步需要什么”不能扩写为领域空白。** 至少从 2023 年的 MemGPT 到 2025 年的官方 context engineering，已经存在由查询、代理判断、任务阶段和上下文预算决定当前输入的方案。[1–3] 若主张仅限某份已审阅清单，应公开清单，并解释为何排除这些直接相关先例。
2. **“缺少宿主活动窗口必然导致节点输入重复”是待验证的架构因果主张。** 宿主维护有界工作上下文，以及将持久状态转换为单次模型输入，都已有先例。[1,3] 但这些资料不保证跨节点零重复；重复也可能来自有意传递公共指令、并行任务的必要交集或实现选择。
3. **“工作集所有权未解决”须拆分。** 谁持久化状态、谁控制窗口、谁选择载入内容已有具体分工。[1,3,4] 尚可研究的是多节点并发下的统一版本、权限、失效和预算仲裁契约，以及可检验的选择质量，而不是笼统宣称不存在所有者。

## 最强一手先例

### [1] MemGPT：显式分层内存、宿主窗口和分页检索

- 来源：Charles Packer 等，*MemGPT: Towards LLMs as Operating Systems*。arXiv 初稿 **2023-10-12**；本次核对 **v2，2024-02-12**，不是将后续版本倒算到首发日期。
- 精确机制：§2.1 将主上下文分为系统指令、working context 和 FIFO 消息队列；§2.2 的队列管理器维护队列、发出 token 压力警告并执行驱逐/摘要；LLM 通过函数读写可编辑内存并检索外部存储。§2.3 明确将检索结果分页，代理可继续请求后续页。这是“宿主持有活动上下文 + 代理决定显式调页”的直接先例。
- 所有权：运行时负责窗口约束和实际数据移动，LLM 负责调用哪些内存操作。它并不是完全无管理者地给每个节点重传所有状态。
- 限制：论文主要在长期对话与文档问答上评估，不是任意并发代理图；§3.2.1 明确观察到代理常在遍历完整检索库之前停止翻页，因而可能漏掉正确文档。这比抽象的“未证明最优”更直接地展示选择策略的不足。分页面向检索结果，不能自动等同于带租约、版本和引用生命周期的通用 artifact 服务。
- URL：https://arxiv.org/abs/2310.08560
- 核对正文：https://arxiv.org/html/2310.08560v2

### [2] Anthropic：逐次推理的上下文整理、即时加载与子代理

- 来源：*Effective context engineering for AI agents*，**2025-09-29**。
- 精确机制：文章将上下文工程描述为每次推理时整理有限上下文；just-in-time 模式保留文件路径等轻量引用，按需调用工具加载，并逐步探索。长期任务的其他机制包括压缩、结构化外部笔记和子代理返回凝练结果。
- 意义：直接讨论“下一次调用应带哪些内容”，不是仅解决存储或扩大窗口。按需引用也可避免把完整工具结果沿图传播。
- 限制：是工程实践，不是可验证的逐节点依赖求解器；搜索可能遗漏，压缩可能丢失信息，多代理还引入协调成本。文章中的“最小高信号集合”是设计目标，不是已证明的最优性结论。
- URL：https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

### [3] LangChain：状态、逐步输入选择与显式压缩节点

- 来源：LangChain 官方，*Context Engineering for Agents*，**2025-07-02**；当次页面显示署名 The LangChain Team。
- 精确机制：以 write/select/compress/isolate 分类；selection 直接针对代理每一步取哪些上下文。LangGraph 的 state 用于保存工作流信息，文章说明可在代理图任意位置压缩上下文，并示例用独立节点总结工具输出；其他选择方式包括记忆、工具和知识的检索。
- 意义：把图的持久状态与当前推理输入的选择过程分开，已有图级实践；不能仅因一个系统显式命名了 working set 就认定此前不存在该机制。
- 限制：该文章不足以证明宿主具有统一活动窗口 API，也不证明字段级读集、自动去重、并发写隔离或选择器完整性。状态容器不等于依赖分析器，开发者仍需指定选择/压缩策略。
- URL：https://blog.langchain.com/context-engineering-for-agents/

### [4] Anthropic MCP 代码执行：查询驱动发现、过滤和外置产物

- 来源：*Code execution with MCP: Building more efficient agents*，**2025-11-04**。
- 精确机制：按需发现工具定义；在执行环境先过滤、连接和转换返回数据，再把必要结果交给模型；允许中间结果保留在执行环境中，并使用文件保存状态。这是“大对象不必进入模型窗口，当前步骤通过程序取得所需视图”的直接先例。
- 限制：文中从约 150,000 降至约 2,000 token、节省 98.7% 是所举示例，不能泛化为所有工作流的实验结论。执行环境本身增加隔离、安全和生命周期管理责任；不保证模型生成的查询正确，也不定义通用代理图工作集一致性协议。
- URL：https://www.anthropic.com/engineering/code-execution-with-mcp

## 已有机制与仍需证明的问题

| 问题 | 已有先例能支持什么 | 不能据此声称什么 |
| --- | --- | --- |
| 当前调用需要什么 | 查询检索、按需加载、工具发现、任务相关过滤和人为编写的状态选择策略 [1–4] | 自动得到必要且充分的最小集合 |
| 有界活动窗口 | 主上下文、FIFO、预算警告、摘要和驱逐 [1] | 任意代理图共享一个一致且最优的活动窗口 |
| 大结果或产物外置 | 分页检索、路径引用、执行环境内处理和文件持久化 [1,2,4] | 所有 artifact 都具备分页、版本、租约及失效通知 |
| 减少节点间重复 | 子代理摘要、独立压缩节点、执行侧过滤 [2–4] | 零重复，或输入重复完全由缺少宿主窗口造成 |
| 工作集所有权 | 运行时管理队列，模型调页；图状态与开发者选择策略；执行环境保管中间数据 [1,3,4] | 跨节点权限、并发写和冲突处理已被统一解决 |
| 选择质量 | 特定任务评估与工程经验 [1–4] | 跨任务最优性、完整性或稳定成本收益保证 |

“上述来源未证明”不等于“整个领域无人解决”。特别是并发、权限和版本等候选缺口仍需另行查新；本次有限检索不能给出排他性新颖性结论。

## 建议的白皮书表述与验证

建议替换为：

> 已有系统提供分层内存、按需检索、上下文压缩、状态隔离及执行侧过滤。本文关注将这些能力整合为长运行代理图中的显式、宿主管理的逐步工作集协议，并明确其所有权、预算与生命周期。本文不主张首次提出上下文选择，也不主张已经解决选择最优性。

其中“协议”仍须由实现证据支持。建议展示：状态所有者与单次读者的边界、节点声明或推断读集的方式、窗口与外置引用的生命周期、并发和失效策略；比较全量状态、手工逐节点投影、检索/分页、摘要和外置产物基线。报告任务成功率、遗漏必要证据、重复输入 token、延迟及外部调用成本；将必要公共输入与可避免重复分开计量。否则无法把收益归因于宿主工作集，也无法支持独立的新颖性主张。
